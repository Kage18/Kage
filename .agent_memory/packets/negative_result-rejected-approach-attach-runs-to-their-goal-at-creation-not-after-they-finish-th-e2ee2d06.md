# Rejected approach: Attach runs to their goal at CREATION, not after they finish — the orch

> A delegated attempt at "Attach runs to their goal at CREATION, not after they finish — the orchestrator wake loop is …

A delegated attempt at "Attach runs to their goal at CREATION, not after they finish — the orchestrator wake-loop is dead because of this ordering. In mcp/index.ts the kage_dispatch handler does `const result = await dispatchRun(...)` and only THEN resolves the goal (explicit goal_id, else the room threads active goal) and calls attachRunToGoal. But dispatchRun executes the ENTIRE run — agent work plus verification — before returning, so for the whole life of the run goalForRun(runId) returns null; notifyManagerOfRunEvent bails at its first check, nothing is appended to the goals pending-events log, and the manager is never woken. Verified live: a goal-owned run went from dispatch to failure without a single event being recorded, and the attachment only appeared after the run was already dead. FIX: (1) add an optional goalId to DispatchOptions in mcp/delegation/dispatch.ts and, inside dispatchRun, call attachRunToGoal(projectDir, goalId, task.id) IMMEDIATELY after createRun (before the brief is written and long before the agent runs), tolerating an unknown goal id the same way the handler does today — a warning path, never a failed dispatch. (2) In mcp/index.ts, resolve the goal id BEFORE calling dispatchRun (explicit args.goal_id, else readActiveGoal for the room thread when KAGE_ROOM is 1) and pass it through DispatchOptions; remove the post-hoc attach. (3) Do the same for the POST /runs route in mcp/delegation/api.ts if it attaches after creation — attachment must always precede execution. TESTS in mcp/delegation.test.ts in a clearly separated block at the END of the file: a dispatch with a goalId has goalForRun resolving the run BEFORE the adapter is invoked (use the stub adapter and assert inside its run callback, or assert on the goal record immediately after a briefOnly dispatch); an unknown goal id still dispatches and warns. Success = npm test fully green." was rejected.

Reason: Never started: dispatched but no supervisor process ever spawned and no agent session was created, so it could not even be resumed (tell correctly refused with no agent session). Redispatching the identical intent. Worth watching: a dispatch that silently produces no supervisor leaves a run stranded in dispatched forever, with no reaper coverage since the reaper only handles running/dispatched/verifying with a DEAD pid — here there was never a pid at all.
