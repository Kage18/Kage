# Help drifted until the flagship command was undiscoverable — now gated

> kage help listed 12 core commands and kage app was not among them, so the desktop app — the surface the product is so…

`kage help` listed 12 core commands and `kage app` was not among them, so the desktop app — the surface the product is sold on — could not be found from the CLI at all. `kage viewer`, the legacy dashboard being retired, was advertised in its place, and the entire orchestrator (room, dispatch, runs, review, merge) was absent. 115 commands are implemented; 32 were documented. The tagline still described Kage as memory only, with no mention of orchestration.

This is a drift failure rather than a coding error: help text is prose, nothing verifies it, and it silently stops describing the product as the product changes. CORE_USAGE in mcp/cli.ts is now organised by what a person does (Start here / Delegate work / Memory / Keep it healthy) and a test in mcp/release.test.ts parses CORE_USAGE, asserts every `kage <name>` it advertises has a matching `command === "<name>"` implementation, and requires app, room, dispatch, recall and install to stay listed. The gate is cheap and catches both directions — advertising a command that does not exist, and quietly dropping one that must stay findable.

Worth remembering when adding any new top-level surface: shipping it is not the same as making it discoverable, and only the second one reaches users.
Evidence: `node mcp/dist/cli.js help` before the change listed install/scan/init/index/recall/learn/gains/verify/setup/doctor/repair/viewer and no app, room, dispatch, runs, review or merge. After: all sixteen advertised commands were confirmed to have implementations, and the new gate fails if any advertised command is missing or if a flagship one is dropped.
