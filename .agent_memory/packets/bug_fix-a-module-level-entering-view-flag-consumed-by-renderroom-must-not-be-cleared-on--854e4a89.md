# A module-level 'entering view' flag consumed by renderRoom must NOT be cleared on a ren...

> A module level 'entering view' flag consumed by renderRoom must NOT be cleared on a render where turns.length is 0 e.…

A module-level 'entering view' flag consumed by renderRoom must NOT be cleared on a render where turns.length is 0 (e.g. switchThread's own synchronous empty-placeholder render before its async refreshRoom() reply lands) — clearing it there means the REAL history that arrives a moment later renders un-pinned. The fix is to only spend the flag on a render that actually has turns to pin to.

Learned while delivering: Redo of a rejected run, with its failure understood: two small Room fixes. (1) CHAT OPENS AT TOP — on entering the Chat view the thread must render pinned to the NEWEST turn, stay pinned while new turns stream when already at bottom, and preserve the user's position otherwise (standard chat behavior); presentation-only in app-client.ts. (2) COLD-PTY IDENTITY WINDOW — the previous attempt raised PTY_IDENTITY_POLL_TIMEOUT_MS from 5000 to 20000 directly, and the suite then timed out at 1200s three times: every pty test that exercises the deflection path waits the full window in REAL time. Do it through the seam instead: the pty leg already has ctx.waitForRoomSessionIdentityFn (injectable) — keep the production default window at 20000ms but ensure every test that reaches this path injects a short wait (or inject via the existing seam/test context so no test ever sleeps the production window), and add one unit test asserting the production constant is 20000 WITHOUT waiting it out. Run the full suite yourself and confirm its wall-clock stays in the normal range (~2-4 min) before claiming — a suite that got minutes slower means a real-time sleep leaked into tests. Use the kage-claim-v1 fence properly (the prior attempt skipped it). Template-literal constraints; cite files individually.
