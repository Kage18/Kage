# Markdown table-cell regex assertions in a doc-guard test need to account for the bold-c...

> Markdown table cell regex assertions in a doc guard test need to account for the bold close immediately before a tabl…

Markdown table-cell regex assertions in a doc-guard test need to account for the bold-close ** immediately before a table pipe (e.g. '**M2 — the memory-side port** | Not yet built' has ** between the phrase and the |) -- a naive \s*\|\s* pattern right after the phrase text fails to match and would have made the new guard test self-broken; caught this by actually running the test rather than trusting the regex by inspection.

Learned while delivering: M1 of the memory store: build the StoreBackend layer itself, exactly as docs/design/MEMORY_STORE.md (just landed on this branch) specifies. New files under mcp/store/ ONLY - this run touches no existing file except to add nothing at all; the ports that wire it into kernel and graph reads come in M2/M3, not here.

READ FIRST: docs/design/MEMORY_STORE.md end to end - it is the contract for this run, it was verified against the code today, and your work must match it or say precisely where and why it deviates. Key laws from it: markdown packets stay the only truth and the store is a derived, rebuildable cache; ZERO new npm dependencies - the sqlite backend uses node's built-in node:sqlite behind feature detection (engines is >=18, so absence is a normal, first-class state, not an error); when node:sqlite is absent the JSON backend preserves today's semantics; no account, no server, an embedded file under .agent_memory/ only.

WHAT TO BUILD, all under mcp/store/:
1. types.ts - the StoreBackend interface, exactly the seam the design names: open/close/migrate; upserts for files, symbols, import and call edges; upserts for packets, packet_paths, packet_symbols; FTS document upsert + query; vector chunk upsert + nearest query; kg entity/edge/episode upserts and reads; the scoped variants that take a subtree path prefix. Every method's contract in a doc comment - the M2/M3 ports will be written against these words.
2. sqlite.ts - the node:sqlite backend. Schema per the design's sketch (files, symbols, edges, packets, packet_paths, packet_symbols, an FTS5 virtual table, vectors as per-chunk BLOB rows, kg_entities/kg_edges/kg_episodes), WAL mode, a schema_version pragma-table and forward-only migrate(). Feature detection lives here: a single detect() that try-requires node:sqlite and reports {available, reason} - never a throw at import time, and TypeScript must not need @types for it (use a narrow local declaration; no new deps).
3. json.ts - the JSON backend: an adapter over TODAY'S file layout (indexes/, graph/, structural/ as the design records them) implementing the same interface read-side, and write-side preserving current whole-file behaviour. It must NOT re-implement ranking - it serves rows; ranking stays with the callers.
4. manifest.ts - reads/writes .agent_memory/store/manifest.json: active backend, schema version, counts, last rebuild. openStore(projectDir) picks sqlite when detect().available and the manifest allows, else json - one function, the only door M2/M3 will use.
5. rebuild.ts - rebuildStore(projectDir): regenerate the ENTIRE derived store from packets + the structural file cache, idempotent, safe to run anytime; this is what makes 'derived cache' true rather than aspirational. Wire NOTHING into the CLI yet - M2 owns the `kage store` commands; export it and prove it in tests.

TESTS - new file mcp/store-layer.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover at minimum: detect() reports available on this machine and the suite still passes when node:sqlite is FORCED absent (inject the require seam - the fallback path must be tested, not assumed); sqlite backend round-trips every entity type (file, symbol, edge, packet, packet_path, FTS doc, vector chunk, kg triple) and survives close/reopen; migrate() is forward-only and re-running it is a no-op; FTS query returns the doc a term appears in and not one it does not; the scoped variants restrict to the subtree prefix; json backend serves the same read answers as today's files for a small fixture; rebuildStore() on a fixture project produces a store whose counts match the fixture; manifest round-trips and openStore() honours a forced backend. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS - no import.meta (TS1470), no top-level await. Zero new entries in package.json dependencies or devDependencies - the diff to package.json must be EMPTY. Do not touch mcp/kernel.ts, mcp/cli.ts, mcp/index.ts, mcp/daemon.ts, anything under mcp/delegation/, or any existing test file - the budget run owns several of those right now. Build and test ONLY inside your own worktree - never run npm, tsc or node against /Users/kushaljain/code/Kage.
VERIFY: npm run test --prefix mcp (882 unit + 12 dogfood green before your change) and npm run build --prefix mcp with no 'error TS'. Run them for real and fill in the claim fence.
