# REVERT CHECK for the new tests added this turn: reverting displayElapsedMs/its wiring i...

> REVERT CHECK for the new tests added this turn: reverting displayElapsedMs/its wiring into report.ts or tui/app.ts fa…

REVERT CHECK for the new tests added this turn: reverting displayElapsedMs/its wiring into report.ts or tui/app.ts fails 'displayElapsedMs: idle/stopped time never counts...' and 'kage status (renderStatusBoard) shows work time for a stopped run...'; reverting the kage config daemon-warning fails 'kage config warns to restart a LIVE daemon...'.

Learned while delivering: resume-run cannot resume a run stopped on the MINUTES cap - which is most of them - and it misreports which cap tripped. Three runs in this repo are stranded on exactly this right now.

WHAT I OBSERVED, immediately after resume-run landed and I used it for real:
1. `--budget-minutes` IS ACCEPTED AND SILENTLY IGNORED. I ran `kage resume-run <id> --budget-usd 40 --budget-minutes 240` on two runs. Both came back "budget raised to $40.00" and both re-stopped within a minute, still capped at 30m. The signature is the cause: resumeStoppedRun(project, runId, budgetUsd, adapterByName) in mcp/delegation/recovery.ts takes no minutes parameter at all, and mcp/cli.ts around line 2839 reads only --budget-usd for this command. The flag exists for `kage config` and was never wired here. A flag that is parsed and discarded is worse than one that errors.
2. THE REFUSAL NAMES THE WRONG CAP. For a run stopped on minutes, resume-run says: "<id> stopped at $2.78 spend against a $40.00 budget. Resume it with a higher budget: kage resume-run <run-id> --budget-usd <n> - e.g. --budget-usd 80.00." $2.78 against $40 is not a budget problem and raising it to $80 cannot help. It was 59.8 minutes against a 30 minute cap. Report the cap that actually tripped, with its real numbers.
3. RAISING CONFIG DOES NOT HELP EITHER, though the kernel's own stop note advises exactly that: "raise it by setting `budgets.minutes` in .agent_memory/config.json". I set it to 240 with `kage config --budget-minutes 240` and resume-run still refused, because a run's budgets are stamped at dispatch and resume never refreshes them. Either honour config on resume or stop advising it; do not leave advice that does not work.
4. THE MINUTES METER LOOKS LIKE WALL CLOCK, INCLUDING TIME SPENT STOPPED. Two runs sat idle for an hour and came back reading 91.2m. If elapsed keeps accruing while a run is stopped, every stopped run is over its cap the moment you try to recover it, and resume-run can never work for the case it exists for. Establish what the meter actually measures, say so in your claim, and if it counts idle time make it count work.

WHAT TO BUILD:
1. Thread a minutes budget through resume-run end to end - CLI flag, recovery.ts signature, the record it writes - and prove it by resuming a run that is over its minutes cap.
2. Make every budget refusal and stop note name the cap that tripped, its observed value and its limit, and the one command that fixes THAT cap. One message per cause; no dollar advice for a minutes stop.
3. Decide and state whether resume should re-read config budgets, and make the kernel's stop note agree with whatever you choose.
4. Fix the meter if it counts idle time.

ALSO IN SCOPE, same area, and the reason two runs went missing today: dispatchDetached in mcp/delegation/dispatch.ts spawns the supervisor with stdio: "ignore", so when a supervisor dies there is no log anywhere and no reason recorded. Two runs today lost their supervisor seconds after dispatch and left nothing but a dead pid and a live orphaned agent. Give each run's supervisor a log file it can die into. Small change, and it is the difference between an hour of forensics and one glance.

ACCEPTANCE, demonstrate it: recover fix-the-resumed-manager-permission-trap-260819-1bc4 (stopped, 91.2m against a 30m cap) using shipped commands only, and quote the command and its output. That run holds real work I intend to land.

TESTS - new file mcp/resume-budgets.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: a minutes-stopped run resumes when the minutes cap is raised; --budget-minutes is never silently dropped; a refusal names the cap that tripped and not another one; the supervisor spawn requests a log destination rather than discarding output. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS - no import.meta (TS1470), no top-level await. Do NOT touch mcp/index.ts, mcp/response-cap.ts, mcp/delegation/room-pty.ts, room-supervisor.ts, app-client.ts, app-html.ts or app-styles.ts - three other runs own those and I intend to land them. Build and test INSIDE your own worktree only; never run npm, tsc or node against /Users/kushaljain/code/Kage.
