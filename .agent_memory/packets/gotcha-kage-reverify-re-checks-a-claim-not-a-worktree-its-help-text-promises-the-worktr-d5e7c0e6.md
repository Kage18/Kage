# kage reverify re-checks a CLAIM, not a worktree — its help text promises the worktree

> kage reverify <run id cannot recover a run that never produced a claim. It refuses with "Run <id has no claim to reve…

`kage reverify <run-id>` cannot recover a run that never produced a claim. It refuses with "Run <id> has no claim to reverify." even when the run's worktree holds complete, correct work. The CLI help line for the command reads "re-check a failed/ready run's current worktree — no agent re-run", which promises worktree-based recovery the code does not implement. This matters most in exactly the case where recovery is needed: when a supervisor dies before its agent finishes, no claim is ever captured (the supervisor is what parses the agent's claim fence), so the one command that looks like the recovery path is the one that cannot help. Do not plan an orphan-recovery flow around reverify without first checking whether a claim exists.
Evidence: Run the-predicted-touch-set-is-uncorrelated-260819-ecbd: supervisor died seconds after dispatch, agent worked ~20 minutes and produced 196 insertions across mcp/delegation/brief.ts, preflight.ts, verify.ts plus a new mcp/touch-set.test.ts. Run state failed, worktree intact. `node mcp/dist/cli.js reverify the-predicted-touch-set-is-uncorrelated-260819-ecbd --project .` printed "Run the-predicted-touch-set-is-uncorrelated-260819-ecbd has no claim to reverify." and exited 0 without re-checking anything.
Verified by: kage reverify invoked against a failed run with an intact worktree and no claim; refusal reproduced
