# Room threads are conversations, not workspaces — and the default thread never moves

> The room now supports several concurrent conversations per project mcp/delegation/room sessions.ts , which looks like…

The room now supports several concurrent conversations per project (mcp/delegation/room-sessions.ts), which looks like AO's session tabs but is deliberately a different object. In AO a session IS the unit of work, so tabs are how you get parallelism. In Kage the units of work are runs in worktrees and the room is the manager who dispatches them, so threads exist only so unrelated conversations don't share one context — dispatching from any thread still produces an ordinary run on the same board. The UI encodes this: the tab strip sits on the right, away from Chat/Terminal (which are two views of ONE thread), and a lone thread renders no tabs at all. If runs, diffs, or state ever start hanging off a thread, that is the bug.

Two backward-compatibility constraints are load-bearing and must not be "cleaned up". First, the default thread ("main") keeps the historical FLAT layout at .agent_memory/room/{history,session,supervisor,pty-supervisor}.json; only additional threads nest under room/s/<key>/. There is no migration step, because a migration that half-fails is a bad trade for a convenience feature. Second, "main" keeps its ORIGINAL socket digest seeds (`<dir>\0__room__` and `<dir>\0__room_pty__`, without the key appended) — callers locate a supervisor by probing that path, so changing it would make a live manager look dead on upgrade and silently respawn underneath a conversation in progress. room-sessions.test.ts asserts both by recomputing the pre-threads digests directly.

The SSE stream stays shared while the screens are not: room deltas and pty frames now carry a `session` field, and the client drops anything from a thread it isn't showing (a background thread only gets a dot on its tab). Late-arriving fetches are also checked against the thread they were asked for, since a reply that lands after a tab switch belongs to the thread it was asked about.
Evidence: Verified against the live daemon, not only in tests: creating a thread returns thread-2, GET /room still shows the default thread's real 6-turn history, GET /room?session=thread-2 returns 0 turns, and closing "main" is refused with 400. In the browser, switching to the second thread shows an empty primer with no bleed and switching back restores the full transcript including the PLUM77 exchange.
Verified by: npm test — 528 pass 0 fail (7 room-sessions tests, 3 new thread API tests); plus live curl against the daemon and a browser round-trip
