> contract.ts's ensureDelegationIgnores has no test asserting its exact needed paths list, so adding '.agent memory/goa…

contract.ts's ensureDelegationIgnores() has no test asserting its exact needed-paths list, so adding '.agent_memory/goals/' to it was safe with no expected fallout.

Learned while delivering: GOALS O1 — the orchestration substrate (backend only; a later run owns all UI; do not touch app-client.ts, app-html.ts, app-styles.ts). Make the Room manager an event-driven orchestrator of multi-run goals, using only primitives that already exist. Read first: mcp/delegation/room-supervisor.ts (the held manager session and how frames are written to its stdin), mcp/delegation/manager-prompt.ts (the constitution), mcp/delegation/manager-client.ts (MANAGER_ALLOWED_TOOLS), mcp/delegation/api.ts (the feed and run routes), mcp/delegation/contract.ts. BUILD: (1) GOAL RECORD, new module mcp/delegation/goal.ts: {id, intent, state: planning|executing|done|abandoned, plan: waves[] where each wave is parallel run specs {intent, type, files_scope: string[] advisory partition}, run_ids per wave, autonomy: recommend|merge (default recommend), budgets {usd, runs}, created_at/updated_at, state_history} — atomic writes like task.json, store under .agent_memory/goals/<id>/goal.json, with createGoal/readGoal/listGoals/patchGoal/attachRunToGoal/goalForRun helpers. (2) EVENT BRIDGE in room-supervisor.ts: export a notifyManagerOfRunEvent(projectDir, runId, event) that, when the held room session is live AND the run belongs to an active goal, writes a compact system-context user frame into the held stdin — one line like [kage event] run <id> (<goal intent>) is now <state>: <question or check summary> — rate-limited (drop duplicate states per run, max one frame per run per 30s) and NEVER injected for runs outside goals (a human-only run must not wake the manager). Wire the daemon: in mcp/daemon.ts where the delegation feed notifies run changes, call the bridge best-effort (try/catch, must never break a request). (3) CONSTITUTION: extend manager-prompt.ts with the orchestrator playbook — when the user gives a large goal, propose a decomposition as waves with disjoint file scopes and ask approval before dispatching; dispatch a wave in parallel with kage_dispatch respecting max_concurrent; on a [kage event] blocked frame, answer via kage_tell ONLY when the answer is derivable from the brief or the goal plan, otherwise leave it for the human; on failed, read the evidence and either steer one precise fix or report; on ready, review the receipt and RECOMMEND the merge unless the goal autonomy is merge; always report wave completion crisply. (4) API in api.ts: GET /goals, GET /goals/:id, POST /goals {intent, plan?, autonomy?} (create, state planning), POST /goals/:id/abandon. Dispatches stay through existing routes — attach a run to a goal via an optional goal_id on POST /runs (thread it through to attachRunToGoal). (5) TESTS in mcp/delegation.test.ts and mcp/delegation-api.test.ts with existing seams (room supervisor fakes, feed harness): goal record lifecycle + legality; the bridge writes exactly one rate-limited frame for a goal-owned run and NONE for a goal-less run (fake held-session seam records frames); goal routes round-trip; POST /runs with goal_id attaches. Diff budget 800. Success = npm test fully green.
Verified by: npm test --prefix mcp, diff-size, citations
