# renderDetail()'s .dclose button now renders in BOTH List and Board layouts (previously ...

> renderDetail 's .dclose button now renders in BOTH List and Board layouts previously Board only ; visibility is CSS g…

renderDetail()'s .dclose button now renders in BOTH List and Board layouts (previously Board-only); visibility is CSS-gated (display:none by default, #v-work.layout-board .dclose unconditional, #v-work:not(.layout-board) .dclose only under the narrow media query) — any future change to the 'how do I get back' control in Work should know this button already serves both roles.

Learned while delivering: Make Kage's app usable on a phone-width screen. We just shipped LAN mode so a phone can reach the daemon - and this is the page it reaches.

WHY NOW, and why this is not "someday responsive polish": the LAN-mode run that merged today exists so a user can point their phone at Kage over their own network. That capability is worthless if the page it lands on is broken, and right now it is. This is the follow-through on work already shipped, not new scope.

THE MEASURED DEFECTS. I measured these in a real browser on the live daemon this session, with getBoundingClientRect and getComputedStyle - not by reading CSS:

1. THE TOPBAR OVERFLOWS AND CLIPS. .top has clientWidth 390 but scrollWidth 565 - 175px of the nav is off-screen with no wrap and no scroll. The notification bell is sliced in half at the right edge. This is the worst of the three, because nothing tells the user the controls are missing.

2. THE WORK LIST IS CRUSHED, WITH A 235px DEAD ZONE UNDER IT. #work-split resolves to grid-template-rows: 379.5px 350.5px. Inside the first row, .list has max-height:38% - and that percentage resolves against the 379.5px ROW, not the container, so it compounds: the list renders 144px tall while its own scrollHeight is 1404px. The detail pane starts at y=466 while the list ends at y=230. That is 235 blank pixels of nothing, mid-screen, between two panes. The rule is mcp/delegation/app-styles.ts line ~852, inside @media (max-width:900px).

3. THE BOARD OVERFLOWS BY CONSTRUCTION. Same media block: .board { grid-template-columns:repeat(2, minmax(220px,1fr)) }. Two 220px floors plus the gap cannot fit in 390px, so the board scrolls sideways on a phone.

ROOT CAUSE, stated plainly so you do not just patch the symptom: the entire stylesheet has exactly THREE @media queries (lines ~89, ~166, ~851 of app-styles.ts) and one of them is prefers-reduced-motion. There is no narrow-width design - there is a 900px afterthought that was never opened at 390px. Fix the design for narrow widths; do not add a fourth patch on top of the third.

WHAT TO BUILD:
1. A real narrow layout for Work. On a phone the list-plus-detail split does not work; pick ONE model and commit to it - most likely list first, and selecting a run replaces the view with the detail plus a back affordance. Whatever you choose: no dead zones, and no pane shorter than its own content when there is room. Say in your claim which model you chose and why.
2. A topbar that fits. Every control must be reachable at 390px. Collapsing labels to icons, wrapping to a second row, or moving secondary controls into an existing menu are all fine. Inventing a new hamburger menu that duplicates navigation that already exists is not - Kage already has a command palette and a settings surface; prefer them over a new pattern.
3. A board that fits: one column at phone width.
4. Check the Room at 390px too. It is the front door and I did not measure it - measure it, report what you find, and fix it if it is broken. If it is fine, say that; "I checked and it was already correct" is a real result.
5. Do not regress the desktop layout. The desktop app is the primary surface and it is currently right.

DESIGN LANGUAGE: read mcp/delegation/app-styles.ts and match what is there - the same type scale, the same mono/sans split, the same surface and line tokens. Do not introduce a new visual system for small screens, and do not import a framework. This stylesheet has no build step and no dependencies; keep it that way.

TOUCH: this is a phone, so tap targets need to be tappable. Kage's rows and chips are sized for a mouse. Raise hit areas at narrow width where it costs nothing. Do not change the desktop hit areas.

TESTS - new file mcp/narrow-layout.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). The composed page is a string, so test it as one: assert the narrow media block exists and contains the rules that fix each of the three defects above; assert .board is single-column below the phone breakpoint; assert the desktop rules are still present and unchanged; and keep the existing composed-page parse gate green. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS - no import.meta (TS1470), no top-level await. app-client.ts and app-styles.ts are TS TEMPLATE LITERALS: client-side escapes must be DOUBLED, no backticks, no ${ }, never innerHTML. Do not touch mcp/delegation/room-supervisor.ts or mcp/delegation/room-pty.ts - another run is editing those.
VERIFY: npm run test --prefix mcp (798 green before your change - use the "npm run test" form) and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence.
