# The Goals orchestrator plans and displays but never executes: no state advance, no manager goal tools, and auto-attach files runs into the LAST wave

> Audited on 2026 08 18: the Goals feature O1 substrate + O2 surface is a shell. It captures a plan, renders it, and br…

Audited on 2026-08-18: the Goals feature (O1 substrate + O2 surface) is a shell. It captures a plan, renders it, and bridges run events to the manager, but nothing drives a goal forward. Four concrete defects, each verified against the source:

1. transitionGoal in mcp/delegation/goal.ts has exactly ONE caller — abandonGoal, which passes "abandoned". Nothing anywhere transitions a goal to "executing" or "done". A goal is born "planning" and the only exit is the user clicking Abandon in the app. This is the same zero-callers disease that already bit reapRun, looksLikeGitRepo and resolveWorkspaceKind in this repo.

2. attachRunToGoal files a run into a wave via patchGoal but deliberately does not transition the goal, so even the first attached run leaves the state at "planning".

3. MANAGER_ALLOWED_TOOLS in mcp/delegation/manager-client.ts contains no goal tool of any kind. manager-prompt.ts explicitly instructs the manager to "propose a decomposition into waves of parallel runs with DISJOINT file scopes" and to act as the orchestrator, but the manager has no tool to create a goal, read goal status, or mark a wave or goal complete. Goals can only be created through POST /goals from the app's alt-Enter path.

4. attachRunToGoal defaults waveIndex to waves.length - 1 (the LAST wave) when the caller passes none — and dispatchRun's implicit attach passes none. In any multi-wave plan every auto-attached run is therefore recorded against the FINAL wave, leaving wave 1 permanently empty. This is masked today only because every goal created so far has a single wave. app-client.ts compounds it: it derives progress as the count of waves with a non-empty run_ids, so the displayed "wave N of M" is wrong as soon as a plan has more than one wave.

Observed consequence: two real goals on disk sit in state "planning" even though runs WERE dispatched into them and finished — 2 and 3 runs respectively. A goal whose runs have all completed still reports "planning". CORRECTION: an earlier version claimed 0 runs attached; that read the top-level run_ids field, which is not where attachment lives — runs are recorded in plan.waves[].run_ids.

The wake-loop itself is fine and proven; see the companion packet on goal wake-loop verification. What is missing is the engine: state advance driven by real run outcomes, manager-side goal tools, correct wave indexing, and budget enforcement (DEFAULT_GOAL_BUDGETS exists and is never consulted at dispatch).
Evidence: grep for transitionGoal across mcp/**/*.ts excluding tests returns only its definition (goal.ts:177) and the abandonGoal call (goal.ts:194). MANAGER_ALLOWED_TOOLS (manager-client.ts:11-23) lists kage_room_state, kage_events_since, kage_compile_brief, kage_dispatch, kage_task, kage_tell, kage_stop, kage_merge_run, kage_reject_run, kage_report, kage_judgment — no goal tool. attachRunToGoal (goal.ts:203-210) computes index = waves.length - 1 when waveIndex is undefined and returns patchGoal with only the plan changed. Reading each .agent_memory/goals/*/goal.json and FLATTENING plan.waves[].run_ids shows state "planning" with 2 and 3 completed runs respectively — the top-level run_ids field is empty on both and is not where attachment is stored.
Verified by: Direct source reads plus on-disk goal.json inspection on branch release-prep
