# mcp/kernel.ts's beliefStaleReason two-hop check (belief -> packet -> packet's own recal...

> mcp/kernel.ts's beliefStaleReason two hop check belief packet packet's own recallStaleReason cascades false positive …

mcp/kernel.ts's beliefStaleReason two-hop check (belief -> packet -> packet's own recallStaleReason) cascades false-positive staleness from monolithic hot files (kernel.ts, delegation/*.ts) because nearly every merge touches SOME cited code path in SOME packet; after the 2026-08-22 lineage-status fix, 49/61 beliefs were still withheld this way, verified live via recall() against each belief's own title.

Learned while delivering: P1a of the belief-staleness follow-up: derive a belief's staleness from the citation fingerprints IT CAPTURED at drafting time, not by re-deriving live from each cited packet's own current citations every recall. Context: after the 2026-08-22 fix that stopped withholding beliefs for deprecated/superseded citations, 49 of 61 beliefs are STILL withheld -- correctly per the letter of docs/design/BELIEF_MEMORY.md ('a belief that cites moved code goes stale like any packet') but the two-hop check (belief -> cited packet -> that packet's OWN live citations) cascades false-positive staleness from monolithic hot files like mcp/kernel.ts and mcp/delegation/*.ts, which nearly every merge touches somewhere, regardless of whether the specific claim the belief made is still true. Operator decision: snapshot fingerprints at consolidation time. THE FIX: (1) when a belief is drafted or revised (the sleep cycle write path), compute and store a content fingerprint (same fingerprint primitive recallStaleReason/packet fingerprints already use) for each of the belief's own citedPacketPaths AT THAT MOMENT, persisted in the belief's frontmatter or a sibling field -- NOT re-derived from the cited packet's live citations; (2) beliefStaleReason (mcp/kernel.ts) changes to compare each citation's CURRENT fingerprint against the SNAPSHOT stored on the belief, not to recurse into the packet's own citation staleness -- a belief only goes stale when one of ITS OWN cited packets' fingerprint has regressed from what the belief captured, or the packet file is missing outright; a packet's own downstream code-citation staleness no longer cascades up; (3) migration: the 62 existing beliefs (drafted before this field existed) need snapshot fingerprints backfilled from their CURRENT state in one pass (this is the intentional one-time re-baseline the operator is authorizing -- document it plainly in the belief docs' frontmatter, e.g. a snapshot_at date, so it is never confused with a fresh unverified claim); (4) tests: a belief whose cited packet is edited in an UNRELATED region still serves (this is the bug today); a belief whose cited packet is edited in a way that changes recallStaleReason's own fingerprint DOES go stale after the next sleep/revision re-snapshots -- i.e. staleness is now tied to belief revision cadence, not live per-recall re-derivation, and that tradeoff must be stated plainly in BELIEF_MEMORY.md's 'What stays true' section (update the exact line there); (5) verify via the same method the original bug was found and confirmed: run all beliefs against their own titles through recall() and report served/withheld counts in your claim, expect all ~61-62 served (barring any that are genuinely, freshly stale). Suite green; cite files individually.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, reachability
