# Rejected approach: A run that is stopped or orphaned has no way back. Two runs are strande

> A delegated attempt at "A run that is stopped or orphaned has no way back. Two runs are stranded in this repo right n…

A delegated attempt at "A run that is stopped or orphaned has no way back. Two runs are stranded in this repo right now with real, correct work in their worktrees and no command in the product that can recover either.

WHAT I OBSERVED TODAY, using the app. Both cases are live in .agent_memory/runs as you read this.

CASE 1 - STOPPED ON BUDGET, WORK STRANDED. Run make-kage-s-app-usable-on-a-phone-width-260819-b65e reached state "stopped" with the kernel note: "estimated spend $5.22 exceeded the $2.00 budget - raise it with `kage dispatch --budget-usd <n>` for just this run, or set `budgets.usd` in .agent_memory/config.json for every run". Its worktree holds 138 insertions across app-client.ts, app-html.ts and app-styles.ts plus a new mcp/narrow-layout.test.ts - correct work, most of the way done. What the user can do with it: nothing. `kage reverify` refuses, correctly and clearly: "Run ... is stopped - reverify only makes sense from failed or ready". The app offers Abandon, which throws the work away. And the remedy the kernel note itself names, `kage dispatch --budget-usd <n>`, starts a DIFFERENT run from scratch - it cannot resume this one. An error message that names an action which cannot recover the thing it is printed about is worse than no advice.
  Note that mcp/delegation/contract.ts:43 already declares stopped: ["running", "failed", "rejected"]. stopped -> running is a LEGAL transition with no command to make it. This is the same designed-but-unwired shape that produced `kage reverify` for failed -> running; it has now happened again.

CASE 2 - SUPERVISOR DIED, AGENT LIVED ON, INVISIBLE. Run the-predicted-touch-set-is-uncorrelated-260819-ecbd: supervisor_pid 59501 died within seconds of dispatch; agent_pid 59646 stayed ALIVE with PPID 1 (reparented to init), ~400MB RSS, and worked correctly for about 20 minutes - 196 insertions across brief.ts, preflight.ts, verify.ts plus a new mcp/touch-set.test.ts. During all of it: transcript.jsonl had 0 events (the supervisor writes it), supervisor.json was empty, the run sat at "dispatched", and the board showed it as working with "no activity yet - 16m". Its spend was never counted and its budget never enforced, because the thing that counts spend was dead. sweepDeadRuns eventually reaped it as "agent process gone", about 20 minutes after death, despite a 5-minute grace and a per-minute sweep - find out why the delay. I recovered the worktree path by running lsof on the orphan's cwd, because task.json had lost it.

A THIRD DEFECT THAT CAUSED CASE 2's RECOVERY PAIN. `worktree` is declared on the run record at mcp/delegation/contract.ts:83 as string | null, initialised to null at line 444, and then NEVER ASSIGNED AND NEVER READ anywhere in the codebase. Every run in this repo, merged ones included, has worktree: null. Merging works only because other code derives the path by convention from the run id. Decide deliberately: either write it at creation time (my preference - it is exactly what was missing when the supervisor died) or delete the field. A schema field that is always null is a promise the record does not keep. This is the same declared-but-never-reached class the reachability check was built for; note in your claim whether reachability could have caught this shape (a field written nowhere, as opposed to read nowhere) and whether it should.

WHAT TO BUILD:
1. A command that resumes a stopped run, with a new budget. It must reuse the existing resume machinery rather than re-dispatching: same run id, same worktree, same branch, budget raised. Make it reachable from the CLI, the API and the app - a stranded run is exactly when a user is not at a terminal. Then FIX THE KERNEL NOTE to name this command instead of `kage dispatch`.
2. A recovery for the orphan case. A run whose supervisor pid is dead while its agent pid is alive is a distinct, detectable state - not "working", not "lost". Give it its own display state and its own words, and one obvious action. Adopting the worktree so the run can be reverified is achievable today; killing a live agent must be a deliberate user action with the spend shown, never automatic cleanup.
3. Persist the worktree path when it is created, before the agent is spawned. Check the surrounding writes for the same ordering hazard: what the supervisor learns should be durable before the next irreversible step.
4. A per-run supervisor log. There is NO log anywhere today - .agent_memory/daemon/ holds only status.json and a token file - so a supervisor that dies leaves no reason behind. That absence is why case 2 took an hour to understand.
5. Report the budget overshoot honestly. $5.22 against a $2.00 cap is 2.6x. Enforcement works - it stopped the run, which it did not used to do - but the check is evidently coarse. Say what the check interval is and whether it can be tightened without adding per-token overhead. Do not silently change the default budget to hide the overshoot.

DO NOT: make the reaper more aggressive. Reaping case 2 on schedule would have destroyed 196 lines of correct work.

ACCEPTANCE, and this is the bar: after your change, recover BOTH runs named above using only commands the product ships - no hand-edited JSON. Quote the commands and their output in your claim. If a run cannot be recovered, say which and why.

TESTS - new file mcp/run-recovery.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: a stopped run resumes with a raised budget and keeps its id, worktree and branch; a stopped run with no budget raise is refused with a message naming the resume command; a dead-supervisor-plus-live-agent run resolves to the orphan state rather than working or lost; both-dead still reaps as today; the worktree path is durable before the agent spawns (assert the ordering, not the end state). Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS - no import.meta (TS1470), no top-level await. Do NOT touch mcp/delegation/brief.ts, preflight.ts, app-client.ts, app-html.ts or app-styles.ts - stranded runs own those diffs and I intend to land them.
VERIFY: npm run test --prefix mcp and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence." was rejected.
