# kageMetricsShallow (used by refresh/gc/compact for performance — the full kageMetrics()...

> kageMetricsShallow used by refresh/gc/compact for performance — the full kageMetrics with qualityReport is measured a…

kageMetricsShallow (used by refresh/gc/compact for performance — the full kageMetrics() with qualityReport() is measured at 80s+ on this repo) has no `quality` field at all, so memory-view.ts's readMemoryOverview(), which reads metrics.quality.totals.stale for the health strip, silently read 0 forever whenever metrics.json was last written by the Shallow path — a second, independent bug beyond the 'frozen file' one, only surfaced by tracing the read side.

Learned while delivering: The Memory view's health numbers are frozen, and the command that promises to refresh them does not. Found by using the app, not by reading code.

WHAT A USER SEES: the app's Memory tab leads with a health strip — active, stale, avg quality, evidence-backed, used recently, never recalled. Right now it reads "8 stale". The packet store on disk has 92 packets with quality.stale === true, and `kage stale` reports 142 needing a human call. Three surfaces, three numbers, same word. The one the user reads first is the most wrong, and it is wrong by an order of magnitude.

ROOT CAUSE, confirmed by grep: .agent_memory/metrics.json is written in exactly TWO places in mcp/kernel.ts — inside gcProject (around line 9565) and inside compactProject (around line 9730). refreshProject (around line 9432) never writes it. So metrics.json only updates when someone runs `kage gc` or `kage compact`, which are maintenance commands a normal user never runs. On this repo the file is stamped 2026-08-17 while the work happened on 08-18 and 08-19.

THIS IS A BROKEN PROMISE, not just a stale cache: `kage refresh`'s own help line reads "rebuild indexes, graphs and metrics". It exits 0, prints "Refreshed <dir>", reports packets indexed and both graphs rebuilt — and silently does not do the third thing it advertises. I ran it and watched generated_at stay at 2026-08-17.

Note for whoever fixes this: do NOT assume the cause is quiet-refresh. Refresh on a non-default branch prints "Quiet refresh (non-default branch): packet metadata not rewritten on disk" — that behaviour is intentional and must be preserved (it avoids merge conflicts from metadata-only packet rewrites). I initially blamed it and was wrong. metrics.json is not packet metadata and its absence is unrelated: refreshProject simply never writes it on any branch.

WHAT TO BUILD:
1. Have refreshProject write metrics.json, using the same call the other two sites use — buildGraphIndexes then writeJson(join(memoryRoot(projectDir), "metrics.json"), kageMetricsShallow(projectDir, rebuilt)). refreshProject already rebuilds the graphs, so reuse that result rather than rebuilding a second time; check what it already has in hand before adding work.
2. Make sure this still happens on a quiet (non-default-branch) refresh. Metrics are a derived report, not packet metadata — freezing them on a feature branch is exactly the bug being fixed. If there is a reason they must be skipped, say so in your claim rather than silently skipping.
3. While you are there: the health strip's "stale" and `kage stale`'s count should not disagree. Read both definitions and either make them the same number or label them differently in the app so a user is not comparing two things called "stale". State which you chose and why. Do not change what `kage stale` counts — it is the triage surface and its number is the actionable one.

TESTS — new file mcp/metrics-freshness.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: refreshProject writes metrics.json where none existed; it updates an existing stale one (assert generated_at moves); the totals it writes match a live count of the packet store rather than a cached figure; and a quiet refresh still updates metrics while still not rewriting packet metadata. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. mcp/kernel.ts is large — make a surgical change, do not restructure it. Do not touch mcp/delegation/reachability.ts.
VERIFY: npm run test --prefix mcp (754 green before your change — use the "npm run test" form) and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence.
