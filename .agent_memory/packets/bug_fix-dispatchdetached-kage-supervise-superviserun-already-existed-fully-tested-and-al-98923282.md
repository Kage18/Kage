# dispatchDetached()+`kage supervise`+superviseRun already existed, fully tested, and alr...

> dispatchDetached + kage supervise +superviseRun already existed, fully tested, and already record supervisor pid cont…

dispatchDetached()+`kage supervise`+superviseRun already existed, fully tested, and already record supervisor_pid (contract.ts) — the CLI's `kage dispatch` command was the only caller of the full (non-brief-only) dispatch flow that never used it, wiring straight to the inline executeRun() instead. Rerouting the CLI to reuse this existing detached path is far lower-risk than building a second detach mechanism.

Learned while delivering: Make a CLI-dispatched run survive the shell that launched it. Right now it does not, and I destroyed a real run proving it.

REPRODUCED LIVE 2026-08-18: SIGTERM to the "kage dispatch" CLI killed the run it had started. The record was left at state "running" with agent_pid pointing at a dead process, supervisor_pid undefined, and liveState().stale true, so it displayed as "dropped" having done no work. Re-running the identical dispatch under nohup survived normally.

CAUSE: dispatchRun (mcp/delegation/dispatch.ts) executes the run INLINE — the hired agent is a child of the CLI process. supervisor_pid is written in exactly ONE place, mcp/delegation/supervisor.ts, which is the detached kage-supervisor path the daemon and app use. Nothing on the CLI path records an owning process and nothing detaches the agent from its parent. Close the terminal, Ctrl-C, or run under any command timeout, and a run that may be 20 minutes and several dollars in is gone with no way to recover it.

WHY THIS MATTERS BEYOND MY MISTAKE: this repo's own architecture notes state the law — "supervisors stay detached anyway... a daemon restart must never kill a 45-minute agent". That guarantee holds only for the daemon/app path. The CLI verb the docs lead with silently violates it. Both AO and Conductor survive the launching terminal; this is a parity gap, not a nicety.

WHAT TO BUILD — pick ONE of these and justify the choice in your claim:
(a) Detach on the CLI path: spawn the agent detached and unref'd the way supervisor.ts already does, and record supervisor_pid for the owning process so liveState can tell a live run from a dead one. This is the smaller change and it matches the existing law.
(b) Hand the work to the detached kage-supervisor and have the CLI follow its progress, so there is ONE execution path instead of two that drift. This is the better architecture and the bigger change — dispatch.ts's executeRun and supervisor.ts's superviseRun already hand-roll claim assembly separately and have drifted before.
Whichever you choose, the acceptance property is the same and must be tested: after the launching process is gone, the run either continues to completion or is honestly recorded — never left claiming "running" with a dead pid and nobody owning it.

ALSO REQUIRED: whatever remains inline must say so. If any path still ties the run to the caller's process, print one plain line at dispatch time telling the user the run is tied to this shell. Silent fragility is the actual defect here — I lost a run to it without warning.

TESTS — new file mcp/dispatch-durability.test.ts (repo rule: new behaviour gets its own test file; mcp/delegation.test.ts is off-limits). Cover: a CLI-path dispatch records a supervisor_pid (or its chosen equivalent owner) so liveState does not read a healthy run as stale; a run whose owning process is genuinely gone IS reported stale rather than left claiming "running"; and if you keep an inline path, that it warns. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. Do NOT touch mcp/delegation/trackrecord.ts — another run is editing it. Be careful with spawn/detached semantics on macOS; verify by actually killing a parent in a test rather than reasoning about it.
VERIFY: npm run test --prefix mcp (687 green before your change) and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, reachability
