> Goal cards can only ever appear in List work layout: v work.layout board hides work split and therefore .list/ goal c…

Goal cards can only ever appear in List work layout: #v-work.layout-board hides #work-split (and therefore .list/#goal-cards) via CSS entirely, even in the board .dover slide-over which explicitly re-hides .list — so the run-detail goal chip's jump handler must force setWorkLayout('list') before it can scroll the card into view.

Learned while delivering: GOALS O2 — the Goal surface in the app. Backend just merged (read it first): mcp/delegation/goal.ts (GoalRecord: id, intent, state planning|executing|done|abandoned, plan.waves[] of {intent, type, files_scope}, run_ids per wave, autonomy recommend|merge, budgets, state_history), routes GET /goals, GET /goals/:id, POST /goals, POST /goals/:id/abandon, and POST /runs accepts goal_id; the event bridge wakes the held Room manager for goal-owned run changes. FILE CONVENTIONS (the renderer trio app-client.ts/app-html.ts/app-styles.ts are TS template literals): doubled escapes, no backticks, no ${, split()/indexOf over regex, never innerHTML, and the delegation-api.test.ts gates (parse, vocab, CSS-var, orphan-class) run on the composed page. Diff budget 800. BUILD: (1) GOAL CARDS at the top of the Work list: each active goal renders one card above the run sections — goal intent, state chip, per-wave progress (wave n of m, each wave a row of tiny run chips colored by display_state, clicking a chip selects that run in the detail), spend summed from member runs cost labels when present, and an Abandon button (confirm; POST /goals/:id/abandon). Goals in done/abandoned collapse into the Done section as a single quiet row. (2) COMPOSER ENTRY: in the Room composer, a third path — typing a large intent and pressing ⌥⏎ creates a goal via POST /goals {intent} and then SENDS the intent to the manager (existing sendRoomMessage) prefixed with [goal <id>] so the manager, whose constitution has the orchestrator playbook, proposes the decomposition in chat; update the room hint line to mention ⌥⏎ orchestrate as a goal; add Orchestrate as a goal to the ⌘K palette. (3) DETAIL LINKBACK: expose the run.goal_id on the run detail/list responses in api.ts if not already present (check first); a run belonging to a goal shows a small goal chip in its detail head; clicking it scrolls the goal card into view with a brief highlight. (4) refresh() also fetches /goals alongside /runs — one extra GET, no new event type. TESTS: api test for the goal round-trip through whatever app-facing shapes you rely on; all gates green.
