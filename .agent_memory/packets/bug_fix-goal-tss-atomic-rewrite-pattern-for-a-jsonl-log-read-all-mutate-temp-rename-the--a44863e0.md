> goal.ts's atomic rewrite pattern for a JSONL log read all, mutate, temp+rename the whole file mirrors dispatch.ts's s…

goal.ts's atomic-rewrite pattern for a JSONL log (read-all, mutate, temp+rename the whole file) mirrors dispatch.ts's steer log exactly (writeSteerRecords/readSteerRecords) and was reused verbatim for the new events.jsonl log under each goal's directory — no new fs imports were needed since goal.ts already imported everything required.

Learned while delivering: Make goal events DURABLE so the orchestrator wake-loop cannot drop the events that matter. Observed live and verified: notifyManagerOfRunEvent in mcp/delegation/room-supervisor.ts delivers through askRoomSupervisor op:ask, which requires busy===false, and a busy manager is treated as an accepted drop — so during a real orchestration ZERO [kage event] frames ever reached the manager (no such turns in .agent_memory/room/history.json). A wave changes state immediately after the very turn that dispatched it, while the manager is still busy, so the events that matter most are exactly the ones discarded. FIX: (1) PENDING LOG — in mcp/delegation/goal.ts add a per-goal pending-events log (JSONL under the goal dir) with appendGoalEvent, readPendingGoalEvents, markGoalEventsDelivered, using the same atomic temp+rename rewrite the steer log uses. notifyManagerOfRunEvent must ALWAYS append first, then attempt immediate delivery; success marks those events delivered, a busy or dead manager simply leaves them pending — never a silent drop. (2) DRAIN ON IDLE — in room-supervisor.ts, at the point where a turn completes and the session goes idle, drain pending events for goals whose active session is this thread (room-sessions.ts now stores the active goal per thread — use it): coalesce into ONE compact frame (group by run, keep only the latest state per run, cap the list and state how many were coalesced), deliver it as the next user frame into the held session, then mark delivered. Keep the existing rate limit so a storm cannot flood the manager, and keep the rule that only goal-owned runs generate events — never wake the manager for a human-only run. TESTS in mcp/delegation.test.ts, in a clearly separated block at the END of the file (this file has had append-collision conflicts): an event fired while the manager is busy is PENDING not lost; going idle drains it as exactly one coalesced frame and marks the events delivered; two state changes for the same run coalesce to the latest; a run with no goal produces no event and no frame; a dead manager leaves events pending for the next live one. Use the existing room-supervisor seams so no real process is spawned. Success = npm test fully green.
