# mcp/delegation/app-client.ts's whole body is one TS template literal, and single-backsl...

> mcp/delegation/app client.ts's whole body is one TS template literal, and single backslash regex escapes written in t…

mcp/delegation/app-client.ts's whole body is one TS template literal, and single-backslash regex escapes written in that source (e.g. \d or \$) get their backslash silently dropped by the template-literal parser at COMPILE time, before the string ever reaches the browser — the browser's own regex engine then sees the wrong pattern (digits become literal 'd', \$ becomes an unescaped end-anchor). Any new regex added to app-client.ts needs every backslash doubled (\\d, \\$), not just \n-style escapes — this bit two of my new functions (parseCapFromStopNote) before the existing 'escapes are doubled' comment's scope became clear to me.

Learned while delivering: Every dead end in the app gets a next step. Six findings from the owner reviewing the live app with screenshots today - all six are real, and two zombie run records sitting in .agent_memory/runs right now are your test fixtures.

THE FINDINGS:
1. GOAL CARDS ARE UN-VIEWABLE. The goal card (title, state chip, autonomy chip, wave dots, spend, Abandon) is the ENTIRE goal surface - clicking it does nothing, the wave dots are unlabeled, 'recommend' is unexplained, the title truncates with no way to read it. Build a goal detail view: click a goal card opens it - full intent, autonomy explained in words, each wave with its runs (name, state, verdict chip) linking to the run detail, spend, and the Abandon action moved there with the existing confirm. Reachable from the board and Room. Keep it read-and-navigate; no new mutations beyond the relocated Abandon.
2. A STOPPED RUN OFFERS NO NEXT STEP. Run a-run-that-is-stopped-or-orphaned-has-no-260819-4e38 (stopped, 17h, work already merged by hand) shows Take Over and Reject only. Build the RESUME button on stopped runs: calls POST /runs/:id/resume-run; when the stop note names a cap, prefill the raise for that cap (the notes are now machine-recognizable from today's budget run - parse which cap tripped from the note the kernel writes; if unparseable, plain Resume with no prefill). On refusal, show the API's message verbatim.
3. ZOMBIE RECORDS: A RUN WHOSE BRANCH ALREADY LANDED. That same run's branch IS merged into release-prep (landed manually under the bootstrap exception), but the record sits stopped forever - the app never learns. Backend addition (mcp/delegation/api.ts and/or contract.ts - you own them this run): when serving a stopped/failed run, detect whether its branch is an ancestor of the current branch (git merge-base --is-ancestor; cheap, cache per serve) and expose branch_landed: true. UI: show 'this run's work is already on the branch' with one action - Close as landed - implemented as the existing reject transition with the note 'closed: work already landed on <branch>' so the vocabulary stays honest (rejected = record closed without kage merge; the note says why). Do NOT invent a new state.
4. AN ORPHAN-SHAPED FAILED RUN OFFERS NO CURE. Run write-the-release-notes-for-the-next-ver-260818-cb42 (failed 'agent process gone', worktree holds CHANGELOG.md +112) is exactly what kage adopt recovers - but the app has no Adopt button. Build it: on a failed run whose note is agent-process-gone-shaped AND whose worktree still exists with changes (expose worktree_adoptable from the API using the existing recovery.ts detection), show ADOPT - 'verify the work it left behind' - calling the adopt route (add POST /runs/:id/adopt to api.ts mirroring the CLI path if missing). On success the run lands ready and the receipt appears - the full cure, in one click.
5. EMPTY STATES MUST TEACH. Receipt tab on a claimless run: instead of blankness, one sentence - 'No claim exists - the run stopped before reporting. Resume it to continue, or Reject to close.' (with the buttons that apply). Queue tab when empty: 'Messages you queue with cmd-enter wait here and deliver at the agent's next pause.' Follow the existing emptyBlock() teaching-empty-state pattern already in app-client.ts - do not invent a second pattern.
6. EVERY TERMINAL-OR-STUCK STATE GETS A WHAT-NOW LINE. Under the state chip on run detail: stopped -> 'stopped by the kernel: <note>. Resume, take over, or reject.'; failed with claim -> 'verification failed: <failing check>. Steer a fix, or reject.'; failed orphan-shaped -> the Adopt line; ready -> 'verified - review the receipt and merge.' One derivation function, driven by the same fields the API already serves; no invented text beyond these shapes.
