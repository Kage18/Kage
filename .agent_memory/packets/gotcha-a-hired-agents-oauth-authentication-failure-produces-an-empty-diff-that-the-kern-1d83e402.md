# A hired agent's OAuth authentication failure produces an empty diff that the kernel marks 'ready', not 'failed' — checks pass trivially against an unchanged tree

> Two consecutive dispatches on 2026 08 29 failed identically: the spawned agent's own transcript showed "Failed to aut…

Two consecutive dispatches on 2026-08-29 failed identically: the spawned agent's own transcript showed "Failed to authenticate: OAuth session expired and could not be..." within 2 seconds of spawn, exit code 1, zero tool calls, $0 spend — yet the kernel proceeded to "verifying" and then marked the run "ready" with a skeleton claim ("work delivered — see diff (agent skipped the kage-claim-v1 fence)"). This happens because checks (tests, diff-size, citations) trivially pass against a completely unchanged worktree — there is nothing to fail. A run whose agent turn ended via an auth/exit-1 failure before any tool use should be classified 'failed' outright, not run through the normal verify-and-maybe-ready path; today the only signal distinguishing this from genuine no-op-but-legitimate work is manually reading transcript.jsonl for a 'say' event containing 'Failed to authenticate' plus zero spend. Diagnostic shortcut: an empty diff (worktree tip == base, no uncommitted changes) combined with protocol_ok:false and $0/0min spend is the fingerprint — check transcript.jsonl directly before redispatching blindly, since redispatching against a session-wide auth outage just reproduces the same failure.
Evidence: two runs (restore-the-viewer-link-to-the-homepage-260829-7cb2 and -8a5c) both show transcript.jsonl containing a 'say' event with label starting 'Failed to authenticate: OAuth session expired', exit_code 1, task.json spend {usd_est:0, minutes:0}, and final state 'ready' with an empty git diff against release-prep
Verified by: direct transcript.jsonl and supervisor.log inspection on 2026-08-29; confirmed identical on the second attempt, ruling out one-off flakiness
