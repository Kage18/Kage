# room-supervisor.ts's superviseRoom() substitutes EMPTY_MANAGER_REPLY_TEXT for an empty ...

> room supervisor.ts's superviseRoom substitutes EMPTY MANAGER REPLY TEXT for an empty manager reply BEFORE emitting th…

room-supervisor.ts's superviseRoom() substitutes EMPTY_MANAGER_REPLY_TEXT for an empty manager reply BEFORE emitting the 'final' RoomStreamEvent over the control socket, so api.ts's resolveRoomReply can never detect emptiness by checking `live.text` truthiness — it is never actually falsy. The fix is to compute the true emptiness signal (Boolean(rawText.trim())) inside room-supervisor.ts before the substitution and carry it as a new `ok?: boolean` field on the 'final' event, which is what makes an empty-reply retry possible on that leg at all.

Learned while delivering: Make the Room chat interactable — the owner: users currently type everything; the manager must offer clickable cards and options. Build the structured-reply layer end to end: (1) PROTOCOL — the manager may end any reply with one fenced block labelled kage-actions containing JSON: either {question, options:[{label, send}]} (2-4 options; send is the message a click submits) or {proposals:[{intent, type}]} (runs to dispatch) or {actions:[{label, kind: open_run|dispatch|create_goal, payload}]}. Parse it in the reply pipeline (BOTH legs — the room-supervisor leg in room-supervisor.ts/api.ts AND the askManager leg), strip the fence from the visible text, and persist it as an actions field on the room turn (extend the turn schema additively — old turns without actions render unchanged). (2) WHILE IN THAT PIPELINE, unify the empty-reply retry: the previous run added retry-once+enriched-failure to the askManager leg only and honestly flagged that the room-supervisor leg has its own empty fallback with no DI seam — add the seam and apply the SAME retry-once + enriched-failure there, with a test through the new seam. (3) CLIENT (app-client.ts/app-styles.ts) — render turn.actions in the thread column: question options as clickable chips (click sends option.send as a normal room message via the existing composer path and disables the chip row for that turn afterward); proposals as compact cards with the intent text and a Dispatch button wired to the existing dispatch API; open_run actions as run chips that open the existing run detail; every control uses existing token-guarded APIs and existing action functions, h() only, never innerHTML, revision-gated like the rest. Style per the app design language (chip/atom vocabulary — see docs/design/mockups/Main.dc.html for the chip treatments). (4) MANAGER PROMPT — extend the constitution: whenever the manager asks a clarifying question it MUST provide the kage-actions options block (2-4 concrete choices); whenever it proposes work it SHOULD attach proposals so the user can click Dispatch; typing always remains possible. (5) TESTS — protocol parse (valid block extracted+stripped, malformed block ignored gracefully and left visible as text so nothing is silently lost), retry-once on the supervisor leg via the new seam, turn schema round-trip, and composed-page string assertions that a turn with actions renders the chips/buttons and one without renders exactly as before. Template-literal constraints as always; parse test and full suite green; cite files individually.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, node --check <composed inline script>, reachability
