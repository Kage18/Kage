# A ctx object passed into handleDelegationRoute is not guaranteed to be the SAME object ...

> A ctx object passed into handleDelegationRoute is not guaranteed to be the SAME object across requests — the producti…

A ctx object passed into handleDelegationRoute is not guaranteed to be the SAME object across requests — the production daemon happens to reuse one long-lived object, but nothing in the function's contract requires that, and the test harness's per-request object literal is equally valid. Any state that must outlive a single request (as opposed to state.room/state.pty, which work today only because startApi's closure captures one shared room/pty object by reference across all per-request ctx literals) belongs at module scope in api.ts, not as a lazily-created field on ctx.

Learned while delivering: WAVE 3 — the interaction surface: wire the merged AO+Conductor parity backends into the app. Backends already in the tree: steer records with queued/delivered status + queue mutations (steer.ts, dispatch.ts readSteerRecords) exposed at GET /runs/:id/steers and POST /runs/:id/steers {op: edit|delete|reorder}; POST /runs/:id/interrupt (true interrupt, honest 503); the kage-plan fence (blocked runs carry waiting_on.needs = plan approval with the plan text in waiting_on.detail); and mcp/delegation/run-pty.ts exporting takeOverRun/handBack/takeOverState/write/resize/snapshot with a pty factory seam (NO api wiring yet — that is yours). FILE CONVENTIONS FIRST: app-client.ts / app-html.ts / app-styles.ts are TS template literals — doubled escapes, no backticks, no ${, prefer split()/indexOf over regex, never innerHTML (a gate enforces it), and delegation-api.test.ts gates run on the composed page (parse, vocab, CSS-var, orphan-class). Diff budget is 800. BUILD, in one coherent pass: (1) QUEUE PANEL in the run detail (a Queue tab or a section under the steer composer): list steer records — delivered ones as immutable history with timestamps, queued ones editable in place, deletable, and reorderable (up/down buttons are fine; no drag dependency) via the steers API; refresh after each op; errors via showError. (2) DELIVERY CHOICE on the detail steer composer: default ⏎ = steer now (existing tell route); a visible toggle plus modifier ⌘⏎ = queue for later WITHOUT delivery — add op:add to POST /runs/:id/steers in api.ts mapping to appendSteerRecord for that (pure queue append, no delivery attempt). Immediate stays the default (Conductor shipped queue-by-default and reverted). (3) INTERRUPT button beside Stop for running/dispatched/verifying runs → POST /runs/:id/interrupt; on 503 showError; label it honestly (Interrupt — session stays alive). (4) PLAN CARD: when a blocked run has waiting_on.needs === plan approval, render a distinct plan-review card in the Follow pane and the work row: the plan text styled as a document (mono, bordered), an Approve button that tells the run approved — proceed as planned, and the normal answer field for revisions; Enter on the focused Approve button approves. (5) TAKE OVER: wire run-pty into api.ts — POST /runs/:id/takeover, POST /runs/:id/handback, plus pty write/resize/snapshot routes for the run, streaming output over the existing SSE pty channel with session key run:<runId> so room terminals and run terminals never cross (feed.notifyPty already carries a session field); in the app, a Take Over button on eligible runs opens a Terminal pane inside the run detail reusing the existing xterm machinery (same vendored assets, same repaint ladder patterns documented in the client), with a Hand Back button that calls handback and returns to the normal detail; state chips must reflect the kernel truth throughout. Add or extend tests: api tests for op:add, the takeover/handback routes with the pty factory seam (never a real claude), and keep every existing gate green. Success = npm test fully green.
Verified by: npm test --prefix mcp, diff-size
