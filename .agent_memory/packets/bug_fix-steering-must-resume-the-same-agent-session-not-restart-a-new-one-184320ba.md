# Steering must resume the same agent session, not restart a new one

> Answering a blocked agent must continue its own session; the first version only appended the message to a steer file …

Answering a blocked agent must continue its own session; the first version only appended the message to a steer file and told the user to run retry, which compiles a fresh brief and hires a NEW agent, discarding everything the blocked one had figured out. That is starting over while calling it steering. Three changes make it real. First, the session handle is pre-assigned at dispatch with the session-id flag and stored on the run, because the handle must be known BEFORE the process starts or the context dies with it; steerRun in mcp/delegation/steer.ts then relaunches with the resume flag and the answer as the prompt. Proven live: an agent blocked asking what to rename a helper to, the answer arrived through kage tell, and the same session resumed and completed the rename. Second, blocked is detected from two independent signals: the claim protocol fence AND the stream post_turn_summary event whose status_category is blocked, which also fires when an agent asks in plain prose where no fence exists. Third, a process that is gone can never be reported as running: the child pid is stored and liveState cross-checks it, so a dead run surfaces as dropped with its last activity instead of claiming to run for hours. Delivery is always reported honestly as resumed, queued or refused, because accepted is not delivered and a surface that conflates them teaches users to distrust it. A run predating session recording is refused with an explanation rather than a silent no-op.
Verified by: npm test --prefix mcp: 438 unit + 12 dogfood pass; live proof — a real claude agent blocked asking for a name, kage tell answered it, the SAME session resumed and renamed retry to withRetry with its context intact
