# Market signal: people refuse to commit AI memory into the code repo — collaborative memory must move out of .agent_memory-in-repo

> Owner reported adoption friction 2026 08 18 : "people are not willing to commit the memory to the same code repo." Th…

Owner-reported adoption friction (2026-08-18): "people are not willing to commit the memory to the same code repo." The in-repo .agent_memory design — the current foundation — creates concrete resistance: every PR carries packet diffs (review noise, merge conflicts on generated files), kage ratify/chore commits interleave with real history, compliance and security reviewers object to AI-authored files in the source of truth, public repos leak internal reasoning, and monorepos make memory ownership unclear. What in-repo bought us and any replacement must preserve: memory versioned against the code it describes (grounding), merge-ratification as the review boundary, clone-equals-onboarding team sharing, zero server infrastructure, OKF portability. The design fork: (A) external git-backed team memory store — memory lives in its own repo (default local at ~/.kage, linkable to a team-controlled remote), zero or one-line footprint in the code repo, packets stamped with the code SHA they were verified against, ratification commits reference code merges; preserves git-native and OSS-adoption-first with no server. (B) hosted memory service — accounts, sync, conflict resolution; bigger product bet, monetizable, but infrastructure to run and a tension with the no-lock-in promise. (C) staged: A now as the open protocol, hosted sync later as managed hosting of the same format. Decision pending with the owner.
Evidence: Owner statement in session; consistent with the OKF-era no-lock-in positioning and the v-next OSS-adoption-first lock recorded in project memory.
Verified by: Owner report, 2026-08-18.
