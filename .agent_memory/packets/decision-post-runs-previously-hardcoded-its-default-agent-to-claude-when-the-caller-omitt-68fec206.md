# POST /runs previously hardcoded its default agent to "claude" when the caller omitted `...

> POST /runs previously hardcoded its default agent to "claude" when the caller omitted agent — there was no per projec…

POST /runs previously hardcoded its default agent to "claude" when the caller omitted `agent` — there was no per-project default at all; DelegationConfig.default_agent (new field this run) plus reading it in that route is the first place a project's preferred worker agent is actually persisted and honored.

Learned while delivering: Make adding a project seamless, in the app. Today it needs a terminal; AO does it in four clicks and lands you in a live session.

WHAT AO'S SETUP ACTUALLY IS — walked through it today, start to finish:
1. Click "+" beside Projects.
2. A dialog: "Import to Agent Orchestrator — What are you importing?" offering two ILLUSTRATED choices — Workspace ("Several Git repos that live under one parent folder", drawn as a parent folder containing three repos) and Project ("A single Git repository - tracked in a single codebase", drawn as one repo on a branch).
3. A native macOS folder picker.
4. A "Project agents" dialog showing the chosen path, with two pickers — Worker agent and Orchestrator agent — plus "Agent availability is cached / Refresh agents", an "Enable issue intake" checkbox, and one button: "Create and start".
5. That button drops you straight into a live orchestrator session, ready to type. No terminal, no config file, no docs.
Total: four clicks from nothing to a working orchestrator.

WHAT KAGE'S IS: `kage install` in a terminal, or `kage app` and then the project must already be wired. mcp/delegation/app-client.ts has a "+" beside Projects in the sidebar — find what it currently does and say so in your claim; whatever it is, it is not the flow above.

WHAT TO BUILD — the same four steps, in Kage's own visual language (read mcp/delegation/app-styles.ts and match it; do not import AO's look):
1. "+" opens an add-project dialog. Kage has no workspace concept, so do NOT invent one in this run — offer picking a repo folder, and if the chosen folder contains multiple git repos, say so plainly and let the user pick which one rather than silently choosing.
2. Choosing the folder must work from the app. The daemon is a local HTTP server and the renderer is a browser page, so a native folder picker is not directly available — solve it honestly: a path input with validation that says exactly what is wrong ("not a git repository", "no commits yet", "path does not exist") is acceptable and better than a broken picker. If the Electron shell (shell/main.js) can supply a real native dialog over its existing bridge, prefer that and use it; check before assuming.
3. Then an agent step: which agent runs the work, and which runs the orchestrator. Kage already has adapters for claude and codex — offer what actually exists and do not list agents Kage cannot run.
4. One button that creates the project AND opens its Room, live, ready to type. The whole point is that the last click leaves the user somewhere useful, not back at an empty board.
5. Everything the flow does must be reachable from the CLI too, so the app is not the only door. If `kage install` already covers it, say so; if the app path does something the CLI cannot, add the flag.

HONESTY REQUIREMENTS, these matter more than the polish:
- Never silently succeed on a folder that is not usable. Kage already has resolveWorkspaceKind (mcp/delegation/worktree.ts) which throws rather than quietly sandboxing when .git exists but git is unhappy — use it and surface its reason.
- When something fails, say what is wrong and what to do, in one line. Do not surface raw git output: AO fails at exactly this — adding a project whose folder had been deleted produced "invalid branch name ... exit status 128: fatal: cannot change to ... No such file or directory (INVALID_BRANCH)", leading with a symptom and burying the cause four clauses deep. That is the bar to beat, and it is low.
- If indexing a large repo takes time, show that it is working. Do not present a frozen dialog.

TESTS — new file mcp/add-project.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: adding a valid git repo registers it and returns the id the app needs to open its Room; a non-git path is refused with a message naming the reason; a path that does not exist is refused with a different, correct message; a repo with no commits is handled per resolveWorkspaceKind's existing rule rather than crashing; and the composed page still parses (the existing renderer gates must stay green). Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. app-client.ts and app-styles.ts are TS TEMPLATE LITERALS: client-side escapes must be DOUBLED, no backticks, no ${ }, never innerHTML. Do not touch mcp/delegation/room-pty.ts or mcp/delegation/room-supervisor.ts — another run is editing those.
VERIFY: npm run test --prefix mcp (767 green before your change — use the "npm run test" form) and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence.
