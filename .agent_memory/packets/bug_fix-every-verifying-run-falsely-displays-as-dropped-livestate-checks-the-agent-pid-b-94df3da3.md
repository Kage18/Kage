# Every verifying run falsely displays as dropped: liveState checks the agent pid, but the agent is gone during verification by design

> Confirmed live 2026 08 18 : a run in state verifying shows display state dropped while its supervisor is demonstrably…

Confirmed live (2026-08-18): a run in state verifying shows display_state dropped while its supervisor is demonstrably alive and running the checks. Mechanism: verification happens AFTER the hired agent exits — the supervisor runs verifyRun itself — but task.agent_pid tracks the AGENT, so during the whole verification window (npm test + build, ~90s here, longer under load) isProcessAlive(agent_pid) is false and liveState marks the run stale. Two consequences, one cosmetic and one dangerous: surfaces show a healthy run as dropped, and sweepDeadRuns reaps dropped runs after a 5-minute grace, so a slow-but-healthy verification can be killed by the reaper. Evidence: run mcp-delegation-verify-ts-citedpaths-trea-260818-2d31 displayed dropped while pgrep showed its supervisor (cli.js supervise <runId>) alive and working. Operator consequence worth remembering: I rejected an earlier run partly on this false signal, so the bug also costs real work. Fix direction: record the SUPERVISOR's pid on the task (supervisor_pid) alongside agent_pid and have liveState treat verifying as in-flight when the supervisor is alive; only when neither the agent nor the supervisor exists is a verifying run genuinely stale. Same family as the day's other honesty bugs — a check that conflates "the thing I happened to track is gone" with "the work is dead".
Evidence: pgrep showed pid 66032 running cli.js supervise mcp-delegation-verify-ts-citedpaths-trea-260818-2d31 while the API reported display_state dropped and task.json had agent_pid null with state verifying.
