# mcp/delegation/guard.ts's GuardContext is a plain interface (not touched by any off-lim...

> mcp/delegation/guard.ts's GuardContext is a plain interface not touched by any off limits file , so extending it with…

mcp/delegation/guard.ts's GuardContext is a plain interface (not touched by any off-limits file), so extending it with optional lanHosts/lanToken fields is safe and doesn't collide with mcp/delegation/api.ts, which imports guardRequest but never constructs GuardContext itself.

Learned while delivering: Let a phone reach Kage over the LAN, the way AO does — without opening a hole.

WHY: this is the biggest capability AO has that Kage does not, and Kage is unusually close to it. AO's Settings has "Connect Mobile — Pair the Agent Orchestrator mobile app with this desktop over your LAN", with an "Enable mobile" toggle described as "Open a password-protected port on your local network so your phone can connect", plus iOS TestFlight and an Android waitlist. No cloud, no account. Kage's daemon already runs an authenticated HTTP server; today it just refuses to be reachable from anything but this machine.

WHAT EXISTS — read these before touching anything:
- mcp/daemon.ts binds DEFAULT_HOST = "127.0.0.1" (around line 118) and calls server.listen(port, host, ...) (around line 981).
- The daemon already has real security from earlier hardening: a mutation token read from a 0600 status file required on every mutating route, an Origin check that rejects foreign origins, and a Host check that rejects non-127.0.0.1 hosts specifically to defeat DNS rebinding. Find all three and understand them before changing any of them. There are existing tests asserting each; they must keep passing in spirit, adapted only where LAN mode genuinely requires it.

THE SECURITY BAR — this is the part that matters more than the feature:
- Loopback stays the DEFAULT. LAN exposure must be explicit, off unless the user turns it on, and never a side effect of some other setting.
- The Host guard exists to stop DNS rebinding. Relaxing it to "any host" would reintroduce exactly that attack. When LAN mode is on, accept the machine's own LAN addresses and reject everything else — do not simply delete the check. State in your claim precisely which hosts you allow and why that set is safe.
- LAN mode must require a SHARED SECRET that is not the existing loopback token. A token sitting in a 0600 file is fine when only local processes can read it; it is not a pairing credential. Generate a pairing secret, require it on every request in LAN mode including reads, and show it to the user so they can enter or scan it. Never log it.
- The Origin check must stay meaningful in LAN mode. Say what you did with it.
- If you cannot make some part of this safe, say so in your claim and leave it off rather than shipping it permissive. An honest "not done, here is why" is a good outcome; a quiet hole is not.

WHAT TO BUILD:
1. A config flag and a CLI flag that enable LAN mode, off by default. Follow the existing DelegationConfig pattern (mcp/delegation/config.ts) for the persisted setting.
2. When enabled, bind to the LAN interface as well as loopback, generate/persist a pairing secret, and require it. When disabled, behave exactly as today — verify that with a test, because "we didn't change the default path" is the claim most worth proving.
3. Print, on enable, exactly what a user needs: the URL a phone should hit and the pairing secret, plus one plain line saying this opens a port on their local network. No jargon.
4. Do NOT build a mobile client, a QR code, or any pairing UI in this run. The deliverable is the secure, reachable, credentialed endpoint. Say in your claim what a client would need to do to connect.

TESTS — new file mcp/lan-mode.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: default is loopback-only and unchanged; with LAN mode on, a request carrying the pairing secret succeeds and one without it is refused; a request with a foreign Host is still refused in both modes; the loopback token path still works; and the secret never appears in any log line the daemon writes. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. Do NOT touch mcp/cli.ts, mcp/delegation/api.ts, mcp/delegation/app-client.ts, mcp/delegation/app-html.ts, mcp/delegation/app-styles.ts or mcp/delegation/config.ts's existing fields beyond adding your flag — another run is editing all of those right now. If your change genuinely requires editing one of them, stop and say so in your claim instead of colliding.
