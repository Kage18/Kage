# kage_context (the MCP tool) can serve a stale in-memory kernel.js even after dist/ is rebuilt and the app daemon restarted — only a full agent-session restart reloads it

> After merging and rebuilding a kernel.ts fix the belief staleness snapshot fix, 2026 08 27 , calling kage context via…

After merging and rebuilding a kernel.ts fix (the belief-staleness snapshot fix, 2026-08-27), calling kage_context via the MCP tool still returned belief-withheld reasons in the OLD pre-fix message format ("cited packet X is stale: <reason>"), even though `mcp/dist/kernel.js` on disk was freshly built and independently confirmed correct (60/60 beliefs served via `node -e` against the same file, in a fresh process). Root cause: kage_context is served by a separate long-running MCP server process for this session, distinct from the `kage app` HTTP daemon on port 3111 — restarting the daemon (`kill <pid>; kage app`) does NOT reload the MCP server's in-memory copy of kernel.js. Only restarting the agent session does. When kage_context's output looks stale (old code paths, old message formats, a fix that "isn't taking"), verify the actual shipped code directly first via `node -e "require('./dist/kernel.js')..."` before suspecting the fix itself — if that confirms correct behavior, the mismatch is process staleness, not a regression, and the fix is safe to report as done.
Evidence: kage_context via MCP tool showed old-format staleness reasons post-fix-merge; direct node -e require of the same dist/kernel.js (fresh process, no daemon, no MCP server) showed 60/60 beliefs served, 0 withheld — proving the shipped code was correct and the MCP layer was serving cached code
Verified by: side-by-side comparison on 2026-08-27: MCP tool call vs direct node -e against the same committed dist/kernel.js
