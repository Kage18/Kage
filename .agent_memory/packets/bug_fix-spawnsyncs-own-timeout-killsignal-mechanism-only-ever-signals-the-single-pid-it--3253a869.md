# spawnSync's own `timeout`+`killSignal` mechanism only ever signals the single pid it is...

> spawnSync's own timeout + killSignal mechanism only ever signals the single pid it is tracking confirmed: result.erro…

spawnSync's own `timeout`+`killSignal` mechanism only ever signals the single pid it is tracking (confirmed: `result.error.code === 'ETIMEDOUT'` on timeout) — it does not know about, and cannot reach, any descendants that pid spawned, even when `detached: true` makes a group-wide kill via `process.kill(-pid, signal)` possible afterward. A real group sweep has to be done by hand, after spawnSync returns.

Learned while delivering: A timed-out check leaves its process tree alive, and the zombies poison every later verification on the machine. Observed over the last 12 hours, autopsied live: a run's `npm run test` check hit the command timeout; the check-runner killed its direct child but npm's TREE (npm -> node --test -> per-file worker processes) survived. THREE such zombie suites accumulated across retry cycles - found still alive this morning via ps, each with a live worker child - and every subsequent verification on the machine ran beside them and hung the same way (238 tests then stall). After killing all of them, the exact same test files passed clean in seconds. The timeout was reporting real hangs - caused by its own previous kills.

THE FIX, in mcp/delegation/verify.ts's command runner (and mcp/delegation/static-checks.ts's runCommand if it shares the hazard - check it): spawn command checks in their OWN PROCESS GROUP (detached: true on the spawn options) and on timeout kill the GROUP (process.kill(-child.pid, 'SIGKILL') after an initial SIGTERM grace of a few seconds - state your grace). The evidence file should record that a tree kill happened ('timeout after Ns - process tree killed'). Never orphan a grandchild again.

Also audit: any other place the harness kills a child on a deadline (the supervisor's agent-child handling in mcp/delegation/supervisor.ts already manages its child deliberately - do NOT change its semantics; only confirm whether ITS timeout paths can orphan grandchildren and note what you find in your claim).

TESTS - new file mcp/tree-kill.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: a check command that spawns a grandchild which ignores SIGTERM and sleeps forever - on timeout, BOTH the child and the grandchild are dead within the grace (poll process liveness by pid, no fixed sleeps beyond the grace); the evidence file names the tree kill; a fast-exiting command is unaffected. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS - no import.meta, no top-level await. Your files: mcp/delegation/verify.ts, mcp/delegation/static-checks.ts, and your new test file. Do NOT touch mcp/delegation/goal.ts, api.ts, manager-prompt.ts, room-pty.ts, room-supervisor.ts (another run owns them), supervisor.ts beyond the read-only audit note. Build and test ONLY inside your own worktree - never run npm, tsc or node against /Users/kushaljain/code/Kage. Rebase onto release-prep first if your base carries an inherited red. End with the kage-claim-v1 fence, citing files individually.
VERIFY: npm run test --prefix mcp (1060 unit + 12 dogfood green on main) and npm run build --prefix mcp with no 'error TS'. Run them for real and fill in the claim fence.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, reachability
