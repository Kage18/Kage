# reverify's diff-size check reads the working tree, so a claim-time commit makes it pass vacuously at 0 lines

> The diff size check, when re run by kage reverify , measures the run worktree's UNCOMMITTED changes. Runs commit thei…

The diff-size check, when re-run by `kage reverify`, measures the run worktree's UNCOMMITTED changes. Runs commit their work at claim time (commitWorktree), so by reverify time the working tree is clean and the check records "0 file(s), 0 changed line(s), budget N" and passes no matter how large the real change is. Observed live: a run whose actual source diff was ~1,400 lines (self-reported in its own claim's unsure notes) reverified with diff-size evidence reading "0 file(s), 0 changed line(s), budget 800" — a vacuous pass in the reassuring direction, which is the exact failure class Kage exists to prevent. The original at-claim verification is not affected (the diff existed uncommitted then, and adopt-time checks on orphans are also correct for the same reason — orphaned worktrees hold uncommitted work). The fix direction: the diff check must measure merge-base..HEAD PLUS the working tree, not the working tree alone, so a committed diff still counts. Until fixed, treat a reverify diff-size pass on a committed worktree as unmeasured, not as within-budget.
Evidence: .agent_memory/runs/budgets-become-a-circuit-breaker-not-a-t-260820-e70a/evidence/diff-size.log reads "0 file(s), 0 changed line(s), budget 800" from the reverify that flipped the run to ready; the run's claim.json unsure[] states "Diff is ~1400 changed lines across 12 modified files + 2 new test files, well over the 800-line guideline"; the merged commit shows 38 files / 4,756 insertions including ratified memory.
Verified by: Direct read of the run's evidence log vs its own claim and the merged commit stat, 2026-08-20
