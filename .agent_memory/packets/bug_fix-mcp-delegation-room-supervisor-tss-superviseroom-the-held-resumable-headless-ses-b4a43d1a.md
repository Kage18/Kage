# mcp/delegation/room-supervisor.ts's superviseRoom (the held, resumable headless session...

> mcp/delegation/room supervisor.ts's superviseRoom the held, resumable headless session dispatchRoomSupervisor/askRoom…

mcp/delegation/room-supervisor.ts's superviseRoom (the held, resumable headless session dispatchRoomSupervisor/askRoomSupervisor talk to) is the PRIMARY production path for a browser Room chat message when claude is installed — mcp/delegation/manager-client.ts's askManager (one-shot `claude -p`) is only reached as the fallback of that fallback, per resolveRoomReply's own comment in api.ts. Both independently substitute the same '(the manager returned nothing)' honesty sentinel on empty text, which is why that exact string is what an owner sees in production even though tests exercising 'headless' behavior via ctx.askManagerFn (the only DI seam available) only ever reach the askManager leg.

Learned while delivering: The Room manager can end a turn with EMPTY text for a legitimate request — owner reproduced it live: asked 'can you use kage app from the browser and see how we can improve it', the headless manager returned nothing, and the (correct, recently-shipped) honesty rendering showed '(the manager returned nothing)'. The honesty layer worked; the manager behavior is the bug. Fix three layers: (1) MANAGER PROMPT (mcp/delegation/manager-prompt.ts): add an explicit standing rule — a turn must NEVER end with empty text; when the user asks for something outside the manager's tool surface (browsing, editing files, using a UI), the manager answers with what it CAN do and does it: propose and dispatch a run (it has the dispatch tools) capturing the user's intent, or ask exactly one clarifying question — declining silently or returning nothing is forbidden; (2) PIPELINE RETRY (the askManager/headless leg in mcp/delegation/api.ts + manager-client.ts): when a manager turn resolves with empty text, retry ONCE with an appended nudge instructing it to answer plainly in one sentence minimum; only if the retry is also empty, persist the visible failure turn — and enrich that failure text with whatever detail exists (exit code, stderr snippet, or 'returned empty twice') so the user sees why, not just that; (3) TESTS: a test that an empty first manager reply triggers exactly one retry and a non-empty retry is persisted as a normal turn; a test that a double-empty persists the enriched visible failure turn. Keep the retry strictly bounded (one), never loop. Suite green; cite files individually.
