# capture() sets freshness.last_verified_at to real wall-clock time at capture (nowIso())...

> capture sets freshness.last verified at to real wall clock time at capture nowIso , which is what staleTriage's whatC…

capture() sets freshness.last_verified_at to real wall-clock time at capture (nowIso()), which is what staleTriage's whatChangedUnderPath uses as the --since window for scoped git log — commits dated years in the future (e.g. 2030) reliably fall inside that window regardless of when the test suite actually runs, which is a simple way to make git-log-dependent tests deterministic without mocking dates.

Learned while delivering: Two follow-ups from the last round, both found by running the product rather than reading it. Both are small and independent.

FOLLOW-UP 1 — "kage stale" is unreadable, which defeats its whole purpose.
The command works and ranks correctly, but its "what changed" section prints FULL commit subjects, and this repo's commit subjects are entire dispatch briefs — the longest is 313 characters, many are multi-sentence. Measured on the current tree: "kage stale --limit 1" emits 3,979 characters and "--limit 3" emits 15,747. A triage surface exists so a human can judge a packet WITHOUT opening five files; at ~5KB per packet it is worse than opening the files, and it is the same context-bloat disease we just fixed in kage_refresh (which went from 149,739 chars to 11,923).
FIX in mcp/kernel.ts where the stale triage output is assembled:
- Truncate each commit subject to roughly 72 characters on a word boundary with a single-character ellipsis. Do not print commit bodies at all.
- Cap the number of commits shown per moved path (3 is plenty) and say how many more there were, in the same honest register the rest of the output uses.
- Target: "kage stale --limit 3" comfortably under 3,000 characters total. Assert a ceiling in a test and state the number you chose.
Do NOT change the ranking, the suggested-action lines, or the honest framing line about reverify only refreshing grounding — those are all correct and were verified working.

FOLLOW-UP 2 — the MCP dispatch path still runs the agent inline, so a manager-dispatched run dies with the MCP server.
"kage dispatch" was just fixed to hand runs to the detached kage-supervise path (dispatchDetached + followRun in mcp/cli.ts). The agent that did it explicitly flagged two remaining inline callers it left out of scope, and one of them matters more than the CLI: mcp/index.ts around line 1393 still calls dispatchRun directly. That is the kage_dispatch MCP tool — the path the Room manager uses. So a run the manager dispatches for you is a child of the MCP server process and dies with it, which is the same defect in the product's front door.
FIX: route the MCP tool through dispatchDetached the way mcp/cli.ts now does. The MCP tool cannot block waiting for completion the way the CLI's followRun does — it must return promptly with the run id and the brief card, exactly as it does today, and let the caller follow the run through the normal surfaces. Preserve the existing return shape (brief card, judgment block, claim card, goal warning) as far as it still makes sense for a run that has not finished yet; where a field can no longer be filled at return time, say so plainly rather than emitting a placeholder that reads like a result.
There is a THIRD inline caller the same agent flagged — the TUI's dispatch in mcp/delegation/tui/app.ts. Fix it too if it is a small change; if it is not, leave it and say so in your claim, naming it as remaining work.

TESTS — add to the existing mcp/stale-triage.test.ts for follow-up 1 (that file is already this feature's home), and a new mcp/mcp-dispatch-detached.test.ts for follow-up 2 (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: a long commit subject is truncated and no commit body appears; the per-path commit cap holds and states the remainder; the total output ceiling; the MCP dispatch tool spawns detached rather than awaiting the agent inline; the tool still returns a run id promptly. Name in your claim which test fails if each change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. Do NOT touch mcp/delegation/reachability.ts — another run is editing it. Do not run kage_refresh, kage_learn or kage_pr_check.
