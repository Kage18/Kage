# A pipe write followed immediately by process.exit() in Node is not guaranteed to flush ...

> A pipe write followed immediately by process.exit in Node is not guaranteed to flush before the process dies — the te…

A pipe write followed immediately by process.exit() in Node is not guaranteed to flush before the process dies — the test's scripted live child avoids this by never calling process.exit() itself, instead relying on the supervisor closing its side of the child's stdin (which happens only after a genuine claim fence is seen), which lets the child drain and exit naturally once nothing else references its stdin.

Learned while delivering: Fix the root cause of orphaned runs: the detached supervisor exits when a run blocks. Design contract (from the parity spec): the agent process stays alive for the session with stdin open; answering writes into the live session; the SAME supervisor that dispatched the run collects its eventual claim. Today superviseRun in mcp/delegation/supervisor.ts treats a kage-blocked fence as the end of its watch: it transitions the run to blocked and returns, killing its socket and abandoning the held child — so a later answer falls back to steer.ts fire-and-forget resume, whose finished claim nobody collects (observed three times today: answer delivered, agent completed a full turn with a kage-claim fence in the transcript, run reaped as agent-process-gone with no claim.json). Fix supervisorRun so blocked is a WAITING state, not an exit: on a blocked fence, transition to blocked as today, but keep the agent child alive with stdin held and keep serving the control socket; when a tell arrives via the socket, inject it as a user message frame (userMessageFrame exists), transition blocked to running, and continue reading the stream for the next fence; loop until a claim fence (verify via the existing verifyRun path and land ready/failed, exactly as the current post-turn sequence does), a stop command (transition stopped, exit), or child death. Never auto-inject queued steers into a blocked run — only an explicit tell may resume it (this rule exists; keep it). Do not change steer.ts fallback behavior in this run (a follow-up run makes steer re-attach a supervisor; keep scopes separate). Tests in mcp/delegation.test.ts using the existing seams (superviseRun tests, userMessageFrame, interruptFrame, isRunLive, stub adapter — extend stubAdapter with a scripted two-phase behavior if needed: emit a kage-blocked fence, wait for a stdin frame, then emit a kage-claim fence): (1) REGRESSION: a supervised run that blocks stays live (isRunLive true) and a subsequent tell through the socket completes it to ready with a real claim.json; (2) a stop on a blocked supervised run lands stopped and the supervisor exits; (3) existing supervisor and steer tests keep passing unchanged. Success = npm test fully green.
Verified by: npm test --prefix mcp, diff-size, citations
