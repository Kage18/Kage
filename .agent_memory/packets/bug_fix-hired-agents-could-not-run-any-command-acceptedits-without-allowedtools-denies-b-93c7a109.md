# Hired agents could not run any command: acceptEdits without --allowedTools denies Bash in headless mode

> Every hired agent dispatched by Kage has been unable to run a single shell command, and therefore could never verify …

Every hired agent dispatched by Kage has been unable to run a single shell command, and therefore could never verify its own work — it could only reason about correctness.

Cause: the claude adapter in mcp/delegation/adapters/index.ts spawns hired agents with "--permission-mode acceptEdits" and no "--allowedTools", on BOTH spawn paths (the one-shot args builder and claudeLiveArgs). acceptEdits auto-approves file edits only; Bash still requires permission, and in headless "-p" mode there is no interactive prompt to answer, so every command is denied with "This command requires approval" and no approval path reaches the agent.

This is drift, not a design choice. The identical bug was already fixed on the MANAGER path: manager-client.ts and room-supervisor.ts both pass "--allowedTools" explicitly, and room-supervisor.ts even carries a comment recording that spawn sites drifted and that acceptEdits covers file edits only while other tools need an explicit allow in headless mode. The hired-agent path never received that fix.

Diagnostic signature to recognize it again: two or more independent agents report in their claims, unprompted, that npm test / node --test / npx tsc / plain node all return "This command requires approval" while npm run build happens to succeed. When two independent agents fail in the same way, fix the harness, not the agents.

Consequence observed: an agent shipped mcp/release.test.ts reading join(__dirname, "delegation", "run-pty.ts") — which resolves to mcp/dist/delegation/run-pty.ts, a .ts file inside compiled output, so it does not exist. The agent could not run the test to see it fail. Kage's own kernel re-run caught it (NOT VERIFIED 1/3), which is the system working, but the mistake was only possible because the agent was blind.

The fix is an explicit AGENT_ALLOWED_TOOLS list including Bash, passed on both spawn paths, with a test asserting the two paths produce the SAME allowlist so they cannot drift apart again. Do not reach for --dangerously-skip-permissions: the agent already works inside a disposable worktree and the kernel re-runs every check, but an explicit allowlist stays auditable and matches what the manager path does.
Evidence: Read of adapters/index.ts shows --permission-mode acceptEdits with no --allowedTools on both the args builder and claudeLiveArgs; grep confirms --allowedTools appears only in manager-client.ts:59 and room-supervisor.ts:153. Two dispatched agents independently reported the denial in their claim fences on 2026-08-18. The resulting release.test.ts path bug failed Kage's kernel re-run with ENOENT on mcp/dist/delegation/run-pty.ts.
Verified by: Source inspection of both spawn paths plus two independent agent claim fences reporting the same denial
