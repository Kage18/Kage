# TUI rendering laws: erase-per-line, never the last column, split key chunks

> Five terminal rendering laws, each learned from a real corruption in kage ui. First, erase per line: writing a frame …

Five terminal-rendering laws, each learned from a real corruption in kage ui. First, erase per line: writing a frame with cursor-home plus newlines leaves the previous frame tail on screen wherever the new line is shorter, so every row must be followed by the erase-to-end-of-line sequence and rows joined with carriage-return newline; clear-below only clears from the final cursor position downward. Second, never write the last column: a glyph in the final cell can trigger auto-wrap and scroll the whole frame up so the header walks off the top, so renderLines budgets width minus one and the app disables auto-wrap while it owns the screen, restoring it on exit and on the process exit event. Third, split key chunks by walking the buffer and keeping each escape sequence whole; the naive branch of treating any chunk beginning with escape as a single key made held arrow keys do nothing. Fourth, truncate styled text by walking its escape sequences and closing with a reset, or a mid-sequence cut leaks colour down the screen. Fifth, clamp every scroll to content length and reselect by identity after a data refresh, or the reader scrolls into blank space and the cursor jumps rows when a run changes state. The board also hides finished runs by default, because a worklist that accumulates history stops being read. Testing note: these tests must contain literal escape bytes, and some editing paths strip them silently so the assertions then prove nothing.
Verified by: npm test --prefix mcp: 421 unit + 12 dogfood pass; board rendered at 90x14 and 46x10 with zero lines exceeding the safe width
