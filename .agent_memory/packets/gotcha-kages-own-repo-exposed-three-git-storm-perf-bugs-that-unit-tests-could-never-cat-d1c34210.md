# Kage's own repo exposed three git-storm perf bugs that unit tests could never catch

> Running Kage against Kage found three separate per item git process storms that made the product unusable and that ev…

Running Kage against Kage found three separate per-item git process storms that made the product unusable and that every unit test passed through. kageRisk forked 1+80 processes PER FILE for co-change (1,040 spawns, 118 SECONDS, so kage plan never returned); deriveWorkState forked a diff-tree PER COMMIT (up to 600, so GET /v2/work took 6-7s every load); and gitCommitCountForPath was called once per file in the code graph. Every one of those signals falls out of a single 'git log --name-only' walk indexed in memory. Two structural lessons. First, guard perf by COUNTING SPAWNS, not wall-clock: a time budget is flaky on a loaded machine, while 'how many processes does one call fork' is the property that actually regressed and is stable everywhere. Second, memoize on an exact key, not a TTL: the history index is keyed on HEAD (a TTL would go stale inside a test that commits then re-reads) and HEAD is read straight off .git rather than by forking rev-parse, because that check runs on every lookup and was itself 500 of the spawns.
Evidence: Measured before/after on this repo: kageRisk 118,121ms -> 3,047ms, git spawns 1,040 -> 49, kage plan never-returns -> 5.9s, GET /v2/work 6-10s -> 33ms warm. Guards in mcp/vnext/orchestrator/risk-perf.test.ts fail at 57 spawns for 3 targets on the old code.
Verified by: measured on the Kage repo, 2026-07-28
