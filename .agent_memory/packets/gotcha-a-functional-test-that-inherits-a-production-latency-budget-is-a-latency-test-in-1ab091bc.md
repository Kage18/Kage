# A functional test that inherits a production latency budget is a latency test in disguise

> vnext/adapters/adapter.test.ts had three tests whose intent is functional — does sendAdapterEvent POST to /v2/events …

vnext/adapters/adapter.test.ts had three tests whose intent is functional — does sendAdapterEvent POST to /v2/events with the right auth and report accepted — but which called the client with no timeout_ms, inheriting the production ADAPTER_EVENT_TIMEOUT_MS of 150ms. Against a localhost stub on a loaded machine that budget is exceeded, the client correctly fails open, and the test reports a PRODUCT failure when the only thing wrong was the CPU. The fix is a named FUNCTIONAL_TIMEOUT_MS of 60000 passed explicitly by tests whose subject is behaviour, not latency. It deletes no coverage: the budget contract is asserted deterministically elsewhere without a stopwatch — by value in 'adapter timeouts are the budgeted 150 ms and 500 ms', and by asserting the --max-time 0.15 and 0.5 flags the shell adapter emits. Tests that pass a deliberately tiny timeout to prove the fail-open path keep it, because there the budget IS the assertion. Rule: a test may assert a wall-clock budget only when the budget is what it is testing.
Evidence: Applied to the three functional cases in mcp/vnext/adapters/adapter.test.ts (live-runtime delivery, the unauthorized-reason case, event-survives-context-timeout). Those same three failed under load earlier in this session; full suite 1980/1980 green after the change.
