# liveState's inFlight check (running/dispatched/verifying) must never rely on agent_pid ...

> liveState's inFlight check running/dispatched/verifying must never rely on agent pid alone: the agent's own child is …

liveState's inFlight check (running/dispatched/verifying) must never rely on agent_pid alone: the agent's own child is expected to be dead throughout the entire 'verifying' state by design, since the supervisor process performs checks itself after the agent exits — a second liveness source (the supervisor's own pid) is required, and it must not be cleared until after verification completes or the same bug reappears.

Learned while delivering: Two ordering/liveness bugs in the delegation kernel, both proven live today. BUG 1 — goal attachment happens AFTER a run finishes, which keeps the orchestrator wake-loop dead. In mcp/index.ts the kage_dispatch handler does const result = await dispatchRun(...) and only THEN resolves the goal (explicit goal_id, else the room threads active goal via readActiveGoal) and calls attachRunToGoal. dispatchRun executes the entire run — agent work plus verification — so for the whole life of the run goalForRun(runId) returns null, notifyManagerOfRunEvent bails at its first guard, nothing is appended to the goals pending-events log, and the manager is never woken; the attachment only appears once the run is already dead. FIX: add an optional goalId to DispatchOptions in mcp/delegation/dispatch.ts and call attachRunToGoal immediately after createRun inside dispatchRun (before the brief is written, long before the agent runs), tolerating an unknown goal id as a warning rather than a failed dispatch; resolve the goal id in the mcp/index.ts handler BEFORE calling dispatchRun and pass it through; do the same for POST /runs in mcp/delegation/api.ts if it attaches post-hoc. BUG 2 — every verifying run falsely displays as dropped. Verification runs AFTER the hired agent exits (the supervisor performs it), but liveState in mcp/delegation/contract.ts checks isProcessAlive(task.agent_pid), so throughout verification a healthy run shows dropped — and sweepDeadRuns reaps dropped runs after a five-minute grace, so a slow verification can be killed outright. Confirmed live: a run displayed dropped while pgrep showed its supervisor process actively verifying. FIX: record the supervisor process id on the task (supervisor_pid) when superviseRun starts, and have liveState treat an in-flight run as alive when EITHER the agent or the supervisor is alive; a verifying run is only stale when neither exists. Keep every existing honesty rule intact — a genuinely dead run must still be reaped. TESTS in mcp/delegation.test.ts in a clearly separated block at the END of the file: a dispatch with a goalId resolves through goalForRun BEFORE the adapter runs (assert inside the stub adapter callback or after a briefOnly dispatch); an unknown goal id warns but still dispatches; a verifying run with a dead agent pid but a live supervisor pid is NOT stale; with both dead it is. NOTE this project compiles to CommonJS — no import.meta, no top-level await; use __dirname/__filename or require.resolve. Success = npm test fully green.
Verified by: npm test --prefix mcp, diff-size, citations
