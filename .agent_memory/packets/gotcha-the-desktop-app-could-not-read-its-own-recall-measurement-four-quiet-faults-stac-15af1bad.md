# The desktop app could not read its own recall measurement — four quiet faults stacked

> The run strip's claim memory reaching an agent mid flight never rendered, and each layer failed silently. 1 stripTick…

The run strip's claim (memory reaching an agent mid-flight) never rendered, and each layer failed silently. 1) stripTicks marked recalls by ASSISTANT TURN INDEX on the reasoning that the Nth proxy request is the Nth turn — false, because buildProxyDelivery writes NO row when nothing was composed, so delivery rows are a subsequence of requests and the index is lost; nobody ever supplied the turn set. 2) main's refreshRecalls fetched /v2/tasks/:id and read body.deliveries, a key that route has never had (its body is {task, receipt_count}) — the count resolved to undefined and fell to 0 every poll. 3) buildTaskReceiptAggregate, the only assembler carrying deliveries, runs ONLY in mcp/vnext/runtime/server.ts, a daemon the desktop app never starts. 4) mcp/proxy.ts SPOOLS each delivery to .agent_memory/daemon/vnext/deliveries/*.json and only drainDeliverySpool (runtime server + runtime/client.readLocalDeliveries) drains it — so the measurement sat on disk complete and unreadable. Fix: /v2/recalls?task= in vnext/desktop/api-dispatch.ts calls readLocalDeliveries (which drains), and refreshRecalls calls it through the worker pool instead of HTTP. Marks are placed on a TIME axis from delivered_at rather than by index. Lesson: measurement that is written but never drained reads identically to measurement that never happened — verify a metric end to end on a live run, not from the writer's logs.
