# The GUI must render structured claim data, not the CLI's text card — and must never re-derive the verdict

> Kage's app looked like a debug console rather than a product, and the root cause was architectural, not cosmetic: sev…

Kage's app looked like a debug console rather than a product, and the root cause was architectural, not cosmetic: several screens re-rendered strings formatted for a TERMINAL inside the GUI. The Receipt — the product's signature moment — displayed renderClaimCard()'s output, so the UI showed box-drawing glyphs and absolute evidence paths (.agent_memory/runs/<id>/evidence/tests.log) wrapping mid-path across three lines. The same facts were already available as structured data on the claim (checks[] with id/cmd/expect/result/exit_code, diff{files,lines}, unsure[], learnings[]), so the GUI now composes its own presentation (verdict stamp, check rows with icon+name+detail+exit code, Change/flagged/learns sections) while the CLI keeps renderClaimCard for terminals. One source of truth, two honest renderings — rather than one rendering pretending to work in both places. CRITICAL bug introduced and caught during that rewrite: the first version RE-DERIVED the verdict client-side from checks[], and rendered a green "VERIFIED 2/3" for a run the kernel had already marked failed — because a check that could not run (exit 127, result skipped) read as merely absent rather than as a reason not to certify. That is precisely the overclaim this product exists to prevent, produced by Kage's own UI. Fix: runDetail() in api.ts now ships detail.verdict from the kernel's own claimVerdict(), computed where the checks actually ran, and the client renders that label verbatim — falling back to a pessimistic local guess only if the field is absent (older API). Law: surfaces render verdicts, they never compute them. Two smaller UI lessons from the same pass: (1) a stamp label from the kernel may already contain its own count ("NOT VERIFIED 2/3"), so appending a client-side count printed "2/3 2/3" — check before adding; (2) board columns used grid-template-columns:repeat(4, minmax(240px,1fr)), where a long unbroken card title forces its column wider than its siblings — minmax(0,1fr) plus min-width:0 on the column keeps them genuinely equal.
Evidence: Regression test "run detail ships the KERNEL's verdict, so a surface can never certify a run the kernel failed" asserts the API sends a kernel-computed verdict and that a non-passing run is never labelled VERIFIED. Verified visually in a real Electron window: the same failed run that previously rendered a green VERIFIED 2/3 now renders a red NOT VERIFIED 2/3 matching the kernel, with checks as readable rows and no leaked evidence paths.
Verified by: npm test --prefix mcp → 494 unit + 12 dogfood pass; Electron window capture of the Receipt tab

## Verification

Regression test "run detail ships the KERNEL's verdict, so a surface can never certify a run the kernel failed" asserts the API sends a kernel-computed verdict and that a non-passing run is never labelled VERIFIED. Verified visually in a real Electron window: the same failed run that previously rendered a green VERIFIED 2/3 now renders a red NOT VERIFIED 2/3 matching the kernel, with checks as readable rows and no leaked evidence paths.
