# A CLI-dispatched run dies with the shell that launched it — no supervisor_pid, no detachment

> Reproduced live on 2026 08 18: killing the kage dispatch CLI process kills the run it launched. The run record was le…

Reproduced live on 2026-08-18: killing the `kage dispatch` CLI process kills the run it launched. The run record was left at state "running" with agent_pid pointing at a dead process, supervisor_pid undefined, and liveState().stale true — so it displayed as "dropped" having done no work at all.

Cause: `kage dispatch` executes the run INLINE. dispatchRun runs the hired agent as a child of the CLI process, and supervisor_pid is written in exactly one place — mcp/delegation/supervisor.ts, the detached `kage-supervisor` path used by the daemon/app. Nothing on the CLI path records an owning process, and nothing detaches the agent from its parent. Close the terminal, hit a shell timeout, or Ctrl-C, and a run that may be many minutes and dollars in is gone.

This is a real parity gap, not a nicety. AO's agents live in panes independent of its daemon and Conductor's survive the launching terminal; both were explicitly studied for this product. The repo's own architecture notes already state the intended law — "supervisors stay detached anyway... a daemon restart must never kill a 45-minute agent" — but that guarantee only holds for the daemon/app path, never for the CLI verb the docs put front and centre.

Two consequences worth remembering:
1. Any long dispatch driven from a script or a tool with a command timeout must be launched detached (nohup/setsid, or via the daemon) or it will be killed mid-run. An operator harness with a two-minute command timeout will silently destroy every run it starts.
2. When this happens the failure is indistinguishable, from the record alone, from an agent that died on its own — the honest disposition is to reject the run naming the real cause rather than let it read as an agent failure, because rejection reasons become repo memory and future briefs will carry the wrong lesson otherwise.

The fix (not yet made) is either to detach the child on the CLI path and record supervisor_pid the way superviseRun does, or to have `kage dispatch` hand the work to the daemon and follow it — plus stating the tie-to-this-shell plainly if it stays inline.
Evidence: Ran kage dispatch under a 120s harness timeout; the CLI was SIGTERMed (exit 143). Reading the run record immediately after showed state "running", display_state "dropped", agent_pid 85608 dead, supervisor_pid undefined, liveState().stale true. grep for supervisor_pid across mcp/**/*.ts excluding tests returns only contract.ts's field declaration, contract.ts's liveState read, api.ts's spawned.pid response, and the two writes in supervisor.ts — none on the dispatch.ts/CLI path. Re-dispatching the identical intent under nohup survived and reached "running" normally.
Verified by: Live reproduction plus source grep of every supervisor_pid write site
