1. TWO separate runs were told 'put your tests in a NEW file X, NOT mcp/delegation.test.ts' and both put them in delegation.test.ts anyway. That file is a merge-conflict hotspot — three merges collided in it in one day, one conflict boundary landed inside a test and ate its closing brace. The convention only ever appears as ad-hoc prose in whatever brief I happen to write, so it is not really a repo convention at all.
2. One run shipped 268 lines of new behaviour (goal state advance, auto-merge, budget and file-scope gates) with ZERO new tests — its only test-file edits were adjustments to two EXISTING assertions so they would still pass. The kernel said VERIFIED 6/6 because the suite was green; nothing checked that the new behaviour was covered. A safety gap in that code (auto-merging a claim the product itself labels UNVERIFIED) survived to review as a result.
3. That same run skipped the claim fence entirely, so its statement was derived from the diff and there was no account of what it did or what it was unsure about.

WHAT TO CHANGE, in mcp/delegation/brief.ts's renderBrief (this is the ONLY file whose behaviour you change):
a. A TEST PLACEMENT section stating the repo convention as a rule, not a preference: new behaviour gets tests in a NEW file named for the behaviour; mcp/delegation.test.ts is append-collision-prone and must not receive new tests. Derive the suggested filename from the run's own type/intent if that is cheap; otherwise state the rule plainly and let the agent name the file.
b. A COVERAGE rule: new behaviour must ship with a test that FAILS without the change. Say why in one line — a test that passes with and without the change proves nothing, and the kernel's green suite cannot tell the difference. Tell the agent to state in its claim which test would fail if the change were reverted.
c. Strengthen the claim-fence instruction so skipping it reads as a failure rather than an option: the fence is how the agent's own account, its unsure notes, and its learnings reach the operator and repo memory. A run without one lands with its statement reverse-engineered from the diff.
d. Keep it SHORT. The brief is already long and every added line competes with the task itself for the agent's attention — this is exactly why the ad-hoc prose version failed. Aim for a handful of lines per point, in the same voice as the existing sections.

HOW YOU'LL KNOW IT WORKED — put tests in a NEW file mcp/brief-rules.test.ts (yes, this instruction is itself an instance of rule (a) — follow it):
(a) renderBrief output contains the test-placement rule and names delegation.test.ts as off-limits;
(b) it contains the fails-without-the-change coverage rule;
(c) it tells the agent to name the test that would fail if the change were reverted;
(d) the claim-fence instruction is present and phrased as required, not optional;
(e) a size assertion: the rendered brief for a fixture task stays under a byte budget you choose and state, so this section cannot grow unbounded later.

CONSTRAINTS: CommonJS — no 'import.meta' (TS1470), no top-level await. Change ONLY mcp/delegation/brief.ts plus your new test file. Do not touch mcp/index.ts, mcp/delegation/goal.ts, mcp/delegation/ratify.ts or mcp/delegation/checks.ts — other runs are editing those.
