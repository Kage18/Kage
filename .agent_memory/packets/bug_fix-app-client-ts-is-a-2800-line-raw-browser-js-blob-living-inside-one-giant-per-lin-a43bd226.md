# app-client.ts is a ~2800-line raw browser-JS blob living inside one giant, per-line-unt...

> app client.ts is a ~2800 line raw browser JS blob living inside one giant, per line unterminated backtick template li…

app-client.ts is a ~2800-line raw browser-JS blob living inside one giant, per-line-unterminated backtick template literal — a plausible first hypothesis was that stripTemplateLiteralText blanks the whole thing (hiding every reference inside it), but that stripper is stateless per-line and only strips content between a balanced backtick pair found on the SAME line; since almost no individual line inside the blob contains a literal backtick character, the blob's tokens are actually still visible to the reference/read-write scan unmodified. Dead end — worth knowing before re-investigating that file.

Learned while delivering: The reachability check's field rule is now doing more harm than good on real receipts. Tighten it or cut it.

MEASURED on real claim receipts today: the reachability line reported 198 names on one run and 196 on another — a wall of text on the receipt a human is supposed to read. Rule A (orphan exports) is clean after two precision passes; this is entirely Rule B, the one-sided-field rule.

CONFIRMED FALSE POSITIVES in the current output:
- autonomy — reported as read-only, but it is now genuinely read at mcp/delegation/ratify.ts (maybeAutoMerge gates on goal.autonomy !== "merge") AND written at mcp/delegation/goal.ts. Both sides exist.
- files_scope — reported, but it is now genuinely read: the wave disjointness gate consumes it.
- delivered_at — reported as write-only, but it is read at mcp/delegation/app-client.ts:2147.
Those three were all made genuinely two-sided by work that landed after the rule was written, and the rule did not notice.

ROOT CAUSE the rule's own author documented: Rule B does not check whether a field was ADDED by the run. It flags any field belonging to an interface declared in a changed file — a deliberately conservative superset. On a run that touches a file holding large interfaces (contract.ts, kernel.ts), that superset is the entire type surface, which is how one receipt reached 198 names.

Rule B is not worthless — it originally found two genuinely inert fields (autonomy and files_scope, before they were wired), which is exactly the value-flow disease this check exists for. So do not delete it reflexively.

WHAT TO DO — choose and justify in your claim:
(a) SCOPE IT TO THE DIFF. Only consider fields the run actually added or modified, from the run's own diff, not every field on every interface in a touched file. This is the fix the author implied and it should collapse the output to a handful of names.
(b) FIX THE READ/WRITE DETECTION so a field consumed inside a conditional or a comparison counts as read, which is what all three false positives above have in common.
(c) CUT RULE B and keep Rule A, if you conclude the detection cannot be made precise enough to be trusted. State that plainly rather than shipping a rule nobody reads.
Prefer (a), and add (b) if it is cheap. (c) is an acceptable honest outcome.

ACCEPTANCE BAR, state each result in your claim: after your change, running findOrphans over mcp/delegation/goal.ts, mcp/delegation/ratify.ts and mcp/delegation/contract.ts must NOT report autonomy, files_scope or delivered_at. A run touching a large-interface file must produce a receipt line short enough to read — assert a cap on the number of reported names and state the number you chose, with the remainder summarised as a count rather than a list. And Rule B must still catch a genuinely one-sided field: construct one in a fixture and prove it.

ALSO IN THIS RUN — pin a timing flake. mcp/mcp-dispatch-detached.test.ts has a test asserting kage_dispatch returns promptly, measured against a wall-clock delay; it failed once today at 2065ms against a 3000ms threshold and passed on rerun. A timing-dependent assertion in a suite this size is a future false alarm that will cost someone an investigation. Make it deterministic — assert the ordering property it actually cares about (that the tool returns BEFORE the agent finishes) using the existing test seams rather than a wall-clock margin. If you cannot make it deterministic, widen the margin substantially and comment why.

TESTS: extend mcp/reachability.test.ts for the Rule B work (that file is this check's home) and mcp/mcp-dispatch-detached.test.ts for the flake. Name in your claim which test fails if each change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. Do NOT touch mcp/delegation/dispatch.ts or mcp/delegation/supervisor.ts — another run is editing those.
VERIFY: npm run test --prefix mcp (731 green before your change — use the "npm run test" form) and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence.
