# mcp/delegation-api.test.ts's DelegationApiContext test seam has no built-in way to atta...

> mcp/delegation api.test.ts's DelegationApiContext test seam has no built in way to attach a run to a room thread's se…

mcp/delegation-api.test.ts's DelegationApiContext test seam has no built-in way to attach a run to a room thread's session — the real linkage is room-sessions.ts's active_goal_id (a thread's active goal) plus goal.ts's attachRunToGoal populating plan.waves[].run_ids; GET /room's suggested_next now reads through that chain via a new roomSuggestedNext() helper in api.ts.

Learned while delivering: W1.1 - close the three API gaps the W2 renderer run named in its claim's unsure notes (it was rightly forbidden from touching api.ts and stopped instead of hacking around them). All three are small, additive, read-side response fields in mcp/delegation/api.ts; the consumers already exist in the merged app-client.
1. VERDICT ON CARDS: run list/board responses expose claimVerdict()'s label (from mcp/delegation/verify.ts) for finished runs - the field the card verdict chip should render instead of the formatted claim_summary it settled for. Name the field verdict_label; absent when no claim exists.
2. ROOM GHOST TEXT: GET /room (and the room status payload the composer reads) carries suggested_next derived from delegation/suggest.ts's suggestedNextPrompt applied to the ROOM's state - the manager waiting on an approval exposes that question; otherwise null. Do not invent room-specific suggestion rules beyond what suggest.ts already encodes; if suggest.ts only understands runs, add one exported room-shaped wrapper THERE and have api.ts call it (suggest.ts is yours for exactly that addition).
3. TRANSCRIPT AVAILABILITY: the room payload states whether a native transcript exists (has_transcript boolean + its turn count) so the chat view can say WHY it fell back to history rendering instead of guessing - the W2 fallback path reads this to label itself honestly.
Then wire the three consumers: flip the card chip to verdict_label, the Room composer to suggested_next, and the chat fallback label to has_transcript - minimal app-client.ts edits only at those three call sites (template-literal rules: escapes DOUBLED, no backticks, no ${ }, never innerHTML).
TESTS - new file mcp/sessions-api-gaps.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits): verdict_label present for a claimed fixture run and absent otherwise; room suggested_next reflects a waiting manager and null otherwise; has_transcript true/false against a fixture; the composed page still parses. Name which test fails on revert.
CONSTRAINTS: CommonJS, no import.meta, no top-level await. Your files: mcp/delegation/api.ts, mcp/delegation/suggest.ts (wrapper only), mcp/delegation/app-client.ts (three call sites only), your new test file. Nothing else. Build and test ONLY inside your own worktree - never against /Users/kushaljain/code/Kage. Rebase onto release-prep first if your base shows an inherited red.
VERIFY: npm run test --prefix mcp (986 unit + 12 dogfood green on main) and npm run build --prefix mcp with no 'error TS'. Run for real, fill the claim fence, cite files individually - never slash-joined.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, node --check <composed inline script>, reachability
