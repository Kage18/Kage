# Concurrent kernel verifications on one machine flake each other's timing-sensitive tests — verify needs a per-machine mutex

> Three different runs failed verification today on three different timing sensitive tests delegation api.test.ts room …

Three different runs failed verification today on three different timing-sensitive tests (delegation-api.test.ts room-queue race, delegation-api.test.ts room-message round-trip, resume-budgets.test.ts dispatchDetached log-file window), and every one passed solo on the same tree — including solo inside the failing run's own worktree. The common factor each time: another kernel verification (or a worker agent's inner test run) was executing the full suite concurrently on the same machine. Verification is correct but not isolated: two full `npm test` suites interleaving starve the spawn/timing windows these tests assert. Until the check-runner holds a per-machine verification lock (serialize full-suite checks across runs; queue, don't interleave), the operator playbook is: when a run fails on a single timing-shaped test its diff cannot touch, wait for the machine to go quiet, then `kage reverify <run-id>` — and never re-dispatch the agent for this failure shape.
Evidence: website run failed room-queue test 12:25 while two other suites ran, passed reverify quiet; polish run failed dispatchDetached at 14:55 and again during reverify while the room run's agent was testing, then passed solo in its own worktree; onboarding run failed room round-trip under the same triple-suite load
Verified by: solo re-executions on main and inside the failing worktree on 2026-08-21
