# The transcript pane must filter to renderable entries BEFORE windowing — invisible stdout starved the visible history

> renderConversation in mcp/delegation/app client.ts windows the transcript to the last 160 entries and now folds 8+ co…

renderConversation in mcp/delegation/app-client.ts windows the transcript to the last 160 entries and now folds 8+ consecutive tool actions into a self-summary row. Both features silently failed at first because the window and the grouping ran over ALL journaled entries: a real claude run's transcript is dominated by kinds the pane never renders (measured: 130 of 160 entries were stdout), so the visible history was starved to ~30 rows and no tool burst was ever consecutive — the fold code was correct and never fired. The fix is ordering: filter to renderable kinds (tool, _ledger, start, non-empty say/final) FIRST, then slice the window, then group. General rule for any windowed/grouped view over a heterogeneous event stream: invisible entries must be transparent to both the budget and the adjacency logic, or the view under-shows and never groups. Also from the same pass: the app's error surface is split by severity — flash() remains a status blip for successes, showError() is a persistent dismissible bar for failures; optimistic action labels (Merging…) live in a pendingActions map outside the DOM so SSE re-renders cannot wipe them; and body.offline + an amber ribbon mark a dropped event stream, with the EventSource onopen handler re-reading /runs and /room because a reconnected board may have missed events.
Evidence: Live diagnosis on the stopped run: kinds histogram showed 130 stdout / 19 tool in the 160-entry window with longest tool run 2; after the filter-first fix the same run rendered fold rows "31 actions — 31 commands" and "22 actions — 7 reads · 15 commands".
Verified by: Commit 446e473; 567/567 tests exit 0; browser verification incl. a real daemon kill/restart cycle for the offline ribbon and resync.
