# guardManagerProse only runs inside room-supervisor.ts's stdout-parsing of the headless ...

> guardManagerProse only runs inside room supervisor.ts's stdout parsing of the headless stream json protocol; the pty …

guardManagerProse only runs inside room-supervisor.ts's stdout-parsing of the headless stream-json protocol; the pty path has no post-processing step at all (raw terminal bytes broadcast straight through), so the guard already does not and structurally cannot apply to the real interactive session

Learned while delivering: Make the orchestrator a real agent session with Kage's tools, the way AO does it. Stop wrapping what we do not need to wrap.

WHAT AO ACTUALLY DOES — observed by running a real two-worker job through Agent Orchestrator today, not from documentation. Its orchestrator is a literal Claude Code session running in its OWN git worktree (~/.ao/data/worktrees/<project>/orchestrator/<project>-orchestrator, on a branch ao/<project>-orchestrator). The app wraps it with a task button, a kanban and notifications — nothing else. Because it is the real agent, it inherits slash commands, /effort, auto-mode cycling, file editing and everything else the CLI can do, for free. It spawns workers by running shell commands. Given "add multiply and divide, one worker each" it replied "No active workers exist, so I'll spawn two parallel workers — one per function", spawned them, and noticed unprompted that both touched calc.js and might conflict.

WHERE KAGE STANDS — read these three files first, the gap is smaller than it looks:
- mcp/delegation/room-pty.ts ALREADY spawns a real interactive claude in a pty. Its own header says "no -p, no --input-format: the same command a person would type". But it passes NO --mcp-config, so that session has none of Kage's tools. It is a bare terminal.
- mcp/delegation/room-supervisor.ts spawns the OTHER manager — headless `-p --input-format stream-json` — and that one DOES get Kage's tools via writeRoomMcpConfig (mcp/delegation/room.ts), MANAGER_ALLOWED_TOOLS and MANAGER_CONSTITUTION.
- Both run with cwd = projectDir. Neither gets its own worktree, so the manager works directly in the user's tree.

So we have a real agent with no tools, and a tooled agent that is not real. Join them.

WHAT TO BUILD:
1. Give the pty orchestrator Kage's tools. Pass --mcp-config (reuse writeRoomMcpConfig — do not write a second config path) to the interactive claude spawned in room-pty.ts, so the orchestrator can call kage_dispatch, kage_goal_create, kage_goal_status, kage_task, kage_tell, kage_merge_run and the rest. This is the whole point: a real session that can actually orchestrate.
2. Give the orchestrator its own worktree. Create it the way runs already get one (mcp/delegation/worktree.ts) — a dedicated branch and directory for the orchestrator session, so it can read the repo and write scratch files without dirtying the user's working tree. Follow AO's shape: a branch named for the orchestrator, a worktree under Kage's own data directory, never the user's checkout. Keep the run worktrees exactly as they are.
3. Carry the constitution as instructions the real session reads, not as a wrapper. MANAGER_CONSTITUTION currently rides on --append-system-prompt for the headless path. For the interactive session, write it into the orchestrator worktree as a CLAUDE.md (AO does exactly this — its own welcome banner suggests /init to create one). State in your claim which mechanism you used and why.
4. Do NOT delete the headless chat path in this run. Chat and Terminal are two views of one session today and the app depends on it. Make the tooled interactive session work and be reachable, prove it, and note in your claim what would have to change for the headless path to be retired later. A half-removed manager is worse than two working ones.
5. Because the real session is no longer post-processed, note in your claim whether guardManagerProse should still apply to it. Do not change the guard in this run — just say what you found. (Context: the guard exists because we wrap a manager we cannot fully trust; a real session the user is watching may not need it.)

HOW YOU'LL KNOW IT WORKED — this is the acceptance bar and it must be demonstrated, not assumed: start the orchestrator session and confirm it can actually call a Kage tool. The cheapest proof is kage_goal_status or kage_report — something read-only that fails loudly if the MCP config is missing. Say in your claim exactly which tool you invoked and what came back. A session that starts but cannot reach a single Kage tool is the current state, not the fix.

TESTS — new file mcp/orchestrator-session.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: the interactive spawn args include --mcp-config pointing at the room config; the orchestrator worktree is created on its own branch and is not the user's checkout; the constitution reaches the session by whichever mechanism you chose; and the existing headless path still spawns unchanged. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. node-pty is an OPTIONAL dependency and is imported lazily — do not make it mandatory, and keep the graceful degradation when it is absent. Do not touch mcp/kernel.ts.
VERIFY: npm run test --prefix mcp (767 green before your change — use the "npm run test" form) and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, reachability
