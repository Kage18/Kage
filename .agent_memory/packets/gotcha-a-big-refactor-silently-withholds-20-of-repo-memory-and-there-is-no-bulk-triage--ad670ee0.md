# A big refactor silently withholds ~20% of repo memory, and there is no bulk triage workflow to recover it

> Measured 2026 08 18 after a day of 28 merged delegated runs: 93 of 466 packets carry quality.stale === true, and kage…

Measured 2026-08-18 after a day of 28 merged delegated runs: 93 of 466 packets carry quality.stale === true, and kage doctor reports 107 packets withheld from recall because the code cited under them moved. Composition of the flagged set: decision 38, bug_fix 14, workflow 13, gotcha 8, runbook 7, reference 6, code_explanation 4, convention 3.

This is NOT a correctness bug — withholding is the honest behaviour working as designed. The uncomfortable part is the shape of the incentive: Kage loses a fifth of its recall precisely after the kind of large, multi-file change it exists to support, and the product offers no affordance to get it back at that scale.

Why bulk reverify is the WRONG reflex, and must not be automated casually: reverifyMemory in mcp/kernel.ts only refreshes path fingerprints and clears the stale flag. It does not re-check whether the packet's CLAIM is still semantically true. Its only refusal is when every cited path is gone, guarded by an explicit comment that reverifying then "would rubber-stamp dead evidence". So running reverify across every stale packet would clear all 93 flags while validating nothing — converting an honest "we are not sure this still holds" into a false "verified". That would corrupt the one property the product sells.

What is actually missing is triage, not a flag-clearing loop: a way to see, for each stale packet, what changed under it and whether the claim survives, then reverify / supersede / mark-stale per packet with a recorded reason. The per-packet commands already exist (kage reverify --packet <id>, kage supersede --packet <old> --replacement <new>); there is no batch surface, no diff-of-what-moved to judge against, and no way to sort by which packets are most worth rescuing.

Practical guidance until that exists: never bulk-reverify. Triage by value — a decision packet whose rationale is unchanged by a file move is worth reverifying by hand; a bug_fix packet describing code that was rewritten should be superseded, not reverified.
