# Expensive synchronous work must leave the process, not just move after listen()

> kage viewer regenerated 26 reports synchronously BEFORE server.listen , so it printed nothing and served nothing for …

`kage viewer` regenerated 26 reports synchronously BEFORE server.listen(), so it printed nothing and served nothing for 227 seconds — measured per call on this repo: kageRepoXray 80s, kageContributors 58s, kageRisk 39s, kageModuleHealth 30s, kageDecisionIntelligence 10s, kageCapabilityAudit 4.6s, kageMetrics 2.8s. To a user that is a hung command, not work in progress.

The instructive part is that the OBVIOUS fix was wrong. Moving generation after listen() made time-to-listen fast but did not make the viewer usable: Node is single-threaded, so an 80s synchronous call blocks the server that is already listening. Adding `await setImmediate` between reports only opens gaps BETWEEN them — a request landing inside kageContributors still measured 58s to return. A measurement taken during one of those gaps read 4.2s and looked like success; the honest worst-case measurement (touch every packet to force full regeneration, then poll) showed 154.8s. Sampling a fast path does not prove the slow path is gone.

The fix that worked: generation runs in a DETACHED CHILD PROCESS (`kage viewer-reports`, an internal command in the same family as supervise-room/supervise-room-pty, spawned by startViewer). Result: 0.5s to first byte cold with every report stale, and the server holds ~0.9ms response times while the child does all 227s of work. Reports also skip regeneration when their mtime is newer than the newest packet/index, so an unchanged repo does no work at all.

Generalizes: any CPU-bound synchronous kernel function called from a request path or a server's startup will freeze that server for its full duration. The app's memory view follows the rule from the other side — it reads only pre-built indexes (catalog.json + metrics.json, ~2ms) and never calls these analysis functions.
Evidence: Per-call timings measured by invoking each kernel function directly. Cold worst case (all packets touched, so every report stale): before 227s to first byte; after moving past listen() but staying in-process 154.8s; after moving to a detached child 0.5s with server responses at 0.000846s/0.000626s/0.000551s during the child's full run. Background child confirmed to write 21 reports.
Verified by: Timed polling of http://127.0.0.1:3113/viewer/index.html after `touch .agent_memory/packets/*.md`; npm test 537 pass 0 fail exit 0
