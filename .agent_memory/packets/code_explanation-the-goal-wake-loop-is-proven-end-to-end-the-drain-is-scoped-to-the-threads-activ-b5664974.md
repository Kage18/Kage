# The goal wake-loop is proven end-to-end; the drain is scoped to the thread's ACTIVE goal

> The orchestrator's goal wake loop was verified end to end on 2026 08 18, not just unit tested. Three facts a future s…

The orchestrator's goal wake-loop was verified end-to-end on 2026-08-18, not just unit-tested. Three facts a future session should not re-derive:

1. Goal attachment provably precedes execution. dispatchRun calls attachRunToGoal immediately after createRun, before writeBrief. Proof technique: dispatch with briefOnly:true, which returns at state "briefed" before any agent work, and assert goalForRun(runId) is already non-null. Before this fix attachment ran after dispatchRun returned, so goalForRun was null for a run's entire life and the wake-loop never fired.

2. notifyManagerOfRunEvent appends to the goal's durable pending log BEFORE testing manager liveness, so a busy or dead manager delays an event but never drops it. It resolves false whenever nothing was sent this call — false means "not delivered right now", NOT "lost". Callers must treat it as fire-and-forget.

3. drainPendingGoalEvents is scoped to the thread's ACTIVE goal, resolved via readActiveGoal(projectDir, normalizeSessionKey(session)). The default session key is the literal string "main" (DEFAULT_SESSION in room-sessions.ts), not "default" — passing "default" silently normalizes to a different key and the drain returns false at its first guard with the events left pending. Every goal created through POST /goals is made active immediately, and POST /goals/:id/activate exists, so the guard is satisfied on the real product path.

Its deps for testing are readActiveGoalFn, readGoalFn, readPendingGoalEventsFn, isLiveFn and sendFrameFn — not the goalForRunFn/sendToManagerFn names notifyManagerOfRunEvent uses. Passing the wrong names produces a silent false that looks exactly like a real bug.

Verified output of a full loop: "[kage event] ordering proof: run touch-a-txt-260818-6ee0 is now ready: proof", after which readPendingGoalEvents returned empty.

KNOWN NARROW GAP, not yet fixed: because the drain reads only the active goal, pending events belonging to a non-active goal are never swept. Immediate delivery still covers them (notifyManagerOfRunEvent uses goalForRun, not the active goal), so this only strands events for a background goal whose immediate delivery failed because the manager was busy or dead.
Evidence: Ran a temp-repo harness against mcp/dist: briefOnly dispatch showed state "briefed" with goalForRun already returning the goal id (ORDERING: PASS). notifyManagerOfRunEvent queued 1 pending event with no live manager. drainPendingGoalEvents with isLiveFn/sendFrameFn stubs returned true, delivered 1 coalesced frame, and left 0 pending. Using session key "default" instead of "main" reproduced the false-at-first-guard failure.
Verified by: Live end-to-end harness against compiled mcp/dist plus npm test --prefix mcp at 627/627 passing
