# Root cause of every orphaned run: ALL supervisors exit at blocked — spec said hold the session, no test pinned it

> Correction and root cause for the orphaned run pattern supersedes the CLI only framing in the first dogfood day gotch…

Correction and root cause for the orphaned-run pattern (supersedes the CLI-only framing in the first-dogfood-day gotcha): superviseRun in mcp/delegation/supervisor.ts exits when a run emits a kage-blocked fence — for DETACHED supervisors too, not just CLI-inline ones. From that moment the run is unownable: steerRun finds no live socket, falls back to fire-and-forget claude --resume, and the resumed turn's kage-claim fence lands in the transcript with no collector — no claim.json, no verification, no transition; the reaper later records agent-process-gone. Observed three times in one day (two chat-fix attempts and the tokenizer fix; each time the finished work sat uncommitted in the worktree and the transcript held the fence). The parity spec explicitly required the opposite ("the agent process stays alive for the session with stdin open; answering writes into the live session") — the behavior was specified, half-built, and no test ever asserted supervisor survival across blocked: the same disease as reapRun-with-zero-callers, an invariant written in prose with no executable witness. Fix dispatched as run fix-the-root-cause-of-orphaned-runs-the-260817-7cae (supervisor holds through blocked: child alive, socket served, tell injects and resumes, same supervisor verifies the eventual claim), with a follow-up planned for steer re-attaching a supervisor when none is alive. Operator rule until both land: treat blocked runs dispatched before the fix as one-answer-then-orphan; do not steer them expecting completion.
Evidence: Three orphans in one day, each with the kage-claim fence present in transcript.jsonl and no claim.json; steer delivery reported "resumed" (no live socket) on a POST /runs detached dispatch, proving the detached supervisor was gone at blocked.
