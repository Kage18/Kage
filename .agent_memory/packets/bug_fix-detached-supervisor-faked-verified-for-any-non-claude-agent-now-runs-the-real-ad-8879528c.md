# Detached supervisor faked VERIFIED for any non-claude agent; now runs the real adapter

> mcp/delegation/supervisor.ts's superviseRun the ONLY path a web app or POST /runs dispatch uses, via dispatchDetached…

mcp/delegation/supervisor.ts's superviseRun (the ONLY path a web-app or POST /runs dispatch uses, via dispatchDetached -> `kage supervise <id>`) special-cased adapter.name !== "claude" by spawning `node -e process.exit(0)` — a no-op placeholder — instead of running the real Adapter. The worktree never changed, state.finalMessage stayed empty, parseReportFence found nothing, and the fallback statement "work delivered — see diff (agent skipped the fence)" plus generic checks passing trivially against a zero-line diff produced a VERIFIED claim for work that never happened. The in-process path (dispatch.ts's executeRun, used by dispatchRun and every existing test) was unaffected because it always called adapter.run() properly — the bug only hit runs dispatched through the daemon/API, which is exactly how the desktop app and `curl POST /runs` create runs. Found by checking why a stub-dispatched run's Follow tab had nothing to render. Fixed: superviseRun now branches on adapter.name — claude keeps the live stdin-held child process; every other adapter (stub, codex) runs through the same `await adapter.run({runId, workDir, briefBody, transcriptPath, sessionId, onStart})` the in-process path already trusted, with the supervisor's own pid standing in for agent_pid liveness (no child process handle exists for these). Do NOT pass onProgress into that adapter.run() call — every adapter already journals its own events directly to transcriptPath (stub.ts and cli-agent.ts both do); onProgress is a separate side-channel for a live console line (dispatch.ts's ProgressLine), and wiring it back into log() double-writes every event. Also: never emit a bookkeeping kind:"final" event without a .message field — stub.ts's real final event already uses kind:"final" with the agent's actual answer for transcript rendering, so a second kind:"final" for exit-code bookkeeping renders as an empty chat bubble right after the real one; the claude branch's own name for that moment, kind:"turn_complete", is the one to reuse.
Evidence: New test "the detached supervisor runs a non-claude adapter for real" asserts claim.statement equals the adapter's real statement (not the generic fallback), protocol_ok is true, and diff.files >= 1. Live-verified via curl POST /runs against a running daemon: transcript.jsonl went from 2 sparse lines (start+final with no message) to a real start/tool/final(with message)/turn_complete sequence, and the app's Follow tab rendered an actual edit row and a real reply bubble instead of nothing.
Verified by: npm test --prefix mcp -> 477 unit + 12 dogfood pass; live daemon dispatch + browser screenshot showing the corrected transcript rendered

## Verification

New test "the detached supervisor runs a non-claude adapter for real" asserts claim.statement equals the adapter's real statement (not the generic fallback), protocol_ok is true, and diff.files >= 1. Live-verified via curl POST /runs against a running daemon: transcript.jsonl went from 2 sparse lines (start+final with no message) to a real start/tool/final(with message)/turn_complete sequence, and the app's Follow tab rendered an actual edit row and a real reply bubble instead of nothing.
