> capture with a nonexistent path in paths succeeds status 'approved', non strict mode just warns and refreshProject fl…

capture() with a nonexistent path in `paths` succeeds (status 'approved', non-strict mode just warns) and refreshProject flags it stale with suggested_action 'update' — this is the simplest reliable way to manufacture N stale packets in a test fixture. Setting a captured packet's status to 'deprecated' post-hoc (via okfConceptToPacket/packetToOkfConcept round-trip) instead yields suggested_action 'mark_stale', useful for testing urgency ranking.

Learned while delivering: kage_refresh returns ~150KB per call — the tool whose whole promise is saving context is one of the biggest context consumers in the product. Cap it.

MEASURED, not estimated (2026-08-18, this repo at 448 packets): one kage_refresh call returned 149,739 characters across 3,053 lines — large enough that the MCP client REFUSED the result outright and spilled it to a file, so the caller got nothing useful at all. Breakdown by JSON key:
- stale_packets: 105,516 chars — an array of 177 entries. Each entry is individually lean (~580 chars: id, title, type, status, paths, reasons, suggested_action). The bloat is the COUNT: every stale packet is returned, uncapped.
- validation: 17,745 chars — 78 warnings, mostly 'low memory quality score NN' lines.
- the rest (~26K) is index, metrics, code_graph, memory_graph, next_actions.

Why this matters more than a normal perf nit: CLAUDE.md instructs every agent to call kage_refresh after meaningful file or content changes, so this cost is paid at least once per session — and Kage prints a gains receipt measured in tokens saved while quietly spending ~37K reporting on itself.

WHAT TO BUILD:
1. Cap the large collections in the kage_refresh MCP response (mcp/index.ts is where the tool result is assembled — find the refresh handler): return a COUNT plus the top N most actionable entries (N around 10 for stale_packets, 10 for validation warnings), never the whole array. Rank stale_packets by whatever the existing suggested_action / status already implies is most urgent; do not invent a new scoring system.
2. Say what was withheld, in the same honest register the rest of the product uses — e.g. 'showing 10 of 177 stale packets' — so a caller is never misled into thinking the list is complete. Silence about truncation is the failure mode here.
3. Give the caller a way to get the rest on demand rather than dropping the data: an explicit argument (e.g. limit, or a full/verbose flag) that returns more when someone actually asks. Default must be the capped view.
4. Do NOT shrink the per-entry fields — they are already lean and trimming them hides detail without fixing the cause.
5. Look at whether this belongs at the MCP boundary as a shared response-capping helper rather than inline in one handler: this repo already has a context-bloat-dump packet in its memory about the same disease in a different tool, so a per-tool fix will simply recur. If a shared helper is the right shape, build it and use it for kage_refresh; note in your claim which OTHER tools should adopt it, without changing them in this run.

HOW YOU'LL KNOW IT WORKED — put tests in a NEW file mcp/response-size.test.ts (NOT mcp/delegation.test.ts — every run appends to that file's end and merges have collided there repeatedly; this instruction has been ignored twice, so treat it as a hard requirement):
(a) a refresh response over a fixture with many stale packets returns at most N of them and states the true total;
(b) the truncation notice text actually appears in the returned payload;
(c) the explicit limit/full argument returns more than the default;
(d) a repo with few stale packets is unaffected — no notice, everything returned.
Also assert a hard ceiling: the default response for this repo's own fixture must serialize under some sane byte budget you pick and state.
