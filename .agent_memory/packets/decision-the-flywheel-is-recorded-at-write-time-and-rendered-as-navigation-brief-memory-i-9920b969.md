# The flywheel is recorded at write time and rendered as navigation: brief_memory_ids + runTag close the memory↔runs loop

> Memory and runs now cross link in both directions. Dispatch records brief memory ids on the TaskRecord mcp/delegation…

Memory and runs now cross-link in both directions. Dispatch records brief_memory_ids on the TaskRecord (mcp/delegation/contract.ts) — the post-judgment packet ids the brief actually carried; ratified packets carry runTag(runId), whose format lives in contract.ts so the writer (ratify.ts) and reader (memory-view.ts) cannot drift. memory-view.ts exposes packetFlywheel (born_from_run via the packet's kage-run: tag, used_by_runs via brief_memory_ids scan of listRuns) and packetsTaughtByRun (catalog tag filter) — prebuilt-index reads only, per the request-path law. The app renders it as navigation: packet overlay shows TAUGHT BY and BRIEFED INTO rows that jump to the run; a merged run's receipt shows RATIFIED INTO MEMORY rows that open the packet. Two rules for extenders: (1) createRun has TWO call sites — dispatchRun in dispatch.ts AND the POST /runs route in api.ts, which is the path the app's ⌘N/⌘⏎ actually takes; any new task-record field must be set in both or the live path silently lacks it (this repo's recurring drift disease — grep for callers before declaring done). (2) Runs dispatched before these fields have no edges; the surfaces render nothing for them, never a guess. Also: packetsTaughtByRun depends on the catalog being fresh — mergeRun's refreshProject covers it in practice.
Evidence: Full-loop test: seeded memory rode run 1's brief; its learned line was ratified on merge; run 2's brief carried the ratified packet; packetFlywheel resolved both directions. Verified live on a scratch daemon: clicked TAUGHT BY into the merged run, receipt showed RATIFIED INTO MEMORY.
Verified by: Commit 978b57c; 567/567 tests exit 0; browser walkthrough on port 3155.
