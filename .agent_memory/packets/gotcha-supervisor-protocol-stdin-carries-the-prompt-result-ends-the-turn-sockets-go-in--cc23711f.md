# Supervisor protocol: stdin carries the prompt, result ends the turn, sockets go in tmp

> Four protocol facts, each found only by running a real supervised agent rather than by reading docs. First, when the …

Four protocol facts, each found only by running a real supervised agent rather than by reading docs. First, when the input format is stream-json the prompt does NOT come from the -p argument: the agent reads it as a user message on stdin, so passing -p leaves it sitting silently forever. The symptom was baffling — the run only came alive when an unrelated steer arrived and accidentally became its prompt. Write the brief as the first user frame instead. Second, holding stdin open is exactly what makes a run steerable, but it also means the agent never exits on its own, so process death cannot be the turn-is-over signal; the result event is, and closing stdin on it lets the agent shut down cleanly into verification. Without this a finished run sits in running forever with its work already done. Third, unix domain socket paths are capped near 104 bytes, so a control socket placed inside a run directory under a long project path fails to bind, and because listen reports errors asynchronously the unhandled error event killed the supervisor outright and stranded the agent. Sockets now live in the system temp dir under a short hash of project plus run id, and the server has an error handler so a socket failure degrades to an unsteerable run rather than a dead one. Fourth, a supervisor must move the run through dispatched and running itself; the first version left every surface reporting briefed while an agent was actually working.
