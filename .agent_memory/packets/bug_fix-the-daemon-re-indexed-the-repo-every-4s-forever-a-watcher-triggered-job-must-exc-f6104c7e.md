# The daemon re-indexed the repo every 4s forever: a watcher-triggered job must exclude its own outputs

> The daemon's recursive project watcher triggered an in process indexProject on any change, but its exclusion list onl…

The daemon's recursive project watcher triggered an in-process indexProject on any change, but its exclusion list only covered .agent_memory/indexes, code_graph, and graph. indexProject writes .agent_memory/structural/** and the refresh handler rewrote daemon/status.json, so every index fired the watcher again: index → write → own event → index, every ~4 seconds, forever. Two long-lived daemons burned ~24 CPU-hours each; every cycle spawned up to 8 worker threads that each compile the full TypeScript library (a V8 profile of an "idle" daemon was 68% module compilation), and the parallel structural build parks the main thread in Atomics.wait, so requests stalled behind indexing. The fix in mcp/daemon.ts: exclude .agent_memory WHOLESALE from the refresh watcher (everything under it is Kage's own output — run ledgers were re-indexing the repo on every agent event), run indexing in a detached child (`kage index`) at boot and on refresh so the serving thread never blocks, debounce 3s, one child at a time with coalescing, and stamp last_indexed_at only when a child completes. Diagnosis recipe that worked: watch .agent_memory/daemon/status.json last_indexed_at on an untouched repo (advancing = loop), `sample <pid>` for the timer/regex shape, and `node --cpu-prof` whose per-THREAD profile files (same pid, tid 1..8) revealed disposable TypeScript-booting workers. Beware: BSD find -newermt '-15 seconds' silently matches nothing (relative syntax is GNU-only) — it produced a false "no loop" reading first.
Evidence: last_indexed_at advanced every ~4s on an idle repo before the fix; after: fresh daemon 0.0% CPU with 0.43s total CPU after boot index, last_indexed_at frozen across idle observation, and touching mcp/kernel.ts produced exactly one re-index then quiet.
Verified by: Commit 7608e91; 563/563 tests exit 0; before/after CPU measurements and a touch-one-file probe on the live daemon at port 3111.
