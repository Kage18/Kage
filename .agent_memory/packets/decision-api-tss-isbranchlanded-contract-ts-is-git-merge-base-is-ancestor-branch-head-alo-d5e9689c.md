# api.ts's isBranchLanded (contract.ts) is `git merge-base --is-ancestor branch HEAD` alo...

> api.ts's isBranchLanded contract.ts is git merge base is ancestor branch HEAD alone; once that has already returned t…

api.ts's isBranchLanded (contract.ts) is `git merge-base --is-ancestor branch HEAD` alone; once that has already returned true, `git merge-base branch HEAD` is mathematically ALWAYS equal to branch's own tip (the merge-base of an ancestor and its descendant is the ancestor itself) — so any 'does the branch have real commits' check that compares against merge-base(branch,HEAD) is unconditionally false for every landed branch, real commits or not. The correct, timing-independent signal is the branch's own reflog entry count (`git log -g --format=%H branch`): `git worktree add -b branch <start>` writes exactly one entry ('Created from ...') until a real commit adds another, and this is unaffected by merges happening elsewhere.

Learned while delivering: Kill the flicker. The app repaints wholesale on every poll tick and SSE notify, so the whole UI visibly flickers while runs stream - the owner called it out with 'AO doesn't do that', and AO doesn't because its renderer does keyed, targeted updates off a change feed. This run makes Kage's vanilla renderer do the same, without a framework.

THE DISCIPLINE TO IMPLEMENT, in mcp/delegation/app-client.ts:
1. REVISION-GATED RENDERS. Every polling refresh path compares the fetched payload against the last one (a cheap stable stringify hash per section - runs list, room, memory, goal rail) and SKIPS the DOM work entirely when unchanged. The SSE feed already carries seq - use it where it exists. State in your claim each render path you gated.
2. KEYED LIST REUSE. The runs list, board columns, sidebar fleet, and goal rail reuse existing DOM nodes by run/goal id: update changed text nodes and class names in place, append/remove only actual additions/removals, never rebuild the whole container. The h() pattern stays for CREATION; updates patch.
3. NEVER REBUILD WHAT THE USER IS TOUCHING. The composer, any focused input, an open modal, the terminal, and the detail pane's scroll position survive every refresh untouched. The detail pane re-renders only when ITS run's data changed (revision per run id), and even then patches sections rather than replacing the pane. Scroll position in Follow/transcript is preserved unless the user is pinned to bottom (keep the existing pin-to-bottom behaviour if present; if absent, add it - streaming output auto-follows only when already at bottom).
4. TIMERS TICK WITHOUT REPAINTS. Age labels ('17h', '2m ago') update via a single interval that patches ONLY those text nodes, not via full refreshes.
5. BATCHING. Multiple SSE notifies inside one frame coalesce (requestAnimationFrame or a 50ms trailing debounce - state which) into one gated render pass.
6. One perf note from the previous run's claim to fold in: branch_landed/worktree_adoptable are computed with git subprocess calls inside withActivity() on every /runs poll - that is server-side (mcp/delegation/api.ts, which you may touch ONLY for this): cache those two per run id keyed on the run's updated_at, so a poll of an unchanged run never shells out to git. State the cache shape in your claim.

HOW YOU PROVE IT - this is the acceptance bar: add a render-counter seam (a module-scope counter object incremented by each section's actual DOM-writing function, exposed for tests and readable from the console). Tests assert: two consecutive identical payloads produce exactly one section render; a payload changing one run's state re-renders only that section (counter for other sections unchanged); the age-ticker patches text without incrementing section render counters. Since the suite tests the page as a string plus vm-sandbox units, exercise the gating logic as pure functions (extract the revision-compare and the patch-vs-rebuild decision into testable functions) - do not hand-wave it as untestable.

TESTS - new file mcp/render-calm.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). The assertions above plus: composed page parses; narrow-layout gates green; the counter seam exists and is reachable from the page string.

CONSTRAINTS: app-client.ts/app-styles.ts/app-html.ts are TS TEMPLATE LITERALS - escapes DOUBLED, no backticks, no ${ }, never innerHTML. No framework, no virtual DOM library - this is disciplined vanilla DOM. Your files: those three, api.ts for item 6 only, and your new test file.
