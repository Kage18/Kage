# Kage desktop shell: zero-HTML Electron frame; ELECTRON_RUN_AS_NODE for CLI children; dock badge rides document.title

> The desktop app is shell/main.js — a ~140 line Electron main process containing zero HTML and zero renderer logic. It…

The desktop app is shell/main.js — a ~140-line Electron main process containing zero HTML and zero renderer logic. It reuses `kage app --no-open` to find/heal/start the daemon (never re-implements daemon management) and loads the daemon's /app page in a hiddenInset BrowserWindow (sandbox on, contextIsolation on, nodeIntegration off). Two non-obvious mechanics: (1) in the Electron main process, process.execPath is the Electron binary, not Node — spawning the Kage CLI with it launches a second app instance that hangs; child processes must set ELECTRON_RUN_AS_NODE=1. (2) The dock badge needs no IPC: the renderer sets document.title to "Kage · N" for N open decisions, and the shell parses page-title-updated — the title is the one channel a sandboxed page and its shell already share. ⌥K is a global summon/hide shortcut; window.open targets go to the system browser; KAGE_SHELL_SHOT=<path.png> makes the window capture itself after load so "the desktop app runs" is a checkable claim. Launch: cd shell && npx electron . --project <repo>. Electron is a devDependency of the private shell/ package only — the npm kage package keeps its 4 runtime deps.
Evidence: First launch failed with spawnSync Electron ETIMEDOUT (execPath trap), fixed by ELECTRON_RUN_AS_NODE; the relaunched app wrote its own window capture (kage-shell.png) showing the redesigned inbox over the Kage repo with the badge title "Kage · 2".
Verified by: Self-capture PNG from the running window; npm test --prefix mcp → 470 unit + 12 dogfood pass
