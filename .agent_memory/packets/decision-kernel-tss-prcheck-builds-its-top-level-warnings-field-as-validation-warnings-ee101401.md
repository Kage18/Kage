> kernel.ts's prCheck builds its top level warnings field as ...validation.warnings, ...ownWarnings — the same ~183 str…

kernel.ts's prCheck() builds its top-level `warnings` field as `[...validation.warnings, ...ownWarnings]` — the same ~183 strings were being echoed twice in kage_pr_check's MCP response (once under `validation.warnings`, once under the top-level `warnings`), independent of the missing array-capping; deduping requires a Set-difference against validation.warnings since the push order isn't guaranteed stable API.

Learned while delivering: Kage's MCP tools spend their caller's context window like it is free. It is the one resource an agent cannot get more of, and Kage's own agents are the customer.

THE MEASUREMENTS, taken this session while doing ordinary operator work:
- kage_supersede returned roughly 10,000 tokens for ONE supersede. It echoes the complete old packet AND the complete replacement packet, each with its full freshness.path_fingerprints array - every cited file, its sha256, its size, and a per-symbol sha256 for every symbol in it. The identical operation through the CLI (`kage supersede --packet <id> --replacement <id> --reason ...`) printed exactly two lines: "Superseded memory: <id>" and "Replacement: <id>". Same work, same result on disk, ~5000x the output.
- kage_pr_check returns 321,873 characters, about 80,000 tokens. A single call can consume a third of a context window.
- kage_refresh had this same disease and was already capped once (it used to dump ~150KB). So the pattern is known, and the fix was applied to one tool instead of to the surface.

WHY THIS IS A REAL DEFECT AND NOT HOUSEKEEPING. CLAUDE.md instructs every agent to call kage_context before edits, kage_learn on discoveries, kage_refresh after changes, and kage_pr_check before finishing. That is the mandated loop. If two of those calls can cost 90,000 tokens between them, the harness that exists to SAVE context is the largest single consumer of it, and the agent has less room for the actual task. Kage's own value receipt counts tokens saved by recall while the tool responses quietly spend more than they save.

THE PRINCIPLE TO APPLY, and please state it in the code as a comment so the next tool added inherits it: a CLI response is read by a human who scrolls and skims, so verbosity is nearly free. An MCP response is loaded into an agent's context whether it is needed or not, so verbosity is a direct tax on the task. These two surfaces must NOT share a response shape. Where the CLI prints a summary, the MCP tool should return the same summary - not the raw record the CLI happened to derive it from.

WHAT TO BUILD:
1. Audit every tool exported on the MCP surface (start from mcp/index.ts) and measure the actual response size of each on this repo. Put the measured table in your claim - that table is the deliverable as much as the fix is.
2. Cap them. For each tool decide what the caller genuinely needs to act, and return that. Structural detail like path_fingerprints, per-symbol hashes and full packet bodies should not be in a default response at all; if something needs them, it can ask for them explicitly or read the packet file. Say in your claim what you cut from each tool and why the remainder is sufficient.
3. When you truncate, SAY SO in the response, with the true total. Kage's honesty law is that an omission must be visible - a silently truncated list reads as a complete one. kage_context already does this correctly for withheld stale memories ("167 memory packet(s) excluded from recall") - follow that precedent exactly rather than inventing a second phrasing.
4. Do not solve this by making the CLI terse too. The CLI's verbosity is appropriate for a human reader; only the MCP surface is over-serving.
5. kage_pr_check at 321,873 chars is the worst offender and is a release blocker in its own right - fix that one even if you run short of room for the rest, and say plainly in your claim what you did not get to.

TESTS - new file mcp/tool-response-size.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: each capped tool's response stays under its budget on a repo with many packets; a truncated response states the true total; supersede returns ids and a short confirmation rather than whole packets; and the CLI output for the same operations is unchanged. Assert byte or token budgets as numbers so the test fails when a future change reinflates a response - that regression is the whole point. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS - no import.meta (TS1470), no top-level await. Do NOT touch mcp/delegation/brief.ts, preflight.ts, verify.ts, room-pty.ts, room-supervisor.ts, app-client.ts, app-html.ts, app-styles.ts, contract.ts, cli.ts or dispatch.ts - four other runs own diffs in those files and I intend to land them all.
VERIFY: npm run test --prefix mcp and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, reachability
