# In app-client.ts, `var x = {}` initializers only run when script execution actually rea...

> In app client.ts, var x = {} initializers only run when script execution actually reaches that line top to bottom; on…

In app-client.ts, `var x = {}` initializers only run when script execution actually reaches that line top-to-bottom; only function DECLARATIONS are fully hoisted. Since the file has real top-level DOM wiring (e.g. document.getElementById('errbar-x').onclick = ...) that throws in any DOM-less/partial test sandbox, any `var x = {}` declared AFTER that wiring line stays `undefined` (not `{}`) in such a sandbox even though it's reachable via hoisting as a name. New persistent client-state vars needed by sandboxed tests should be declared up near `var state = {...}` at the top of the file, not near their first use.

Learned while delivering: Fix two app-client defects found by operator dogfooding today, both in mcp/delegation/app-client.ts (+styles if needed). DEFECT 1 — the goal overlay never renders the due-wave banner or the Dispatch wave button: waveGateStatus(wave) reads goal.plan.waves[i].status.due (a boolean on the wave object), but the API ships the derived status as a TOP-LEVEL goal.wave_status array (withWaveStatus in api.ts) whose entries carry status as a STRING ('merged'|'executing'|'due'|'waiting'|'partial') — the two shapes never met, so the button has never rendered for any due wave. Reconcile: make the client read goal.wave_status[i] (map the string to due/waiting display), keep dueWaveIndex consistent, and add a test that composes the page and asserts a goal with wave_status [merged, due] renders the 'due now' line and a Dispatch wave button — this must not be able to silently regress again. Do not change the server shape (other clients read wave_status). DEFECT 2 — inlineAsk rows do not survive re-renders: the inline reason row (from the recent prompt() replacement) disappears when a background revision render rebuilds the run-detail overlay (reproduced: opened Reject reason row, waited ~15s, row vanished with typed state lost). Make open inline-ask state survive: hold it in client state keyed by run id + action and re-render it (with its typed text preserved) after any rebuild, or suppress rebuilding the affordance region while open — whichever matches the codebase's revision-gated render pattern; add a test if the harness allows asserting it. CONSTRAINTS: app files are TS template literals — doubled escapes, no backticks or dollar-brace, h() only, never innerHTML; composed-page parse test stays green; cite files individually.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, node --check <composed inline script>, reachability
