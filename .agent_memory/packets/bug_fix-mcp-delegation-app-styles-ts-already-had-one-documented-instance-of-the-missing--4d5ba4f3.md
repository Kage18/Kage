# mcp/delegation/app-styles.ts already had ONE documented instance of the 'missing min-wi...

> mcp/delegation/app styles.ts already had ONE documented instance of the 'missing min width:0 on a flex column ancesto…

mcp/delegation/app-styles.ts already had ONE documented instance of the 'missing min-width:0 on a flex-column ancestor lets an unbreakable-text descendant grow the whole chain' bug pattern, at #room-term-pane (with a comment explaining exactly why). #room-chat-pane, its sibling, was missing the same fix, and so were .view and .liverail/.liverow further up/down the same chain — worth checking for this same anti-pattern anywhere else long unbreakable text (branch names, activity labels) sits inside nested flex containers in this file.

Learned while delivering: Three topbar/app-shell defects, all confirmed by clean isolation in the live app during a full manual sweep.

1. THE SETTINGS BUTTON OPENS THE WRONG SURFACE. Clicking the topbar gear (title 'project settings') opens the NEW RUN modal. The Project-settings overlay EXISTS in the DOM (an .overlay whose content begins 'Project settings /Users/kushaljain/code/Kage') - the button is bound to the wrong opener after the topbar became icon buttons. Isolation: every overlay closed, gear clicked alone, New-run opened; reproduced twice. Fix the binding; add a page-string test that the gear handler references the settings opener and that no two topbar icon buttons share an opener.

2. TRANSIENT FLASH TEXT SURVIVES INTO A FRESH MODAL. A freshly opened New-run modal contained a .flash element reading 'dispatched' from a run dispatched an hour earlier. Fix the CLASS: any modal/overlay open clears stale flash content, and a flash auto-expires after a few seconds regardless (state your TTL). Test: the flash helper installs an expiry; the modal-open path clears it.

3. A STALE MUTATION TOKEN TURNS EVERY ACTION INTO A BARE 'refused'. When the daemon restarts while an app tab stays open, the tab's cached token is invalid, so every mutating action 401s and the UI shows only the word 'refused' - the Dispatch button in the modal did exactly this, with no explanation and no recovery. Reproduced live: dispatch from a pre-restart tab -> status 401 {error:'refused'}; after a page reload the same dispatch succeeds. Fix in the client: on a 401 from any mutating call, re-fetch the token by the same mechanism the page uses at boot and retry the request ONCE; if it still fails, show 'the daemon restarted - reload the page' instead of 'refused'. Find how the token reaches the page at boot and reuse that path - do not invent a second token channel. Server changes are out of scope; if the token is only embedded in the page HTML and no endpoint can re-serve it, say so in your claim and ship the honest message-only version. Test: the retry-once-then-explain logic as a pure function (inject fetch), covering recovered and still-refused paths.

CONSTRAINTS: mcp/delegation/app-client.ts (+ app-styles.ts if the flash expiry animates) are TS TEMPLATE LITERALS - escapes DOUBLED, no backticks, no ${ }, never innerHTML. Your files: those two plus extending mcp/sessions-ui.test.ts. CommonJS. Build and test ONLY inside your own worktree - never run npm, tsc or node against /Users/kushaljain/code/Kage. Rebase onto release-prep first if your base carries an inherited red. End with the kage-claim-v1 fence, citing files individually.
VERIFY: npm run test --prefix mcp (1040 unit + 12 dogfood green on main) and npm run build --prefix mcp with no 'error TS'. Run them for real and fill in the claim fence.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, node --check <composed inline script>, reachability
