> The runs ledger path .agent memory/reports/runs ledger.jsonl, via contract.ts's private runsLedgerPath has no exporte…

The runs ledger path (.agent_memory/reports/runs-ledger.jsonl, via contract.ts's private runsLedgerPath) has no exported reader — tests that need to assert ledger entries currently re-derive the path and parse JSONL by hand (see mcp/delegation.test.ts's own ledger assertions and now mcp/trust-gate.test.ts).

Learned while delivering: Gate autonomy on track record — but fix the metric first, because it currently over-counts and would hand out trust nobody earned.

PART 1, THE METRIC BUG (do this first, it is the foundation). computeTrackRecord in mcp/delegation/trackrecord.ts:27-30 counts a run as verified_first when 'claim.checks.length && claim.checks.every(check => check.result === "pass")'. That fold is TRUE when nothing was executed: in a repo with no configured test command the only checks that run are non-executing ones (diff-size kind 'diff', citations kind 'citation', reachability kind 'analysis') and they all pass, while claimVerdict in mcp/delegation/verify.ts labels the very same claim 'UNVERIFIED — nothing was executed'.
Measured on this repo: 31 runs count as verified_first, 1 of which executed nothing — mild here because this repo HAS a test command. In a fresh repo with none, the figure is 100%: every run scores a perfect record having proven nothing. That is precisely the situation where an autonomy gate matters most, so the gate would be at its most wrong exactly when it is most load-bearing.
FIX: verified_first must additionally require claimVerdict(claim).executed. This is the identical bug already fixed in maybeAutoMerge (mcp/delegation/ratify.ts) — the repo now has a memory packet stating the rule: 'every check passed' is NOT a synonym for 'verified', and any consequential gate must consult claimVerdict rather than re-deriving pass/fail by folding over checks. Do not re-derive it a third time; call claimVerdict.

PART 2, THE GATE. Use the corrected track record to decide how much a goal may do unattended, replacing the current all-or-nothing autonomy field behaviour:
- A goal with autonomy 'merge' should only auto-merge runs of a TYPE whose track record justifies it. Require a minimum sample before trusting anything — renderCurationLine in the same file already refuses to draw conclusions from thin data; follow that precedent and reuse its threshold rather than inventing a second one. Below the threshold, fall back to 'recommend' and SAY SO in the refusal reason, e.g. 'holding: only 2 merged bugfix runs on record, need N'.
- Above the threshold, gate on the corrected verified_first rate for that run type. Pick a defensible bar, state it in one line of comment, and make it a named constant — not a magic number buried in a condition.
- Every hold must be recorded with its reason on the run ledger, the same way maybeAutoMerge already records auto_merge_held. A silent refusal is indistinguishable from a bug.

ALSO, small and related: the previous run flagged that checkGoalAcceptsNewRun calls the now-reconciling readGoal, so a pre-dispatch check can persist a goal to 'done' as a side effect before deciding whether to accept a run into it. It is harmless today because checkGoalAcceptsNewRun never reads goal.state, but it is a latent trap. Either use a non-reconciling read there or add a comment stating why reconciliation is safe at that call site. Your choice — state which you picked and why.

TESTS — new file mcp/trust-gate.test.ts (the repo rule: new behaviour gets its own test file; mcp/delegation.test.ts is off-limits). Cover: a claim where nothing executed does NOT count toward verified_first; a run type below the sample threshold is held with a reason naming the shortfall; a run type above the threshold with a good rate auto-merges; above threshold with a poor rate is held; every hold writes a ledger entry. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS — no 'import.meta' (TS1470), no top-level await. Do not touch mcp/kernel.ts or mcp/cli.ts; another run is editing those. Do not run kage_refresh, kage_learn or kage_pr_check.
VERIFY: 'npm run test --prefix mcp' (683 green before your change — use the 'npm run test' form) and 'npm run build --prefix mcp' with no 'error TS'. Run them for real and fill in the claim fence.
