# Rejected approach: Fix project switching in the app: it fails with 'The daemon did not com

> A delegated attempt at "Fix project switching in the app: it fails with 'The daemon did not come up within 15s' whene…

A delegated attempt at "Fix project switching in the app: it fails with 'The daemon did not come up within 15s' whenever the target project has no daemon already running. Root cause, reproduced live: ensureAppDaemon in mcp/delegation/app-daemon.ts starts the target project's daemon on DEFAULT_APP_PORT 3111 — but the CURRENT project's daemon already occupies 3111, so the spawned child dies on EADDRINUSE and the 15s poll times out. Switching only ever worked when the target daemon happened to already be running on another port. Fix: when ensureAppDaemon must START a daemon, request an ephemeral port (--port 0), and make startDaemon in mcp/daemon.ts honor port 0 honestly — after server.listen() succeeds, read the ACTUAL bound port from server.address() and use that real port everywhere the requested port is used today: the status.json it writes (which is exactly what ensureAppDaemon polls), the guard's allowed origins (loopbackOrigins is currently computed from the requested port BEFORE listen — restructure so the guard context uses the actual port or is built after listen), the self-warm fetches, and the printed URL. An explicitly requested nonzero port that is busy must keep failing loudly — never silently move a port the user asked for. Add tests: mcp/app-daemon.test.ts already has a spawnFn seam — assert that the spawn args request port 0 when starting fresh; and add a daemon-side unit for the port-resolution helper if you extract one (a full startDaemon boot in the suite is too heavy — test the seam, not the world). Success = npm test fully green, and the fix must not change behavior when a healthy daemon already exists." was rejected.
