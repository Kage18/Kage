# writeRoomMcpConfig's output path was previously a single shared file (.agent_memory/run...

> writeRoomMcpConfig's output path was previously a single shared file .agent memory/runs/room mcp.json for every room …

writeRoomMcpConfig's output path was previously a single shared file (.agent_memory/runs/room-mcp.json) for every room thread even though each thread is a separate supervised process (mcp/delegation/room-supervisor.ts spawns one per thread) — making the config content thread-specific (KAGE_ROOM_SESSION) without also splitting the file per thread would create a write race between threads at room-open time, so the fix required per-thread config filenames too.

Learned while delivering: Make goal attachment IMPLICIT so the orchestrator loop cannot silently open. Observed live: the Room manager planned a goal correctly and said it would pass goal_id on kage_dispatch, then dispatched without it — attachRunToGoal never ran, the goal record kept zero waves, goalForRun returned null, and the event bridge (which only wakes the manager for goal-owned runs) could never fire. Capability and instruction were both present (dist had goal_id, built before the supervisor started), so the fix is structural, not a stronger instruction: the manager must not be ABLE to forget. BUILD: (1) Room sessions carry an active goal. In mcp/delegation/room-sessions.ts (read it first — sessions are keyed thread records) add an optional active_goal_id to the session record plus setActiveGoal(projectDir, sessionKey, goalId|null) and readActiveGoal(projectDir, sessionKey), atomic writes like the rest. (2) POST /goals in mcp/delegation/api.ts accepts an optional session (default the DEFAULT_SESSION key) and calls setActiveGoal for it, so a goal created from a room thread is owned by that thread; add POST /goals/:id/activate {session} and clear the active goal when a goal is abandoned or reaches done. (3) The MCP dispatch handler in mcp/index.ts (kage_dispatch, which already takes optional goal_id) runs inside the room MCP server with env KAGE_ROOM=1 and KAGE_PROJECT_DIR: when goal_id is ABSENT and KAGE_ROOM is set, resolve the active goal for the room session (default thread unless a session env/arg is available) and attach the run to it automatically; an explicit goal_id always wins; when neither exists, behave exactly as today. Say so in the tool description: runs dispatched from a room thread with an active goal attach to it automatically. (4) manager-prompt.ts: replace the pass goal_id on every dispatch instruction with the truth — runs you dispatch while a goal is active attach automatically; pass goal_id only to attach to a DIFFERENT goal. (5) Tests in mcp/delegation.test.ts (and api tests where routes changed): setActiveGoal/readActiveGoal round-trip; a dispatch with no goal_id under KAGE_ROOM attaches to the session active goal (drive the handler directly, do not spawn anything); an explicit goal_id overrides the active one; no active goal and no goal_id leaves the run unattached; abandoning a goal clears the active pointer. Keep the diff tight. Success = npm test fully green.
Verified by: npm test --prefix mcp, diff-size
