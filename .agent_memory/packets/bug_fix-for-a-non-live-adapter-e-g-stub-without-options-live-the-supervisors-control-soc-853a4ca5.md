# For a non-live adapter (e.g. stub without `options.live`), the supervisor's control soc...

> For a non live adapter e.g. stub without options.live , the supervisor's control socket 'stop' op only sets an in mem…

For a non-live adapter (e.g. stub without `options.live`), the supervisor's control socket 'stop' op only sets an in-memory flag (child is null, nothing to child.kill()) — the underlying process keeps running until its adapter.run() promise naturally resolves, so confirming/forcing exit via process-group signals is the ONLY way to actually stop such a run early, not an edge case.

Learned while delivering: Two run-control defects from a live incident this morning (run p2b-memory-leaves-...-d911): (1) STOP MUST STOP — the run record transitioned to 'stopped' (by 'manager', 06:58:25) but the detached supervisor and its agent child kept running for 14+ minutes of untracked work and spend until the operator killed them by hand; whatever path serves a manager/API stop must deliver the stop to the supervisor (its control socket exists — control.ts) and confirm process exit (poll pid a few seconds, then group-kill as the tree-kill machinery already does for check commands), recording 'stop delivered/confirmed' vs 'stop recorded but process unreachable — killed by sweep' honestly on the run; (2) MANAGER STOPS MUST CARRY A REASON — a stop by actor 'manager' landed with no recorded reason anywhere on the run (activity/history), leaving the operator to guess it was the overlap guard; require a reason string on the stop op and surface it in the run's activity and detail view what-now line. Add tests for both: a stopped run's supervisor pid must be gone within the confirmation window in the stub-adapter harness, and a manager stop without a reason is refused. Suite green; cite files individually.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, reachability
