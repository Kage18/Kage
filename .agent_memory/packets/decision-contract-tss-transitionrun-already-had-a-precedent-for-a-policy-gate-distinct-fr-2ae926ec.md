# contract.ts's transitionRun already had a precedent for a policy gate distinct from LEG...

> contract.ts's transitionRun already had a precedent for a policy gate distinct from LEGAL TRANSITIONS's pure structur…

contract.ts's transitionRun already had a precedent for a policy gate distinct from LEGAL_TRANSITIONS's pure structural legality: assertConcurrencyAllows for 'running'. I added assertReviewOptIn following the same pattern (called unconditionally inside transitionRun, before the concurrency check) so review_required is enforced at the kernel level for every caller, not only inside review.ts's own reviewRun — this is a sanctioned place for future per-run opt-in gates.

Learned while delivering: Wave 1 of the reviewer goal, RE-DISPATCHED because the first attempt merged EMPTY - its branch tip was an unrelated ancestor commit, so despite the record reading merged/VERIFIED 5/5 the tree contains none of it (no mcp/delegation/review.ts, no review states in contract.ts - verify this yourself first and say so in your claim; the two Wave-2 runs currently sitting blocked discovered it by checking the tree). BUILD THE KERNEL CONTRACT: (1) new OPT-IN run states ready->reviewing->approved|changes_requested in mcp/delegation/contract.ts LEGAL_TRANSITIONS - default OFF, existing ready->merged behavior unchanged unless review_required is set on the run; approved is required for merge ONLY when review was required; changes_requested allows back to running via the existing resume machinery. (2) mcp/delegation/review.ts: reviewRun modeled on ratify.ts - executes a reviewer agent via the existing Adapter abstraction (claude/codex/stub) against the claim + diff, parses a structured kage-review fence (verdict approved|changes_requested plus findings[]), never trusts free prose, writes review.json + evidence under the run. (3) The kage-review fence protocol documented in the brief constants alongside kage-claim-v1. (4) mergeRun (mcp/delegation/ratify.ts) refuses an unapproved run only when review_required. NOTE landed since the original brief: the mcp-tool surface for reviews just merged (kage_review tool in mcp/index.ts + manager prompt) - read it and make your kernel contract match ITS expectations so the two halves join; if they cannot, say exactly why in your claim. ALSO: your run must land a NON-EMPTY diff - the failure mode you are replacing merged nothing; if your claim-time diff is empty, say so and fail loudly rather than claim. TESTS - new file mcp/review-contract.test.ts (delegation.test.ts is off-limits): the opt-in states are legal only under review_required; default path unchanged; reviewRun with the scripted stub produces approved and changes_requested verdicts from fixture fences; merge refuses unapproved only when required; malformed fence degrades to protocol_ok=false, never a crash. CONSTRAINTS: CommonJS, no import.meta, no top-level await. Files: contract.ts, review.ts (new), ratify.ts, your test file; do NOT touch index.ts/manager-prompt.ts (just merged), goal.ts, api.ts, app files. Build and test ONLY in your worktree - never against /Users/kushaljain/code/Kage. Rebase onto release-prep first if your base carries an inherited red. End with the kage-claim-v1 fence, citing files individually.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, reachability
