# A run's build can escape its worktree into the main checkout's dist, and a supervisor spawned in that window keeps running the leaked code

> Worktree isolation is a convention, not an enforced boundary. A hired agent working in .agent memory/worktrees/<run i…

Worktree isolation is a convention, not an enforced boundary. A hired agent working in .agent_memory/worktrees/<run-id> compiled its TypeScript into the MAIN checkout's gitignored mcp/dist, which is what the daemon and every newly spawned supervisor load — so the running system briefly executed unreviewed code from an in-flight run. Source did not leak (git status on mcp/ stayed clean); only the build output did. Two things make this worse than it first looks. First, rebuilding mcp/dist from committed source fixes the FILES but not already-running processes: a supervisor spawned during the contamination window keeps the leaked code in memory for the rest of its life, and one of them went on to stop a run and write a stop note advertising `kage resume-run`, a command that does not exist in the shipped build. Second, dispatchDetached spawns the supervisor with stdio: "ignore" (mcp/delegation/dispatch.ts around line 383), so there is no log anywhere when a supervisor dies or misbehaves. Note what is NOT affected: command checks receive the worktree explicitly via runCommandCheck(projectDir, runId, worktreeDir, check), and evidence logs record the worktree as cwd, so verification itself tests the right tree. When briefing an agent, do not ask it to act on records that live in the main repo's .agent_memory without telling it explicitly that reading there is fine and building or writing there is not.
Evidence: Verified two independent ways. (1) `worktree: handle.path` and `worktree: workspace` existed only in the run's worktree dispatch.ts/supervisor.ts, never in the main checkout's source, yet both appeared compiled in the main checkout's mcp/dist; git log -S found the line in no commit. (2) The string "orphan" matched 8 of the worktree's .ts files, 5 of the main checkout's, and 8 of the main dist's .js files — the main build matched the worktree, not its own source. Rebuilt mcp/dist from committed source and both markers went to 0. Afterwards `grep -rl resume-run mcp/dist` found nothing while a supervisor spawned earlier still emitted a stop note naming that command, and `node mcp/dist/cli.js resume-run ...` printed the CLI help.
Verified by: Two-marker source-vs-dist comparison, git log -S, rebuild-and-recheck, and a live CLI invocation of the advertised command

## Verification

(1) `worktree: handle.path` and `worktree: workspace` existed only in the run's worktree dispatch.ts/supervisor.ts, never in the main checkout's source, yet both appeared compiled in the main checkout's mcp/dist; git log -S found the line in no commit. (2) The string "orphan" matched 8 of the worktree's .ts files, 5 of the main checkout's, and 8 of the main dist's .js files — the main build matched the worktree, not its own source. Rebuilt mcp/dist from committed source and both markers went to 0. Afterwards `grep -rl resume-run mcp/dist` found nothing while a supervisor spawned earlier still emitted a stop note naming that command, and `node mcp/dist/cli.js resume-run ...` printed the CLI help.
