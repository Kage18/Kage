# The manager event bridge drops every event fired while the manager is busy — which is exactly when a dispatched wave changes state

> First live orchestration 2026 08 18 proved the planning and cleanup layers and disproved the wake layer. What worked,…

First live orchestration (2026-08-18) proved the planning and cleanup layers and disproved the wake layer. What worked, unaided: the manager compiled per-intent briefs before proposing, warned that both runs' predicted touch sets shared mcp/delegation.test.ts, asked approval, dispatched the wave, then — on its own — STOPPED a run that had landed in an empty sandbox and REJECTED it with an accurate reason (duplicate of the sibling that got a proper worktree). Run state history shows `stopped | by: manager | stopped from the room` followed by a rejection whose reason the manager wrote. What did NOT work: no `[kage event]` frame ever appears in .agent_memory/room/history.json, so the kernel never woke it — the cleanup happened inside its own still-running turn. Root cause: notifyManagerOfRunEvent in mcp/delegation/room-supervisor.ts sends through askRoomSupervisor's op:ask path, which requires busy===false, and the O1 implementation deliberately treats a busy manager as an accepted drop. But a wave's runs change state immediately after the very turn that dispatched them — the manager is still busy — so the events that matter most are exactly the ones discarded. A wake mechanism that only reaches an idle listener cannot orchestrate. Fix direction: make goal events DURABLE, not fire-and-forget — append them to a per-goal pending-events log and drain it into the manager the moment it goes idle (or inject a user frame straight into the held stdin, which the supervisor already owns, instead of routing through the idle-only ask protocol). Related: mcp/delegation/goal.ts, the Goal record's wave run_ids are what goalForRun and the bridge key on.
Evidence: Zero turns containing "[kage event]" in the room history after a goal-owned run went blocked; the same run's state_history shows the manager stopping it from inside its own turn; O1's own claim documented the busy-drop behavior.
Verified by: Live orchestration of goal harden-the-verification-loop-make-the-su-260818-d82d on the merged Goals build (603/603 green).
