# A rebased-away red is a distinct failure shape from a self-caused one: a run's own work...

> A rebased away red is a distinct failure shape from a self caused one: a run's own worktree can show a failing test t…

A rebased-away red is a distinct failure shape from a self-caused one: a run's own worktree can show a failing test that traces to its BASE commit, not its diff, when a parallel run fixes a shared guard (here, a doc-truth-maintenance run correcting sessions-doc.test.ts/store-doc.test.ts's assertions after another parallel run landed the code those docs were behind on) and merges before this run's base. The tell is that `git diff <base> -- <the failing test's own file>` is empty and the failure is a doc/guard assertion, not a runtime assertion on files the run touched — that's a signal to check whether a fresher base already fixes it (rebase) rather than trying to fix or explain away a red that isn't the run's to own. This will recur for any run whose window overlaps a doc-guard-fixing run; worth carrying into future briefs so a red test doesn't get misdiagnosed as a self-inflicted regression.

Learned while delivering: Three meter-and-guard integrity defects, each observed live today with evidence on disk. They share one theme: a check or meter that reports in the reassuring direction when its measurement window is wrong. Fix all three.

1. REVERIFY'S DIFF-SIZE CHECK PASSES VACUOUSLY ON COMMITTED WORKTREES. Runs commit their work at claim time (commitWorktree), so by the time `kage reverify` re-runs the diff-size check the working tree is clean and the check records literally '0 file(s), 0 changed line(s), budget 800' - see .agent_memory/runs/budgets-become-a-circuit-breaker-not-a-t-260820-e70a/evidence/diff-size.log, written while that run's own claim admitted ~1,400 changed lines. Fix: the diff measurement must be merge-base..HEAD PLUS uncommitted changes, wherever the diff check computes its numbers (find the single place; verify.ts's runDiffCheck or its data source) - so a committed diff still counts and an uncommitted one still counts, on every path that runs checks (claim-time, reverify, adopt). Regression test: a worktree whose change is fully committed must report its real line count under reverify, not zero.

2. SPEND RESETS ON RESUME. recordSpend overwrites spend with the agent CLI's latest usage report, and a resumed run starts a FRESH agent session whose cumulative usage starts at zero - so a run that had spent $30.96 before its stop showed $2.95 after resuming (both figures observed on budgets-become-...-e70a today). The meter under-counts exactly the expensive runs. Fix: accumulate across sessions - keep a per-session ledger keyed by agent_session_id (the run record already carries the current one, and it now lands mid-stream) or a sealed-spend baseline that each new session's usage adds onto; state in your claim which design you chose and why it cannot double-count a session that reports usage multiple times (the CLI reports cumulative-per-session on every tick - the last figure per session is the truth for that session). Regression test: stop, resume with a new session id, report smaller usage - total spend must be prior + new, never just new.

3. THE WORKTREE-BOUNDARY GUARD ATTRIBUTES BY DRIFT, NOT BY CONTENT. It fired today on run m1-... because mcp/dist in the MAIN checkout changed during the run's lifetime - but that change was the OPERATOR's own legitimate post-merge rebuild, not the run's escape (evidence: .agent_memory/runs/m1-of-the-memory-store-build-the-storeba-260820-3ff8/evidence/worktree-boundary.log lists dist files from a merge the run never touched). A guard that cries wolf on every operator rebuild will get ignored, which is worse than no guard. Fix: attribute by CONTENT - flag only when the main checkout's changed build output contains code traceable to THIS run's worktree (e.g. identifiers/strings present in the run's new or modified source but absent from the main checkout's committed source - the exact two-marker method that caught the real leak on 2026-08-19). Both cases need tests: the operator-rebuild scenario must NOT flag; a planted leak (a marker string from the worktree's source appearing in main dist) MUST flag.

TESTS - new file mcp/meter-integrity.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). The three regression tests above plus: the diff fix counts committed+uncommitted together when both exist. Name in your claim which test fails if the change is reverted.
