# Terminal mode: four stacked bugs behind one blank pane, and the debugging lesson

> Kage's Terminal mode real interactive claude in a node pty, rendered with xterm.js showed a blank pane for a long tim…

Kage's Terminal mode (real interactive `claude` in a node-pty, rendered with xterm.js) showed a blank pane for a long time. It was FOUR independent bugs stacked, each masking the next, and an early wrong hypothesis ("my sandbox blocks pty allocation") that survived far too long because every follow-up probe was a variation of the same experiment rather than a test that could falsify it. The tell was ignored for several turns: the failure printed `posix_spawnp failed.` followed by Kage's OWN CLI error formatting — proof the process reached our code and node-pty threw, which a wholesale sandbox block could never produce. Lesson: when a hypothesis explains a failure, immediately try to DISPROVE it; re-running variants that confirm it is not evidence. (1) node-pty's prebuilt `spawn-helper` lost its execute bit during npm extraction (`-rw-r--r--`). On Unix node-pty's spawn() execs that helper, so every spawn died with the opaque `posix_spawnp failed.` — no file named, no permission mentioned. Fixed by ensureSpawnHelperExecutable() in room-pty.ts, which chmods it in-process before the first spawn (idempotent, resolves via require.resolve so it follows the package anywhere). Note a from-source `npm rebuild node-pty` restores the bit, which is why an early throwaway rebuild in /tmp "worked" while the real copy in mcp/ stayed broken. (2) Missing scrollback at the supervisor: a terminal's visible screen is CUMULATIVE, so broadcasting only post-connect bytes meant any client attaching after the banner printed saw nothing. Added a 256KB rolling buffer replayed on attach. (3) The same bug one layer up: the daemon attaches to the supervisor ONCE and lives for hours fanning out to N browser tabs over SSE, so it consumed the replay at attach time and later tabs got nothing. Added PtyState.scrollback plus GET /room/pty/snapshot, which the client paints on open. (4) xterm sizing/painting: as a flex item the terminal host needs flex:1 + min-width:0 or fit() measures a ~zero box and picks cols=2 (session renders one char per line); and a refresh() issued while xterm is still initializing (open + first write + resize in one burst) is silently a no-op, so repaintTerminal() runs a 60/250/600ms ladder. CRITICAL environment gotcha that wasted many turns: the preview browser used for verification does NOT run requestAnimationFrame (measured: rAF fired 0 times in 3s while setTimeout fired 13). xterm paints on rAF, so the buffer was always correct while the screen stayed blank, and only a manual console call — which forces a frame via CDP — painted it. Terminal creation was therefore moved off requestAnimationFrame onto setTimeout, which also fixes a REAL user-facing bug: browsers throttle rAF in background tabs, so an rAF-gated creation means the terminal silently never exists for a user who opens it in a backgrounded tab. Verified working in a real Electron window (rAF runs normally there). One more process trap: the daemon compiles app-html into memory at startup, so rebuilding does NOT change what a running daemon serves — several "still broken" observations were actually stale HTML; always restart the daemon after a frontend rebuild.
Evidence: Terminal mode captured working in a real Electron window: Claude Code v2.1.233 banner, Sonnet 5 · Claude Max, ~/code/Kage, live input prompt — fully automatic with no manual console calls. State assertion at capture time: roomMode=terminal, paneDisplay=flex, cols=174, 8 non-empty buffer lines. Regression tests added for the spawn-helper execute bit (deliberately chmods it away, asserts repair) and for scrollback replay to a late-attaching client.
Verified by: npm test --prefix mcp → 493 unit + 12 dogfood pass; Electron window self-capture with asserted DOM/terminal state
