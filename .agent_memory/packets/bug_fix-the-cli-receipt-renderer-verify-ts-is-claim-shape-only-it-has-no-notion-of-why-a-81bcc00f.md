# The CLI receipt renderer (verify.ts) is claim-shape-only — it has no notion of *why* a ...

> The CLI receipt renderer verify.ts is claim shape only — it has no notion of why a diff is empty — so any 'lead with …

The CLI receipt renderer (verify.ts) is claim-shape-only — it has no notion of *why* a diff is empty — so any 'lead with X when diff is empty' requirement has to be threaded through the claim itself (rewriting its statement) rather than through the renderer, or it risks conflating a genuinely-empty no-change conclusion with an empty diff caused by a failing/incomplete check.

Learned while delivering: Two verification-honesty guards, closing the two classes that let a content-empty merge read VERIFIED and that have now failed four claims on formatting. Both reproduced live; the empty-merge one cost a full feature.

1. MERGE REFUSES AN EMPTY FEATURE DIFF. Yesterday a run merged reading VERIFIED 5/5 while its branch tip sat AT the merge-base - zero commits, zero content. Every check passed honestly (the suite was green, an empty diff is trivially under any cap), the merge fast-forwarded nothing, merge cleanup deleted the worktree holding the only uncommitted copy, and the goal record said 'wave 1 merged' over nothing for two days until downstream agents checked the tree. Fix in mcp/delegation/ratify.ts's mergeRun: before merging, count commits merge-base..branch-tip (the same zero-commit signal recovery.ts's branch_landed check uses - reuse, do not duplicate); when zero AND the run's type is feature/bugfix/refactor/migration, REFUSE with a message naming the branch tip and what it means ('this branch adds no commits - the work was never committed; the worktree may still hold it, do not merge-and-delete'). chore/investigation may merge empty (a legitimate no-change conclusion) but the receipt and the merge output must then LEAD with 'EMPTY DIFF' so a human cannot miss it. Never delete a worktree on a REFUSED merge.
2. SLASH-JOINED CITATION ENUMERATIONS SPLIT INSTEAD OF FAIL. Four claims have now failed citations on tokens like 'contract.ts/ratify.ts/review.ts/review-contract.test.ts' - filenames an agent joined with slashes, read as one path. Fix in mcp/delegation/verify.ts's citation extraction: when a formally-cited token fails to resolve AND splitting it on '/' yields two or more segments that EACH independently resolve as files (directly or by the existing unique-suffix rule), treat it as an enumeration of those files rather than one missing path. A token where any segment does not resolve keeps failing exactly as today - the guard's teeth stay (a genuinely invented path still fails; 'src/utils' style real directory paths are unaffected because they resolve as-is before splitting is ever tried).

TESTS - new file mcp/merge-honesty.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: a feature run whose branch adds zero commits is REFUSED at merge with the worktree left intact; a chore run merging empty succeeds with EMPTY DIFF leading its output; a normal non-empty feature merge is unchanged; the citation splitter accepts the exact four-file token above when all segments exist, still fails it when one segment is invented, and leaves single real paths and real directory-joined paths untouched. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS - no import.meta, no top-level await. Your files: mcp/delegation/ratify.ts, mcp/delegation/verify.ts, and your new test file; reuse recovery.ts's zero-commit helper by import, do not modify recovery.ts. Do NOT touch contract.ts, review.ts (just landed), adapters/, app files, index.ts (two other runs own their areas right now). Build and test ONLY inside your own worktree - never run npm, tsc or node against /Users/kushaljain/code/Kage. Rebase onto release-prep first if your base carries an inherited red. End with the kage-claim-v1 fence, citing files individually - never slash-joined.
