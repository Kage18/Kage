# In this codebase's TS formatting style, top-level declarations always start at column 0...

> In this codebase's TS formatting style, top level declarations always start at column 0 and their matching close is a…

In this codebase's TS formatting style, top-level declarations always start at column 0 and their matching close is also at column 0, which makes a simple brace-depth counter (not a real parser) a reliable way to find top-level declaration boundaries -- except for app-client.ts/app-styles.ts/app-html.ts, which are each one giant unclosed-template-literal-to-EOF by their own documented invariant and need a special case (detect an odd, unclosed backtick count on a `const NAME = \`` line and treat the rest of the file as one scope).

Learned while delivering: Build a reachability check: stop runs from landing code that exists, compiles, passes tests, and is never reached from anything real.

WHY — this is the single most repeated defect class in this repo. Seven instances found, all shipped green:
- transitionGoal (mcp/delegation/goal.ts): its ONLY caller is abandonGoal, so a goal can never reach 'executing' or 'done'.
- supervisor_pid (mcp/delegation/contract.ts): READ by liveState, WRITTEN only by supervisor.ts — never on the CLI dispatch path, so the fix that reads it is inert where it matters most.
- goal attachment: existed, but ran AFTER the run finished, so goalForRun was null for the run's whole life.
- reapRun, looksLikeGitRepo, resolveWorkspaceKind: all shipped with zero callers.
- LEGAL_TRANSITIONS allows failed -> running with a comment explaining why, but no command anywhere performs it.
In every case tests passed, because the test called the new symbol DIRECTLY or patched the field by hand (the liveState test literally does patchRun(project, id, { supervisor_pid: ... })). Nothing ever asked whether the code was reachable from a real entry point. That is the hole to close.

WHAT TO BUILD — a new module mcp/delegation/reachability.ts:

1. Export findOrphans(projectDir: string, changedFiles: string[]): OrphanFinding[].
   An OrphanFinding names the symbol or field, its file and line, and which of the two rules it broke.

2. RULE A — orphan export. For each symbol EXPORTED by a changed file, resolve every reference to it across mcp/**/*.ts. If its only references are its own definition and *.test.ts files, it is an orphan: nothing in production reaches it. Report it.

3. RULE B — write-only or read-only field. For each field added to an interface in a changed file (TaskRecord, GoalRecord and friends), find its readers and its writers across non-test sources. A field with readers but no non-test writer (the supervisor_pid case) or with writers but no reader is reported. This rule is what would have caught the inert liveness fix.

4. Reachability must be judged from REAL entry points, not from 'something imports it'. Treat these as roots: mcp/cli.ts, mcp/index.ts (the MCP tool surface), mcp/daemon.ts and mcp/delegation/api.ts (HTTP routes), and any bin entry in mcp/package.json. A symbol only reachable from another orphan is still an orphan, so compute this transitively from the roots rather than checking one hop.

5. ESCAPE HATCH, mandatory: a symbol is exempt when the line above it carries the comment marker '// reachability: <reason>'. Some exports are deliberate public API. The marker must require a written reason — an unexplained exemption is how this rot returns. Honour it, and cover it with a test.

6. WIRE IT AS A KERNEL-EXECUTED CHECK on every run, exactly the way the static checks that just landed in mcp/delegation/static-checks.ts are wired — read that file first and follow its pattern, including how it writes evidence through verify.ts's writeEvidence and how it appears in the receipt as a check run by Kage rather than by the agent. IMPORTANT: static-checks.ts had to be wired into BOTH dispatch.ts's executeRun (foreground runs) and supervisor.ts's superviseRun (detached runs) because those two call sites hand-roll claim assembly independently and have drifted before. Wire yours into both, and add a test asserting both call sites run it — otherwise this task ships its own orphan, which would be a genuinely embarrassing outcome for this particular feature.

7. A finding must NOT hard-fail the run. Report orphans as a distinct, visible check result with the symbol names and the rule each broke, so the operator sees them in the receipt and decides. Getting the signal in front of a human is the goal; a false positive that blocks a merge would get this check disabled within a week.

TESTS — put them in a NEW file mcp/reachability.test.ts, NOT in mcp/delegation.test.ts. That file is a merge-conflict hotspot because every run appends to its end; three merges in a row have collided there today. Cover: an export referenced only by a test is reported; an export reachable from cli.ts is not; an export reachable only via another orphan IS reported (the transitive case); a field with a reader and no non-test writer is reported; the '// reachability: <reason>' marker exempts a symbol; an unexplained marker does not; both executeRun and superviseRun invoke the check.

SELF-TEST, do this before you claim: run your own findOrphans against this repo's current mcp/delegation/goal.ts and confirm it reports transitionGoal. If it does not, the check does not work — say so plainly rather than claiming success.

CONSTRAINTS: this project compiles to CommonJS — no 'import.meta' (TS1470), no top-level await. Do not touch mcp/delegation/adapters/index.ts or mcp/delegation/brief.ts; another run is editing them right now. Do not run kage_refresh, kage_learn or kage_pr_check; those are the operator's job. Run 'npm test --prefix mcp' (636 tests green before your change) and 'npm run build --prefix mcp' (no 'error TS'), and state honestly in your claim if any command was denied to you.
