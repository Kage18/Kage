# A competing test runner breaks this suite; a busy background daemon does not

> Measured 2026 08 05, correcting an overstatement. The full suite passed 1980/1980 while a runaway Kage daemon PID 194…

Measured 2026-08-05, correcting an overstatement. The full suite passed 1980/1980 while a runaway Kage daemon (PID 1946) was consuming 462% CPU — 4.6 cores — on the same machine, having accumulated 119 hours of CPU time. So a background daemon under heavy load does NOT break the suite. What did break it was a leftover shell waiter re-spawning 'node --test' every 10 seconds; its exit condition never matched, so it ran indefinitely and blew the wall-clock budgets in three latency-sensitive adapter tests, which read exactly like a product regression. Two consequences. First, diagnose by process class, not by load: 'pgrep -fl "node --test"' before trusting any timing result, because a competing TEST RUNNER contends for the same fixed ports, temp dirs and event-loop-sensitive assertions in a way generic CPU load does not. Second, that waiter also defeats any 'wait for the machine to go quiet' guard built on pgrep for node --test, since the waiter is itself the thing being waited on. The three adapter tests that failed are now immune regardless: they pass an explicit FUNCTIONAL_TIMEOUT_MS instead of inheriting the production 150ms budget.
Evidence: ps -o pcpu= on PID 1946 read 462.9 with TIME 7143:01 during the same window in which 'npm test' exited 0 with 1980/1980. The three failures occurred only while the respawn loop was live and did not recur after TaskStop killed it, including on a run that started at load average 18.20.
Verified by: claude-opus-5
