# Delegation web app: one origin, token injected at serve time, events as notifications

> The delegation web app is a single self contained HTML string emitted from mcp/delegation/app html.ts and served by t…

The delegation web app is a single self-contained HTML string emitted from mcp/delegation/app-html.ts and served by the guarded daemon at /app on the same origin as the run API (mcp/delegation/api.ts). The daemon injects the 0600 mutation token by replacing __KAGE_TOKEN__ at serve time — safe because the guard only serves loopback Host + same-origin requests. SSE (/runs/events) carries only {run_id, seq}; clients re-read /runs; API mutations call feed.notify() directly so app-driven changes never wait on fs.watch. POST /runs accepts hold:true to skip the detached supervisor in tests. The complete surface now also includes GET /runs/:id/diff (branch diff vs merge-base plus uncommitted worktree changes, unified format colored client-side by prefix), GET /runs/:id/raw (the transcript verbatim — the genuine escape hatch), per-run activity from readActivity attached only to in-flight runs, and Web Notifications fired only when a run newly becomes needs_you and the page is not both visible and focused. Verified end to end: a real stub dispatch reached VERIFIED 3/3, was merged from the app's Merge & ratify button, and the pending learning packet on the run branch flipped to x-kage-status approved on main.
Evidence: 15 tests in mcp/delegation-api.test.ts including diff/raw against a full stub dispatch and a client-script parse gate; live browser session: merge from the UI produced commits "kage: merge …" + "kage: ratify 1 learning(s)" and the packet status flipped pending→approved.
Verified by: npm test --prefix mcp → 470 unit + 12 dogfood pass; live daemon + browser walkthrough on the seeded demo repo
