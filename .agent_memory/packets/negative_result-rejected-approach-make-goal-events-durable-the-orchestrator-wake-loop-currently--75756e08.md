# Rejected approach: Make goal events DURABLE — the orchestrator wake-loop currently drops e

> A delegated attempt at "Make goal events DURABLE — the orchestrator wake loop currently drops every event that matter…

A delegated attempt at "Make goal events DURABLE — the orchestrator wake-loop currently drops every event that matters. Observed live: notifyManagerOfRunEvent in mcp/delegation/room-supervisor.ts sends through askRoomSupervisor op:ask, which requires busy===false, and a busy manager is treated as an accepted drop. But a wave changes state immediately after the very turn that dispatched it, while the manager is still busy — so zero [kage event] frames ever reached it during a real orchestration (verified: no such turns in .agent_memory/room/history.json), and the manager only acted because it happened to still be inside its own turn. A wake mechanism that only reaches an idle listener cannot orchestrate. FIX: (1) PENDING QUEUE — add a per-goal durable pending-events log (JSONL under the goal dir; goal.ts owns paths and helpers: appendGoalEvent, readPendingGoalEvents, markGoalEventsDelivered, atomic rewrite like the steer log which already models queued/delivered). notifyManagerOfRunEvent ALWAYS appends the event first, then attempts immediate delivery; a successful delivery marks those events delivered, a busy or dead manager simply leaves them pending — never a silent drop. (2) DRAIN ON IDLE — when the room supervisor finishes a turn and goes idle (find the point in room-supervisor.ts where busy flips false / the turn resolves), drain any pending goal events for goals whose active session is this room thread: coalesce them into ONE compact frame (group by run, keep only the latest state per run, cap the list and say how many were coalesced) and deliver it as the next user frame into the held session, then mark delivered. Rate-limit as today so a storm cannot flood the manager. (3) Keep the existing rule that only goal-owned runs generate events, and never wake the manager for human-only runs. TESTS in mcp/delegation.test.ts using the existing room-supervisor seams (fake held session recording frames, plus the goal record helpers): an event fired while the manager is busy is PENDING not lost; going idle drains it as exactly one coalesced frame and marks the events delivered; two state changes for the same run coalesce to the latest; a run with no goal produces no event and no frame; a dead manager leaves events pending for the next live one. Put the new tests in a clearly separated block near the end of the file. Success = npm test fully green." was rejected.

Reason: Never produced a transcript or a workspace — agent process gone immediately after dispatch, a casualty of five concurrent runs contending for git locks and machine resources. Nothing to salvage; the durable-events work is unchanged in value and will be redispatched once concurrency is back to 3 and the git-retry fix has landed.
