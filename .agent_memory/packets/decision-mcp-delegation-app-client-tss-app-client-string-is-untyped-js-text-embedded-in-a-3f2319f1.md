# mcp/delegation/app-client.ts's APP_CLIENT string is untyped JS text embedded in a TS te...

> mcp/delegation/app client.ts's APP CLIENT string is untyped JS text embedded in a TS template literal — tsc only chec…

mcp/delegation/app-client.ts's APP_CLIENT string is untyped JS text embedded in a TS template literal — tsc only checks the outer .ts file, never the JS-in-string contents (only a runtime parse-gate test does), so referencing a not-yet-existent field like wave.status on a TS-typed GoalRecord causes no compile error at all; safety there comes only from defensive runtime checks (typeof wave.status.due === "boolean"), not the type system.

Learned while delivering: Redesign the goal detail overlay - the owner reviewed it with a screenshot and called it 'not a good view', and every criticism is structural. What it does wrong today: (1) the FULL INTENT opens the modal as a wall of large text - the least actionable content gets 40% of the height before any structure; (2) wave 2 renders as a giant empty void with centered 'no runs yet' - even though the goal record CONTAINS wave 2's planned run intents and the reason nothing is running; (3) no goal-level summary - no progress, no spend, no dates; (4) no actions beyond Close/Abandon; (5) the intent block's typography does not match the app (oversized serif-looking body vs the app's sans/mono system).

THE REDESIGN (mcp/delegation/app-client.ts + app-styles.ts):
1. HEADER: first sentence of the intent as the title (one line, ellipsis), then one chip row: state, autonomy, 'wave N of M', total spend, age. Close stays top-right. The FULL intent collapses behind the existing 'Full intent' expander pattern from run detail - reuse it, same classes.
2. AUTONOMY explainer stays one quiet line under the chips (the current 'Recommend: ...' copy is good - keep it).
3. WAVES as the body, each a compact section: 'WAVE n' header + ITS STATUS from the API's new per-wave status field (the goal-continuity backend run landing in parallel adds wave statuses to the goal responses - consume that field; if it is absent at runtime, derive NOTHING and show only what exists today, so the two runs land independently). Attached runs render as the standard row: display_name, state dot, verdict chip, spend, click opens the run detail. A wave with NO runs is never a void: render its PLANNED run intents (first line each, from plan.waves[n].runs) as muted rows labelled 'planned', plus one status line - 'waiting - dispatches after wave N-1 merges' or, when due, 'due now - wave N-1 merged' WITH a 'Dispatch wave' button calling POST /goals/:id/dispatch-wave (same parallel backend; on refusal show the API's message verbatim; hide the button when the endpoint 404s so this run stands alone).
4. Abandon moves to the overlay footer with its existing confirm; goal CARD (board/list) gains a 'wave N due' amber chip when any wave status is due, replacing nothing else on the card.
5. Typography: everything through the app's existing tokens - sans for prose at the standard body size, mono for chips/ids; no oversized text block anywhere.

TESTS - extend mcp/sessions-ui.test.ts (the goal-overlay markup assertions live there): header renders first-sentence title + chip row; full intent is behind the expander; an empty wave renders planned rows + status line, never the bare 'no runs yet' void; the dispatch-wave button appears only for a due wave with the endpoint present; composed page parses; narrow gates green. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: app-client.ts/app-styles.ts are TS TEMPLATE LITERALS - escapes DOUBLED, no backticks, no ${ }, never innerHTML, DOM via h(). Your files: those two + mcp/sessions-ui.test.ts. Do NOT touch mcp/delegation/goal.ts, api.ts, manager-prompt.ts, room-pty.ts, room-supervisor.ts - a parallel run owns them. CommonJS. Build and test ONLY inside your own worktree - never run npm, tsc or node against /Users/kushaljain/code/Kage. Rebase onto release-prep first if your base carries an inherited red. End with the kage-claim-v1 fence, citing files individually.
