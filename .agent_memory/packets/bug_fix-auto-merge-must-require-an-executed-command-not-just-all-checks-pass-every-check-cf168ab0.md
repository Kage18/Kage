# Auto-merge must require an EXECUTED command, not just all-checks-pass — every check passing is true when nothing ran

> maybeAutoMerge in mcp/delegation/ratify.ts originally gated on "the claim exists, has checks, and every check passed"…

maybeAutoMerge in mcp/delegation/ratify.ts originally gated on "the claim exists, has checks, and every check passed". That gate is satisfied by a claim where NOTHING WAS EXECUTED, so a goal with autonomy "merge" would have landed code unattended that the product itself refuses to call verified.

The mechanism: in a repo with no configured test command — Kage's primary target case, an arbitrary repo it was just installed into — the only checks that run are non-executing ones: diff-size (kind "diff"), citations (kind "citation") and reachability (kind "analysis"). All three pass. Meanwhile claimVerdict in mcp/delegation/verify.ts derives "was anything actually executed?" from `checks.some(c => c.kind === "command" && c.result !== "not_run")`, so it labels that exact same claim "UNVERIFIED — nothing was executed (3/3 static checks)". Two parts of the kernel disagreed about the same claim, and the one that merges code was the permissive one.

Fix: maybeAutoMerge now also requires claimVerdict(claim).executed, and records the refusal reason naming the verdict. Auto-merge is the only path where code lands with no human in the loop, so it must never land what the rest of the product declines to call verified.

Two generalisations worth keeping:
1. "Every check passed" is NOT a synonym for "verified" anywhere in this codebase. Any new gate that decides something consequential must consult claimVerdict rather than re-deriving pass/fail by folding over checks, or it will silently disagree with the receipt the human reads.
2. When you add a check whose kind is not "command", audit every existing predicate that folds over claim.checks — adding a passing non-executing check makes all such predicates more permissive, never less. The reachability check being added is what made this gap reachable in practice.

Verified by mutation: with the executed gate removed, both auto-merge refusal tests in mcp/goal-engine.test.ts fail; with it restored they pass. A safety test that passes with and without the fix proves nothing, so mutation-check any gate like this rather than trusting a green suite.

After adding the executed requirement, mcp/goal-engine.test.ts's two refusal tests pass; deleting the `&& Boolean(verdict?.executed)` clause makes both fail. Full suite 655 unit + 12 dogfood green on release-prep after the fix.
