# AdapterLiveInput's `sessionId` (start fresh under a chosen id) and `resumeSessionId` (r...

> AdapterLiveInput's sessionId start fresh under a chosen id and resumeSessionId reattach an existing session are mutua…

AdapterLiveInput's `sessionId` (start fresh under a chosen id) and `resumeSessionId` (reattach an existing session) are mutually exclusive spawn shapes for claude's live mode, mirroring the same sessionId/resumeSessionId split AdapterInput already had for the non-live `.run()` path — the live path just never modeled it until now.

Learned while delivering: Part 2 of the orphaned-run fix: make steering a supervisor-less run RE-ATTACH a supervisor instead of orphaning the result. Context: part 1 (just merged) made superviseRun in mcp/delegation/supervisor.ts hold through blocked — the same supervisor now takes a tell via its socket and collects the claim; it also gave Adapter an optional spawnLive capability and superviseRun an adapterOverride test seam. Remaining hole: when steerRun in mcp/delegation/steer.ts finds NO live supervisor socket (isRunLive false) for a run in a resumable state (blocked, stopped, failed — and dropped displays, whose raw state is in-flight with a dead pid), it falls back to a fire-and-forget claude --resume child: the message is delivered, the agent completes a turn, and its kage-claim fence lands in the transcript with no collector — no claim.json, no verification, no transition (observed three times; the orphaned tokenizer run one-array-bugfix-in-mcp-delegation-app-c-260817-d1a3 is still parked this way). Fix: in that fallback path, append the steer to the run steer log as today, ensure the run state permits re-entry (failed→running and stopped→running are legal; for a raw in-flight state with a dead pid, reap first via reapRun then re-enter — follow part 1 state-guard patterns), and spawn a DETACHED supervisor for the run (same spawn shape dispatchDetached uses: the kage supervise <runId> CLI entry, detached, unref, stdio ignore) instead of the bare resume child. superviseRun must then handle RESUME: when it starts and finds an existing agent_session_id plus undelivered steers, resume that session — the claude resume spawn shape (claude -p --resume <session-id> with stream-json stdio) belongs in the claude adapter alongside spawnLive, not hardcoded in the supervisor — and deliver the pending steer text as the first user message frame, then run the normal read→fence→verify→land loop. Keep delivery vocabulary honest: this path reports resumed, and it must now be TRUE that resumed work gets collected. Never auto-resume a blocked run without an explicit tell (rule stands). Tests with the part-1 seams (adapterOverride, scripted spawnLive stub, real sockets): (1) REGRESSION: a run with a dead session — state failed, no live supervisor, undelivered steer appended — is resumed by a reattach supervisor via the stub spawnLive and lands ready with a real claim.json; (2) steering a HEALTHY supervised run still goes through the live socket with NO reattach spawned (assert via a spawn seam or spawn count); (3) existing steer delivery-vocabulary tests keep passing. Success = npm test fully green.
Verified by: npm test --prefix mcp, diff-size, citations
