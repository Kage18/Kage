# notifyManagerOfRunEvent and drainPendingGoalEvents both compose their '[kage event]' me...

> notifyManagerOfRunEvent and drainPendingGoalEvents both compose their ' kage event ' message text from data already o…

notifyManagerOfRunEvent and drainPendingGoalEvents both compose their '[kage event]' message text from data already on the GoalRecord + live readRun state, not from a separate event stream — so wave-completion detection can be added as a pure message-formatting helper (waveCompletionNote) shared by both paths, with no new persisted event type needed.

Learned while delivering: Give the manager the tools to actually run a plan. Right now it is instructed to orchestrate and has no way to do it.

THE DEFECT, measured today: there are ZERO goal tools on the MCP surface — grep -c "kage_goal" mcp/index.ts returns 0 — and MANAGER_ALLOWED_TOOLS in mcp/delegation/manager-client.ts lists only kage_room_state, kage_events_since, kage_compile_brief, kage_dispatch, kage_task, kage_tell, kage_stop, kage_merge_run, kage_reject_run, kage_report, kage_judgment. Meanwhile manager-prompt.ts has an entire "Orchestrating a goal" section telling the manager it is the orchestrator, to decompose work into waves of parallel runs with disjoint file scopes, and to dispatch an approved wave. The manager is told to manage and given no instrument to manage with. A goal can only be created from the app's orchestrate shortcut today.

This is now the central gap, not a side one: the product's position is that Kage manages your work the way AO and Conductor do, with memory as what makes it better. A manager that cannot open a goal, see where it stands, or move it forward is a chat partner, not a manager.

WHAT TO BUILD — three MCP tools in mcp/index.ts, added to MANAGER_ALLOWED_TOOLS, each thin over the goal.ts functions that already exist. Do NOT add new goal semantics; the engine landed yesterday and works (state advances planning -> executing -> done from real run outcomes, autonomy governs auto-merge, files_scope disjointness and budgets are enforced at attach, waves fill first-open-first).

1. kage_goal_create — intent, optional plan (waves of run specs with intent/type/files_scope), optional autonomy ("recommend" default | "merge"), optional budgets. Wraps createGoal. Inside a room thread (KAGE_ROOM=1) it must also make the new goal that thread's ACTIVE goal via setActiveGoal, exactly as POST /goals in mcp/delegation/api.ts already does — that is what makes subsequent kage_dispatch calls attach automatically, and it is the mechanism that stops the manager from having to remember goal_id.
2. kage_goal_status — given a goal id, or defaulting to the thread's active goal, return the goal's state, its waves with each run's id and CURRENT state, spend against budget, and which wave is next to dispatch. This is the tool that lets the manager answer "where are we" without guessing, and it must read through the reconciling readGoal so a stale record heals on read.
3. kage_goal_finish — abandon a goal with a reason (wraps abandonGoal). Do NOT add a tool that forces a goal to "done": done is derived from its runs and must stay derived, never asserted. If the manager wants to stop a goal early, that is abandoning it, and the reason is worth keeping.

ALSO update mcp/delegation/manager-prompt.ts's "Orchestrating a goal" section to name these tools, so the instruction and the capability finally match. Keep it to a few lines in the existing voice — the section already explains the wave discipline, it just needs to say which tool opens a goal, which one reports on it, and that runs dispatched while a goal is active attach automatically.

WAVE ADVANCE — the point of the whole feature. The manager is already woken by "[kage event]" frames when a goal-owned run changes state (the wake loop is built and proven). Make the event that matters explicit: when the LAST run of a wave reaches a terminal state and the goal has a further wave planned, the frame the manager receives must say so plainly and name what is next — e.g. "wave 1 of 3 complete: 2 merged, 1 rejected. Wave 2 is next: <the wave's run specs>." Today the frame reports a single run's state change and leaves the manager to infer wave completion, which is exactly the inference it keeps getting wrong. Do this in the coalescing that already exists in mcp/delegation/room-supervisor.ts rather than inventing a second event path.

TESTS — new file mcp/manager-orchestration.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Drive the tools through callTool(name, args) — mcp/index.ts exports it and the MCP-boundary tests already use it. Cover: kage_goal_create makes the goal and sets it active under KAGE_ROOM=1; a dispatch with no goal_id afterwards attaches to it; kage_goal_status reports each wave's runs with their current states and names the next wave; kage_goal_status on a goal whose runs all settled reports "done" (proving it reads through the reconciling path); kage_goal_finish abandons with the reason recorded; there is NO tool that can force a goal to done; and the wave-complete frame names the next wave's specs. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. Read mcp/delegation/goal.ts and mcp/delegation/api.ts's /goals routes FIRST and reuse them; the API already does most of this over HTTP and the MCP tools should not diverge from it. Do not touch mcp/delegation/reachability.ts or mcp/delegation/trackrecord.ts.
VERIFY: npm run test --prefix mcp (708 green before your change — use the "npm run test" form) and npm run build --prefix mcp with no "error TS". Run them for real and fill in the claim fence.
Verified by: npm test --prefix mcp, diff-size, citations, npx tsc --noEmit -p mcp/tsconfig.json, reachability
