# git ls-files (after the worktree is already staged via `git add -A`, which verifyRun's ...

> git ls files after the worktree is already staged via git add A , which verifyRun's stageAndMeasure always does first…

git ls-files (after the worktree is already staged via `git add -A`, which verifyRun's stageAndMeasure always does first) is a clean, .gitignore-respecting source for suffix-matching a cited path against real repo files, and needs no shell/manual directory walk.

Learned while delivering: Two fixes to the verification loop itself. It is currently jamming: it fails correct work on a false signal, and then offers no way to recover that work.

PROBLEM 1 — the citations check fails runs over prose. It has now produced a FALSE failure on three runs today, two of them back-to-back on work whose tests actually passed:
- 'state.room/state.pty' — an identifier pair read as a file path (already fixed once this morning, in citedPaths).
- 'dist/x.js' and 'shell/app' — placeholders occurring in the agent's own prose.
- 'adapters/index.ts' — a REAL file that exists at mcp/delegation/adapters/index.ts, cited by its short name. The extractor resolves cited paths only from the repo root, misses it, and fails the entire run.
That last run had: tests exit 0, static-typecheck exit 0, diff-size ok, and citations as the ONLY failing check. Correct, verified work was blocked by a naming technicality.

FIX in mcp/delegation/verify.ts (citedPaths and whatever performs the existence check):
a. Before declaring a cited path missing, try to resolve it as a UNIQUE SUFFIX of a real repo file. 'adapters/index.ts' uniquely matches 'mcp/delegation/adapters/index.ts', so resolve it and pass. If the suffix matches two or more files it is ambiguous — do not guess; treat it as unresolved.
b. Distinguish a path the agent formally CITED from a path merely mentioned in prose (learnings, unsure notes, narrative). Only a formally cited path may FAIL the check. An unresolvable path found in prose is reported as a warning on the receipt, never a failure. Rationale: this check exists to catch an agent citing files it never touched, not to police its English.
c. Keep the guard's teeth — a formally cited path that resolves nowhere must still fail. Add a test proving a genuinely invented citation like 'mcp/delegation/does-not-exist.ts' still fails.

PROBLEM 2 — a run that fails verification has no way back, even after the defect is fixed. Right now the only options are merge (refused: 'Only a verified claim can be merged') or reject (throws away correct work). Two runs are sitting in exactly this state. Note that mcp/delegation/contract.ts's LEGAL_TRANSITIONS ALREADY allows failed -> running, with a comment saying 'A failed verification is not the end of the story: retry with steering' — the transition was designed and simply never given a command. This is the same designed-but-unwired pattern that has bitten this repo seven times.

FIX — add a 'kage reverify <run-id> --project <dir>' command:
a. Wire it in mcp/cli.ts next to the existing review/merge/reject commands, and list it in the CLI help under the delegate/orchestrator section so it is discoverable.
b. It re-runs the SAME kernel-executed checks against the run's CURRENT worktree contents, then lands the run at ready or failed based on the fresh result. It must NOT re-run the agent, must NOT recompile a brief, and must NOT alter the agent's claim text — only the check verdicts and the state.
c. Legal from 'failed' and from 'ready' (re-checking an already-ready run before merging is legitimate). Refuse with a clear message from merged/rejected — those are terminal.
d. The receipt must show the verdicts were re-run and when, so a reader can never mistake a stale pass for a fresh one.
e. Reuse the existing check-execution path rather than duplicating it. Read mcp/delegation/verify.ts and mcp/delegation/static-checks.ts first; the checks are already assembled in one place for dispatch.ts's executeRun and supervisor.ts's superviseRun, and reverify should call that same assembly.

TESTS — put them in a NEW file mcp/reverify.test.ts, NOT in mcp/delegation.test.ts (that file is a merge-conflict hotspot; three merges collided there today). Cover: a unique suffix citation resolves and passes; an ambiguous suffix does not; an invented citation still fails; a prose-only unresolvable path warns without failing; reverify moves a failed run to ready when the worktree now passes; reverify leaves it failed when it still does not; reverify is refused on a merged run.

SELF-TEST before claiming: run your new suffix resolution against the literal string 'adapters/index.ts' in this repo and confirm it resolves to mcp/delegation/adapters/index.ts.
