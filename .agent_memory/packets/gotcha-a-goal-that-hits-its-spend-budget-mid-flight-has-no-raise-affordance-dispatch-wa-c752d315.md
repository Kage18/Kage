# A goal that hits its spend budget mid-flight has no raise affordance — dispatch-wave refuses and only hand-editing goal.json unblocks it

> Goals default to budgets {usd: 20, runs: 10} DEFAULT GOAL BUDGETS when created without budgets, and dispatch wave har…

Goals default to budgets {usd: 20, runs: 10} (DEFAULT_GOAL_BUDGETS) when created without budgets, and dispatch-wave hard-refuses to attach a run once cumulative run spend exceeds the cap ("is already at its spend budget ($38.98/$20.00) — refusing to attach another run"). Unlike runs (kage resume-run --budget-usd raises a run's cap explicitly), there is NO route, CLI verb, or app control to raise a GOAL's budget after creation — the operator had to hand-edit .agent_memory/goals/<id>/goal.json budgets.usd (bootstrap exception, 2026-08-21, 20→60) to continue a 3-wave goal. Product gap: goals need an explicit budget-raise affordance (API + CLI + goal-overlay control) with the same stated-raise honesty as resume-run. Until it exists, size goal budgets at creation for ALL planned waves, not the default.
Evidence: dispatch-wave response warnings on goal build-the-entire-app-and-website-from-th-260821-f892: run_ids [] with the $38.98/$20.00 refusal; wave 3 attached successfully after the hand-raise to 60
Verified by: live dispatch-wave refusal + successful re-dispatch on 2026-08-21
