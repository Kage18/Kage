# RoomSessionMeta.native_transcript_path is set only by room-pty.ts (the interactive/pty ...

> RoomSessionMeta.native transcript path is set only by room pty.ts the interactive/pty session , never by room supervi…

RoomSessionMeta.native_transcript_path is set only by room-pty.ts (the interactive/pty session), never by room-supervisor.ts's headless room — confirming and extending the existing repo memory on this — so Chat's has_transcript flag depends entirely on the pty session's native jsonl file, which is exactly why this bug degraded Chat even though the warning was observed in the Terminal tab.

Learned while delivering: The orchestrator session silently loses its native transcript whenever Kage's daemon was launched from inside another agent session - fix the spawn env. Observed live in the app's Terminal tab just now: the interactive orchestrator claude printed '⚠ Transcript saving is off - inherited CLAUDE_CODE_CHILD_SESSION marker · restart with CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1'. Consequence: the native transcript file the unified-session chat view renders from (room-transcript.ts) is never written for that session, so Chat permanently degrades to its fallback rendering - the has_transcript flag stays false and the user gets the old view with a small label, with no hint why.

FIX, in mcp/delegation/room-pty.ts (and mcp/delegation/room-supervisor.ts if the headless spawn passes env through the same shape): the spawned claude's env must (a) DELETE any inherited CLAUDE_CODE_CHILD_SESSION-style marker variables (find the exact names by checking what the claude CLI reads - grep its docs/help output at runtime is fine; at minimum the one named in the warning), and (b) set CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1, so the orchestrator ALWAYS persists its native transcript regardless of who launched the daemon. Audit the same env hygiene for WORKER spawns (mcp/delegation/adapters/cli-agent.ts): workers run headless -p and their stream is captured by the supervisor either way, but if the same marker suppresses their native session persistence, resume via --resume may be affected - establish whether it is, state what you found in your claim, and apply the same env fix there only if resume actually depends on it.

TESTS - new file mcp/spawn-env.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: the pty spawn's computed env deletes the inherited marker and sets the persistence flag (use the existing spawn seams - never a real claude); the headless room spawn likewise if you changed it; an env WITHOUT the marker passes through otherwise untouched (no accidental scrubbing of unrelated vars). Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS - no import.meta, no top-level await. Your files: mcp/delegation/room-pty.ts, room-supervisor.ts, adapters/cli-agent.ts (only if resume depends on it), and your new test file. Do NOT touch app-client.ts/app-styles.ts (another run owns them right now), api.ts, contract.ts. Build and test ONLY inside your own worktree - never run npm, tsc or node against /Users/kushaljain/code/Kage. Rebase onto release-prep first if your base carries an inherited red. End with the kage-claim-v1 fence, citing files individually.
