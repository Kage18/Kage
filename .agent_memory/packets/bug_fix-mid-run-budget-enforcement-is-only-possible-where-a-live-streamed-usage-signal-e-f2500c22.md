# Mid-run budget enforcement is only possible where a live, streamed usage signal exists:...

> Mid run budget enforcement is only possible where a live, streamed usage signal exists: supervisor.ts's spawnLive bra…

Mid-run budget enforcement is only possible where a live, streamed usage signal exists: supervisor.ts's spawnLive branch parses per-turn total_cost_usd/usage off each stream-json 'result' line, but dispatch.ts's executeRun and supervisor.ts's non-spawnLive fallback both await one single Adapter.run() call and only see usage once the agent is already done — there is no incremental hook to enforce against there, only after-the-fact reporting.

Learned while delivering: Enforce the per-run budget. It is displayed on every run and enforced on none.

MEASURED: run build-a-stale-memory-triage-surface-do-n-260818-ec2c recorded spend.usd_est 3.4124 against budgets.usd 2 — 70% over its own cap — and nothing stopped it, warned about it, or noted it. It also ran 13.2 minutes against budgets.minutes 30, so the minutes cap was never tested; the dollar one simply does not exist as a control.

WHERE IT STANDS: budgets are written onto every run record (budgets: {usd, minutes, diff_lines}) and shown per-run in the app. diff_lines IS enforced — it is a real check in the claim. usd and minutes are not: grep of mcp/delegation/dispatch.ts and mcp/delegation/supervisor.ts finds no usd comparison anywhere. Budget refusal was built for GOAL attachment only (checkGoalAcceptsNewRun), so a run dispatched outside a goal — which is most runs — has an unenforced cap displayed next to it.

WHY THIS MATTERS: a displayed limit that does not hold is worse than no limit, because the user reads it as a control. This product's whole position is that it reports honestly; a fake cap is the same class of defect as a claim that says VERIFIED when nothing ran.

WHAT TO BUILD — pick the honest option and justify it in your claim:
(a) ENFORCE. The supervisor already sees token usage as the run streams (tokens_used is on the record and updated during the run). Convert that to an estimated dollar figure with the same rate the rest of the product uses — there is an existing KAGE_USD_PER_MTOK env var and a default documented in the gains output; find it and reuse it, do not invent a second rate. When estimated spend crosses budgets.usd, stop the run the same way a stop already works, record the reason on the run ledger, and land it in a state that makes clear it was halted on budget rather than failed on its work. A halted run must still keep its worktree and its partial diff — the user may well want to merge or resume it.
(b) STOP CALLING IT A BUDGET. If enforcement mid-run is genuinely not feasible with the data available, rename the field to what it is (an estimate, or a target) everywhere it is written and displayed, and say plainly in the app that it is not a cap.
Prefer (a). Choose (b) only if you find a concrete reason (a) cannot work, and state that reason.

WHATEVER YOU CHOOSE, also make the overrun VISIBLE after the fact: a run whose final estimated spend exceeded its budget must show that on its receipt and in the app's run detail, not silently. That is the minimum honest behaviour even if enforcement lands later.

CONSIDER the minutes cap in the same change if it is cheap — the same "is this run over its stated limit" question, the same honest reporting. If it is not cheap, leave it and say so.

TESTS — new file mcp/run-budget.test.ts (repo rule: new behaviour gets its own file; mcp/delegation.test.ts is off-limits). Cover: a run whose estimated spend crosses budgets.usd is halted (or, under option b, is never described as capped); the halt reason is recorded and names the limit and the actual figure; a run under budget is untouched; the worktree and diff survive a budget halt; and a completed run that exceeded its budget reports the overrun on its receipt. Name in your claim which test fails if the change is reverted.

CONSTRAINTS: CommonJS — no import.meta (TS1470), no top-level await. Do NOT touch mcp/index.ts, mcp/delegation/manager-client.ts, mcp/delegation/manager-prompt.ts, mcp/delegation/room-supervisor.ts, mcp/cli.ts or README.md — two other runs are editing those right now.
