# Benchmarks, Agent Orientation, and MCP Tool Token Economy

**Confidence:** firm for the orientation features (stable since May 2026) and the MCP response-size fixes (measured byte/token counts, regression-tested); provisional for the benchmark posture as a whole, since the answer-accuracy measurement remains genuinely unrun and one internal contradiction below was never explicitly reconciled by the source packets.

Three sequential features give an agent working in a Kage-managed repo small amounts of always-on orientation without forcing it to load the whole memory store: pinned context slots (`.agent_memory/slots/slots.json`, repo-local, git-reviewable, blocked from carrying sensitive content, injected ahead of task-specific memory in recall/context — chosen deliberately over a global-persona-slot design); the project profile (`kageProjectProfile`), a rebuildable *report* rather than a second mutable memory store, summarizing the structural index, code graph, and approved memory into repo totals, languages, key files, memory focus, run commands, next actions, and warnings, exposed identically through the CLI, MCP, REST, and the viewer, and built to tolerate older packets missing newer fields so a Kage upgrade never breaks an existing repo; and Repo X-Ray, the broadest of the three, a first-use structure map combining entry points, core modules, risk signals, tests, a memory overlay, and knowledge gaps, with an explicit rule that its risk layer must filter out Kage's own `.agent_memory` paths so a user sees real code risk, not Kage's own bookkeeping mistaken for a risk signal. Kage holds its own recall quality to a matching self-imposed discipline. The synthetic memory-scale benchmark moved from a standalone script into the package proper (`kage benchmark --scale`, MCP `mode: memory_scale`) and was verified at 240/1,000/5,000 synthetic packets, all reaching 100% recall (5,000 packets: 362ms median recall, 99.83% context reduction). For the external LongMemEval-S benchmark, two configurations were run and both numbers are real, but they answer different questions and were never reconciled into one reported figure by the source evidence: date-aware temporal expansion plus lightweight concept-group expansion (garden/produce, phone battery, siblings, business milestones, kitchen appliances) reaches R@5 97.45%, R@10/R@20 100.00%, MRR 0.9202, NDCG@10 0.9398 over 470 non-abstention questions — this is the product's actual, tuned day-to-day recall behavior (BM25 plus graph/date/concept expansion, explicitly not vector-embedding search or answer-generation accuracy) — while the *headline/reportable* number is required to run with concept expansion explicitly disabled, so a third party evaluating "vanilla retrieval" isn't quietly credited with a feature they never enabled: under that strict mode the same 470-question slice measures R@5 96.17%, R@10 98.72%, R@20 99.79%, MRR 0.9094, NDCG@10 0.9279. A separate 50-question slice compared dense local embeddings against default recall and found identical top-line numbers (R@10 100%, MRR 0.9575, NDCG@10 0.9675) while embeddings ran slower (232ms vs. 189ms median) — no accuracy gain plus a latency cost kept embeddings an opt-in path rather than the default. The packaged coding-memory benchmark adds a source-diversity probe (four high-scoring memories from one noisy session plus one from an independent session; top-4 recall must include the independent source with no more than three from the noisy one) exposed to the viewer as a named `source-diversity` proof-ledger item. A parallel attempt to measure *answer* accuracy (not just retrieval) via a MemoryArena-style harness remains unrun rather than negative: the harness reaches Kage's strict recall, asks an answer provider per subtask, and scores against gold answers, but a genuine LLM provider is required for real numbers (`--provider gold` is a scorer smoke test only, never reportable as accuracy), and the one live attempt via the OpenAI Responses API was blocked before producing data by `429 insufficient_quota` — a working ChatGPT login does not imply the separate API project has billing configured.

On the tool-surface side, Kage discovered its own MCP tools were spending a caller's context window as if it were free, a defect distinct from (but in the same spirit as) the `kage_refresh`/`kage_pr_check` response-cap work documented elsewhere: an audit found `kage_supersede` returning roughly 10,000 tokens for one operation (echoing the complete old and replacement packets, including every cited file's and symbol's sha256) against two lines from the equivalent CLI command for the same work, and `kage_memory_lifecycle` carrying each packet's full `body` *and* `summary` with no truncation — on a 433-packet repo that one field alone accounted for over half the tool's total response size, making it the single worst offender found in that audit. The fix pattern — a shared `capCollection()` helper, with regressions tracked in the repo's single dedicated `mcp/response-size.test.ts` file rather than a new test file per tool — generalizes a pattern already proven once elsewhere on the MCP surface. In the same spirit of tuning the tool surface for its actual consumers, the 11 `CORE_TOOLS` in `mcp/index.ts` deliberately carry a full `description` on every input-schema parameter and MCP `annotations` (title, `readOnlyHint`, `destructiveHint`/`idempotentHint` for writers) specifically because Glama's Tool Definition Quality Score penalized undocumented parameters and missing annotations — and that score only reflects the published npm version, so a schema change needs a republish to actually move it.

## Contradictions / open questions

- The two LongMemEval-S numbers cited here (concept-expanded R@5 97.45% vs. strict R@5 96.17%) are not a data contradiction — they are two different, deliberately distinct configurations — but the source packets never state in one place which number Kage actually publishes externally; read the expanded number as internal/product truth and the strict number as the one that should appear in any outward-facing claim.
- `kage_memory_lifecycle`'s uncapped `body`+`summary` field was found to be the single worst offender on the MCP surface, worse than `kage_pr_check`; no packet in this set confirms it was actually fixed, only that `capCollection()` existed as a proven pattern at the time of the audit.
- No packet in this set confirms whether the MemoryArena answer-accuracy benchmark was ever successfully run after the OpenAI quota block was resolved; it remains an open, unmeasured gap rather than a negative result.
- This doc's MCP-token-economy material (`kage_supersede`, `kage_memory_lifecycle`, `CORE_TOOLS` annotations) covers different specific tools than the `kage_refresh`/`kage_pr_check` response-cap fixes documented elsewhere in this repo's memory — both describe the same recurring defect (uncapped MCP responses) and the same fix pattern, but were captured as separate audits with non-overlapping tool citations; a future pass may want to merge them into one MCP-response-budget doc rather than keeping the pattern split across two.
