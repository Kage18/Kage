# Terminal Mode and PTY Take-Over Lessons

**Confidence:** firm — the original blank-pane failure was root-caused and fixed with concrete, verifiable mechanisms (chmod, scrollback buffer, snapshot endpoint, setTimeout repaint), and the later per-run take-over work reused those same mechanisms deliberately; the newest layer (per-run take-over UI/API wiring) is still in progress, which keeps this short of settled.

Kage's interactive terminal (a real `claude` process in a node-pty, rendered client-side with xterm.js) is a thin but fragile stack, and its history is one long lesson in not trusting the first plausible hypothesis. The original "blank pane" bug turned out to be four independent bugs stacked on top of each other, discovered only after a wrong hypothesis ("the sandbox blocks pty allocation") survived several turns of self-confirming probes instead of being tested to failure — the actual tell, a `posix_spawnp failed.` error wrapped in Kage's own CLI formatting, proved the process reached Kage's code, which a sandbox block could never produce. The real causes, in order: (1) node-pty's prebuilt `spawn-helper` binary lost its executable bit during npm extraction, so every spawn failed with an opaque, file-less error — fixed by chmod'ing it in-process before first use (`ensureSpawnHelperExecutable` in room-pty.ts); (2) the supervisor broadcast only post-connect bytes, so any client attaching after the terminal's banner printed saw nothing — fixed with a 256KB rolling scrollback buffer replayed on attach; (3) the same bug one layer up — the daemon holds one long-lived supervisor connection fanning out to many browser tabs over SSE, so it drained the replay once and later tabs got nothing — fixed by exposing `PtyState.scrollback` via a snapshot endpoint the client reads on open; (4) xterm needs a real flex box (`flex:1; min-width:0`) to size correctly, and — critically — the preview browser used for verification does not fire `requestAnimationFrame` at all, so terminal creation had to move off rAF onto `setTimeout`, which also happens to fix a genuine production bug where backgrounded browser tabs throttle rAF and would otherwise silently never paint the terminal. This same pty machinery (snapshot-on-attach, resize, repaint-ladder patterns from room-pty.ts) was later deliberately reused to build a second, distinct capability: per-run terminal take-over, where a human can seize an in-flight run's own agent session as an interactive pty (`claude --resume <sessionId>`) and hand it back to a detached supervisor afterward. That reuse surfaced a small but instructive interface/usage mismatch — `PtyLike.onExit`'s exit-code parameter was declared but never read by any caller, dead plumbing that should not have been in the interface at all. Separately, when the Room's cold-start "identity" wait window was raised from 5s to 20s to fix a race, the fix had to route through an existing injectable-wait test seam rather than let the real 20s window run in every affected test — a first attempt that skipped the seam turned a normal 2-4 minute test suite into a 1200-second timeout by making tests literally sleep the production window. A related rendering-discipline fix landed in the same run-detail pane: `renderDetail()`'s naive re-render used to blow away a live xterm instance because it reset the whole pane via `textContent = ""`; the fix restructured the pane from one class/id div into a wrapper split into stable sibling nodes, so re-rendering the surrounding chrome no longer destroys the terminal instance living inside it.

A separate terminal surface — the standalone TUI (`mcp/delegation/tui/*`, driven by `kage ui`) — is the same "framework-free rendering, corruption only visible live" story in a different codebase: it writes raw ANSI escape sequences directly, with nothing validating frame correctness, rather than going through node-pty/xterm.js like the Room and run take-over above. Five rendering laws were each learned from a real corruption: erase every line to end-of-line before writing the next frame (cursor-home plus newlines alone leaves stale tail characters wherever the new frame is shorter than the last one); never write into the terminal's last column (a glyph there can trigger auto-wrap and scroll the whole frame up, walking the header off-screen — the app must budget width-1 and disable auto-wrap while it owns the screen); split key-chunk parsing by walking the buffer and keeping each escape sequence whole (treating any chunk starting with escape as one key silently breaks held arrow keys); truncate styled text by walking its escape sequences and always closing with a reset, or color leaks down the screen; and clamp every scroll to content length while reselecting by identity after a data refresh, or the view scrolls into blank space. A testing footnote applies here too: TUI tests must contain literal escape bytes, and some editing paths strip them silently, which makes the assertion pass while proving nothing.

## Contradictions / open questions

None found in the cited evidence — the four-bug diagnosis and the later take-over reuse are consistent and sequential, not conflicting. The per-run take-over feature itself was still backend-only at the time of these packets (UI/API wiring assigned to a separate, later run), so its full end-to-end behavior is not yet verified by this evidence set. The standalone TUI (`kage ui`) is a genuinely separate codebase from the node-pty/xterm.js Room and run-take-over terminal documented above — it is folded into this doc because it is the closest thematic home ("terminal rendering, framework-free, corruption only visible live"), not because the two share implementation.
