# Distillation and Curation Lifecycle

**Confidence:** provisional — the auto-distill/resume behavior has been rewritten at least three times in this packet set alone (v1 → v2.2.0 signal-gating → later warm-start hardening that reversed part of v2.2.0), which suggests the design was still actively settling rather than stable, and the "fixes need a rebuild+restart" runbook shows the loop is operationally fragile to reason about live.

Kage's ambient capture pipeline starts with hooks installed by Claude Code setup — UserPromptSubmit, PostToolUse, PostToolUseFailure, PreCompact, Stop, and SessionEnd in addition to SessionStart — which store privacy-filtered observations, inject relevant recall context on prompts, and distill durable observations before compaction or session end; this is the mechanism that makes distillation ambient rather than something a user invokes by hand. `kage distill --auto` writes candidates to a pending inbox (not approved memory) tagged `auto-distill`, and those pending drafts are excluded from recall until reviewed — with `sessionAlreadyCaptured` skipping sessions where the agent already captured memory directly, to avoid double-counting. This behavior was revised at least twice: the v2.2.0 pass added *signal-gating* (`observationSignalScore >= AUTO_DISTILL_SIGNAL_THRESHOLD`, 0.4) so raw JSON payloads, hook notifications, sub-50-char fragments, and Kage self-echoes score 0 and get silently skipped rather than distilled into junk pending drafts — and it also added a "Recent memory" timeline (newest 15 packets, capped ~800 tokens) to the `kage resume` SessionStart digest. A later hardening pass then *removed* that recency timeline again, on the grounds that it fired before the task was known (so it could never be targeted) and was the exact surface injecting raw command dumps and ungrounded junk at the top of every session; `kage resume` now emits only task-relevant "Open threads" (change-memory, pending drafts, reconcile pointers) plus always-on pinned repo facts, deferring task-relevant recall to the first prompt. Separately, an adoption-focused change added *tiered auto-promotion*: a distilled draft can be written straight to approved/recallable memory (skipping human review) only when auto-promote is enabled, mode is auto, admission classifies it `high_signal`, every cited path exists, and there are zero duplicate or contradiction candidates — with the explicit reasoning that this does not weaken the trust model because verification (citations checked at write, stale-withheld at recall) is a separate concept from human review; only clearly-good grounded learnings skip the review gate. The `kage sessions` command and viewer Memory page make this distillation visible (privacy-scanned observed sessions, durable-candidate framing, the exact `kage distill` action to run) as Kage's deliberate alternative to raw session-transcript replay. On the curation side, `curationComparison` and `renderTrustLine`'s verified-claim tally were both audited against a repo-wide rule that "every check passed" is not the same as "verified" — a claim where nothing executed still passes trivially in a repo with no configured test command, so both call sites were required to gate on `claimVerdict(claim).executed`, following the same fix already applied to auto-merge and track-record computation; `curationComparison` already accepted an optional `runs?: TaskRecord[]` test-seam parameter, which let its tests write claims directly rather than driving a full git-worktree dispatch. Finally, a hard operational gotcha applies to all of the above: a fix to capture/distill/recall code does not take effect in the running session's live tooling until the global `kage` binary is rebuilt and reinstalled AND the agent process is restarted, because the Stop/SessionStart hooks shell out to the PATH-installed `kage` binary and the MCP server loads its dist at session start — verifying a fix requires running the freshly built CLI directly, not the live hooks/MCP tools.

## Contradictions / open questions

The `kage resume` SessionStart digest was extended (v2.2.0: added a 15-packet "Recent memory" timeline) and then had that same feature explicitly removed in a later pass, for a stated reason (it injected junk before the task was known). Both changes are evidenced and the later one is clearly reasoned, but a reader relying only on the v2.2.0 packet would describe current behavior incorrectly — this is a case where "the current v2.2.0 behavior" packet title is itself now stale relative to the warm-start hardening packet. Whether tiered auto-promotion and the task-driven-resume hardening (both from the same general period) were shipped together or one depends on the other is not established by the cited packets.
