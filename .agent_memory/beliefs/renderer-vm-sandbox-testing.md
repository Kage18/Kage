# VM-Sandbox Testing of app-client.ts's Module-Level State

**Confidence:** firm — the sandbox-construction technique and its failure mode have been rediscovered near-identically across at least four separate runs, so the fact is well established even though it is not centralized into a single shared test helper.

app-client.ts executes real top-level DOM-wiring code the instant the script runs — an Electron-detection `if (navigator.userAgent.indexOf("Electron") >= 0) ...` right after `var state = {...}`, followed by dozens of `document.getElementById(id).onclick = ...` assignments scattered through the file. Unit-testing any function in this file with Node's `vm.runInNewContext(APP_CLIENT, sandbox)` therefore depends entirely on how permissive the sandbox's `document`/`navigator` stubs are: a `getElementById` stub that returns `null` for unlisted ids, or a bare `navigator` without `userAgent`, throws at the first unmatched statement and aborts the script partway through. Because only hoisted `function` declarations (not `var` initializers) survive a mid-script throw, every module-level `var` assigned AFTER the throw point — `roomLinkedRuns`, `roomPaintedCount`, `roomSignature`, `roomEnteringView`, `STATE_DOT_COLOR`, `VERDICT_CARD_STATES`, `DIFF_HUNK_RE`, `pendingActions`, `openInlineAsks`, and others — stays permanently `undefined` in that sandbox, even though the names are reachable via hoisting. Any function that reads one of these vars (e.g. `renderRoom`, or a new `buildDecisionBtnGroup` reading `pendingActions[run.id]`) is unsafe to call through a partial sandbox, and will appear broken even when the real implementation is correct. The pattern that works, arrived at through repeated trial: a fully permissive sandbox — a catch-all `getElementById` returning a generic non-null fake element per id (memoized per id so repeated lookups are stable), `document.documentElement`, a stubbed `navigator.userAgent`, a no-op `EventSource` constructor, and `localStorage`/timer stubs. With all of that present, APP_CLIENT's entire top level runs to completion with zero throws, every module-level var is safely assigned, and functions like `renderRoom`, `fillBoardCard`, or `midTruncate` become genuinely callable and testable with real behavior rather than just source-text regex checks — the same `runInNewContext(APP_CLIENT, sandbox)` recipe against a minimal `document` stub works for *any* top-level function declaration in the file, not just the one it was first built for, because function declarations hoist ahead of the throw point regardless of source position. Where a function's full dependency chain can't be made safe even with a permissive sandbox, the practical fallback used in this repo is testing via composed-script regex/string assertions instead of direct execution. Three adjacent testing gotchas: fake DOM mocks used in these tests must implement every method a new code path calls (a `FakeElement` missing `setAttribute` crashed on a chip using `ageSpan`'s live-tick `data-age` attribute); `h(tag, cls)` sets a real multi-word `className` string (e.g. `"dline add"`), so a find-by-class test helper must split on whitespace and match by token membership, not treat the class string as one opaque token, or two-word-class lookups silently return nothing; and some tests pin exact source text via regex against specific call sites (`useTranscript`, `renderHistoryTurns`) or even a single CSS rule's exact text (`.turn.you .bubble2`), so edits to those call sites — or a future visual edit to that selector — can break an unrelated-looking test unless a second rule block is added rather than editing the first in place.

One piece of module state whose lifecycle this sandbox testing has had to get exactly right is the "entering view" flag (`roomEnteringView`) that `renderRoom` consumes to decide whether to pin the transcript to the newest turn on view-entry. The flag must NOT be cleared on a render where `turns.length` is 0 — for example `switchThread`'s own synchronous empty-placeholder render, which fires before its async `refreshRoom()` reply lands — because clearing it there means the real history that arrives a moment later renders un-pinned. The flag may only be spent on a render that actually has turns to pin to; this is exactly the kind of state-machine subtlety that a real (permissive) sandbox test, rather than a source-text check, is needed to catch.

## Contradictions / open questions

No packet disagrees with another on the mechanism. The open question is that this same sandbox-construction gotcha (partial stub → later `var`s undefined) was independently rediscovered and separately written up at least four times across different runs, suggesting the fully-permissive sandbox recipe was never centralized into a shared, reusable test helper — each run reconstructed the workaround from scratch rather than importing a known-good fixture.
