# Room Chat Unification and Actions

**Confidence:** provisional — the underlying mechanics (transcript resolution, retry, action fences) are verified by tests and live repro, but this was an actively iterating feature area with a rejected redispatch as recently as the latest packet, so the current shape should be treated as still settling.

The Room can answer a chat message through two different managers — a held interactive pty session or a held headless stream-json session — and a recurring theme in this cluster is that those two legs must be brought to parity rather than left to diverge, because a user typing in Chat should never be able to tell (or be shortchanged by) which leg happened to answer. Historically, when a chat message routed to the pty leg, the pipeline would return a canned deflection turn ("Kage sent your message to the terminal session, but hasn't recorded its identity yet... check the Terminal tab") instead of the manager's actual reply — even though `room-transcript.ts` already parses the pty's own native `claude` jsonl and the reply is usually sitting right there. The fix was to extract the real reply from the native transcript within the existing ask window (polling briefly rather than giving up immediately) and only fall back to a deflection when the transcript is genuinely unresolvable by the deadline — and even then, the fallback must state what IS known and offer an actionable "open terminal" affordance rather than bare prose. This depends on a fact that is easy to get wrong: `RoomSessionMeta.native_transcript_path` is set ONLY by the interactive pty leg (`room-pty.ts`); the headless manager's stream-json protocol has no equivalent file to point at (this is stated directly in the source comment, and was independently rediscovered and reconfirmed across several packets during the sessions-surface renderer work) — so `GET /room/transcript` is genuinely empty for any thread that has never been answered via the pty, even mid-conversation over headless, and `has_transcript` exists specifically so the client can say *why* it fell back instead of guessing. A second parity problem was structural: the manager can end a fenced `kage-actions` reply (clickable question/options, dispatch proposals, or run-opening actions) that must be parsed, stripped from visible text, and persisted as `turn.actions` — but this only worked on the headless leg. Unifying it required running the pty-extracted reply text through the same fence parser, and fixing a subtler bug underneath: `room-supervisor.ts`'s `superviseRoom()` substitutes `EMPTY_MANAGER_REPLY_TEXT` for an empty reply BEFORE emitting the "final" stream event, so `api.ts` could never detect true emptiness by checking `live.text` truthiness — it was never actually falsy by the time the caller saw it. The real fix computes emptiness (`Boolean(rawText.trim())`) inside `room-supervisor.ts` before the substitution and carries it as a new `ok?` field on the event, which is what makes a bounded, single retry-on-empty possible on that leg at all (mirroring the retry-once-then-enriched-failure pattern already built for the headless leg). Even the action-kind protocol itself has a sharp edge: adding a new `KageActionKind` requires TWO edits — the TypeScript union type AND the runtime `ACTION_KINDS` Set, because `normalizeKageActions` validates against the Set, not the type, so a type-only addition compiles cleanly but is silently rejected at runtime. This whole area is still moving: a later attempt to fix the identity-resolution timing directly (raising `PTY_IDENTITY_POLL_TIMEOUT_MS` from 5s to 20s to match how long a cold pty actually takes to boot) was rejected because it made the pty test suite hang in real time — the correct fix routes the wait through an injectable seam so tests stay fast, rather than raising a real-time constant that tests then have to sit through.
