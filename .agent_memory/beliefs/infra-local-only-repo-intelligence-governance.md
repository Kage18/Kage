# Local-Only Repo Intelligence Governance

**Confidence:** settled — the same constraint is independently applied and reaffirmed across eight separate feature decisions spanning roughly a month (mid-May through mid-June 2026), with no contradicting packet found in this batch; this reads as a foundational, repeatedly-reasserted design law rather than a one-off call.

Across a wide range of unrelated features, Kage consistently made the same architectural call: repo intelligence stays local, git-native, and dependency-free, with human review required only at the point memory is promoted beyond the repo (to org/global/public/registry/CDN scope) — never for ordinary repo-local writes. Contributor profiles and cross-repo workspace co-change detection both compute entirely from local git history and the existing code graph (commits, touched files, ownership, hidden coupling via same-author-same-24h-window commits) rather than calling out to GitHub or standing up a hosted database. The daemon's REST surface was deliberately built to expose the *same* repo-local memory primitives (context, capture, learn, feedback, setup-doctor) that MCP tools already expose, reusing existing packets/graphs/recall/audit machinery instead of inventing a parallel REST-only memory store — the explicit reason given was giving HTTP-only agents full parity with MCP agents, not a new capability. Two first-class reporting surfaces (memory lifecycle, memory timeline) were added on top of the same principle: visibility into what agents learned and how packets are aging, exposed uniformly through CLI, MCP, the daemon, and the viewer, with no hidden auto-decay — a packet's lifecycle state is always inspectable, never silently changed. Retrieval got an explicit two-tier local/optional split: the default sparse packet index is dependency-free and always on, while dense embeddings are a separate, rebuildable, opt-in artifact (`kage embeddings build`) precisely because they may require downloading a model — normal recall must stay local, fast, inspectable, and dependency-free even when the richer option exists. Finally, the write-then-review boundary itself was made explicit as a decision, not an implicit default: repo-local Kage memory is written directly as git-visible packets, and human review is required only when memory is promoted out of repo scope — everything that stays repo-local is trusted to git's own review mechanisms (commits, diffs, PRs), reinforced by a git post-commit hook that keeps memory current automatically (running `kage refresh`/`kage pr summarize` in the background, skippable via `KAGE_SKIP_HOOK=1`) rather than requiring a manual step.

## Supporting evidence

- `.agent_memory/packets/decision-decision-repo-local-kage-memory-should-be-written-directly-as-git-visible-packet-9b07fe4c.md` — the foundational review-boundary decision: repo-local packets are written directly; human review is gated only at promotion to org/global/public/registry/CDN scope.
- `.agent_memory/packets/decision-contributor-profiles-stay-local-git-intelligence-d97134d6.md` — contributor profiles (ownership, hotspots, commit-category mix) computed from local git history and the existing code graph, exposed via CLI/MCP/viewer/docs, with no GitHub calls or hosted database.
- `.agent_memory/packets/decision-workspace-co-change-links-stay-local-git-intelligence-83cfaee4.md` — cross-repo hidden-coupling detection (same-author, 24h window, capped commit size) built the same way: local git logs only, no hosted backend, no network calls.
- `.agent_memory/packets/decision-daemon-rest-exposes-complete-agent-memory-operations-9b6072ac.md` — the daemon's REST endpoints (`/kage/context`, `/kage/capture`, `/kage/learn`, `/kage/feedback`, `/kage/setup-doctor`) reuse existing repo-local memory machinery to give HTTP-only agents parity with MCP agents, rather than building a separate REST memory store.
- `.agent_memory/packets/decision-memory-lifecycle-is-now-a-first-class-report-7e20a9b1.md` — packet lifecycle classification (healthy/hot/cold/stale/disputed/ungrounded/pending/generated) exposed uniformly via CLI, MCP, daemon report, and dashboard, explicitly with no hidden auto-decay.
- `.agent_memory/packets/decision-memory-timeline-is-now-a-first-class-handoff-report-f285de3e.md` — the companion timeline report (recently added/updated/pending/retired packets) for handoff visibility, same uniform CLI/MCP/daemon/viewer exposure pattern.
- `.agent_memory/packets/decision-optional-dense-embeddings-stay-rebuildable-and-opt-in-6e736585.md` — dense embeddings kept as a separate, rebuildable, explicitly opt-in artifact (`kage embeddings build` / `kage recall --embeddings`) so default recall stays local, dependency-free, and fast.
- `.agent_memory/packets/decision-repo-git-hook-keeps-kage-memory-current-after-commits-04fbc7e1.md` — a git post-commit hook automates `kage refresh`/`kage pr summarize` in the background, preserving existing hook content, with an explicit `KAGE_SKIP_HOOK=1` escape hatch.
- `.agent_memory/packets/decision-workspace-contracts-stay-source-evidence-based-ea6a0e82.md` and `.agent_memory/packets/decision-workspace-topic-contracts-stay-deterministic-8ca85087.md` — cross-repo HTTP route contracts and pub/sub topic contracts are detected purely from Kage's own route facts plus grep-style source-string evidence across sibling repos in a workspace, deliberately without a hosted database or generated API docs — the same local-first, deterministic-evidence principle applied to a workspace-scoped feature.
- `.agent_memory/packets/bug_fix-expensive-synchronous-work-must-leave-the-process-not-just-move-after-listen-0f2c0341.md` — `kage viewer`'s report generation was moved to a detached child process after discovering that moving work past `server.listen()` alone still blocks the single-threaded daemon; kept local (no hosted rendering service) by fixing the process model instead of offloading it externally.

The same local-first instinct governs what actually gets committed to git versus regenerated on demand: `.agent_memory/packets/` is the durable, git-tracked source of truth, while `indexes/`, `code_graph/`, `graph/`, `structural/`, and `metrics.json` are derived caches Kage regenerates locally and must never commit — committing them was directly responsible for most of a 127-conflict master merge, since every refresh regenerated and re-diffed those directories. This repo's own `.gitignore` already blanket-ignores `.agent_memory/*` and explicitly un-ignores only `packets/`, so every derived subdirectory here was already excluded regardless of any per-directory listing; the real gap was that `ensureDelegationIgnores()` — which bootstraps `.gitignore` on *other* repos when Kage is installed there — had an incomplete explicit list (missing `store/`, `branches/`, `daemon/`, `marketplace/`, `observations/`, `public-bundle/`, `public-candidates/`, `slots/`, `global-cdn/`, `metrics.json`), so a repo without this repo's blanket rule would still commit those. The recommended way to decide tracked-vs-derived for any given `.agent_memory/` path — in docs, tests, or tooling — is to ask git directly (`git check-ignore -q <path>`, exit 0 = ignored, exit 1 = not ignored, anything else = a real error) rather than hardcoding a list of "the ignored subdirectories," since `.gitignore` itself is the actual source of truth and can drift independently of any doc's or test's assumptions about it. Two CI workflows keep this maintained day to day without a hosted service: `kage-pr.yml` runs on every PR (builds the CLI, runs quality + pr-check, posts a memory-health comment) and `kage-sync.yml` runs on every merge to master (refreshes the graph/indexes, proposes change-memory from the diff, auto-deprecates stale packets with no helpful votes, commits packets back with `[skip ci]`) — its staging is restricted to packets only, never the derived artifacts, consistent with the tracked-vs-derived rule above.

## Contradictions / open questions

None found in the cited evidence — all packets are `approved`/`verified`, apply the same constraint to different features, and none narrows or reverses another's scope. Whether this governance principle survived the later August 2026 store-backend rewrite (which introduces an optional `node:sqlite` file, still local and dependency-free but a real schema/migration surface) is not addressed by any packet in this batch and would be worth checking against `docs/design/MEMORY_STORE.md` directly. Note also that the tracked-vs-derived/gitignore-completeness findings here describe the *diagnosis and fix pattern* as captured at the time; the repo's actual commit history (see recent `kage: ratify ... P1a — derived state is never committed again` commits) indicates this specific gap was subsequently acted on directly in code, so treat the packets above as the rationale trail rather than an unverified todo.
