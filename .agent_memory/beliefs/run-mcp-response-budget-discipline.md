# MCP Tool Response Budget Discipline

**Confidence:** firm — both fixes are grounded in measured, cited byte/character counts on the real repo, not estimates, and both landed with regression tests that assert numeric budgets rather than just "smaller than before."

This is a cluster the assigned packet list didn't name explicitly but that recurs clearly across the goal/run tooling work: Kage's own MCP tools were spending their caller's context window as if it were free, which is a direct tax on exactly the agents Kage exists to help. The core principle, stated in the code as a comment so it survives future additions, is that a CLI response is read by a human who scrolls and skims (verbosity is nearly free) while an MCP response is loaded into an agent's context whether it's needed or not (verbosity is a direct cost) — so the two surfaces must not share a response shape, even when they're derived from the same underlying record. `kage_refresh` was measured returning 149,739 characters on a 448-packet repo, large enough that the calling MCP client refused the result outright and the caller got nothing; the bulk of it was an uncapped array of every stale packet (177 entries at ~580 characters each) rather than any one field being individually bloated. `kage_pr_check` was worse — 321,873 characters, roughly 80,000 tokens, enough to consume a third of a context window in one call — and part of that bloat was pure duplication: the same ~180 warning strings were being echoed twice, once under `validation.warnings` and again under a top-level `warnings` field built by naively spreading both arrays together. The fix pattern in both cases is the same: cap large collections to a small number of the most actionable entries (ranked by whatever the domain already implies is most urgent, not a new invented scoring system), and when truncating, say so explicitly with the true total — "showing 10 of 177" — because a silently truncated list reads as a complete one, and that violates the same honesty law the rest of the product already follows for withheld stale memories. A caller that genuinely needs the rest gets an explicit `limit`/`verbose` argument to ask for more; the default stays capped.

- `.agent_memory/packets/bug_fix-refreshprojects-full-option-kernel-ts-already-existed-but-controls-forcing-a-ful-cd61ae61.md` — the `kage_refresh` fix: measured 149,739 characters / 3,053 lines on this repo at 448 packets, large enough that the MCP client refused the result; the bloat was almost entirely an uncapped `stale_packets` array, not per-entry verbosity. Notes that the existing `full` option on `refreshProject` controls forcing a full code-graph reindex, a different concern, so new `limit`/`verbose` arguments were added rather than overloading it.
- `.agent_memory/packets/decision-kernel-tss-prcheck-builds-its-top-level-warnings-field-as-validation-warnings-ee101401.md` — the `kage_pr_check` fix: measured 321,873 characters (~80,000 tokens) on a single call; found the top-level `warnings` field was built as `[...validation.warnings, ...ownWarnings]`, echoing the same ~183 strings twice; states the CLI-vs-MCP verbosity principle explicitly and cites `kage_supersede` (full old + new packet bodies, ~10,000 tokens for one operation vs. two lines from the CLI) as a further example of the same disease.
- `.agent_memory/packets/gotcha-kage-refresh-returns-150kb-per-call-177-stale-packets-and-78-warnings-dumped-in--d42c8a6e.md` — an independent capture of the same `kage_refresh` measurement from a different session (~150KB, 177 stale packets, 78 warnings), which explicitly frames itself as "the same disease as [an] existing context-bloat-dump packet in this repo's memory, resurfacing in a different tool" — that referenced dump packet is about capture-time serialized dumps (see the admission-quality-floor belief), a different failure mode at a different point in the pipeline, not the same fix; kept here as confirming, independently-discovered evidence of the `kage_refresh` bloat rather than new nuance.

## Contradictions / open questions

- None found in the cited evidence — the packets describe the same recurring defect (uncapped MCP responses) being fixed with the same pattern (cap + honest truncation notice + explicit opt-in for more), and the `kage_pr_check` packet explicitly frames itself as generalizing the fix already applied once to `kage_refresh`.
- Open question the `kage_pr_check` packet raises itself and leaves unresolved in this evidence: it names `kage_supersede` as measured but out of scope for that particular run ("fix that one even if you run short of room for the rest, and say plainly in your claim what you did not get to") — no packet in this set confirms whether `kage_supersede` was subsequently capped.
