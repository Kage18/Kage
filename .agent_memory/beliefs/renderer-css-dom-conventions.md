# CSS/DOM Conventions and Layout Gotchas in the App Renderer

**Confidence:** provisional — each individual layout bug is well-evidenced by a single measured run, but the sample is small (one visual-regression sweep and one phone-width sweep) rather than a broad, repeated pattern like the template-literal or sandbox-testing beliefs.

app-client.ts (DOM structure/behavior) and app-styles.ts (CSS) are separate files describing the same rendered page, and several bugs have come from that split not staying honestly in sync. Most basically, an element's id and its class are just two names for the same DOM node — `#work-split` (from app-html.ts) and `.runs` (from app-styles.ts) are the same element, targeted by whichever selector a given CSS rule finds convenient, not two different elements — so reasoning about "the id-targeted part" versus "the class-targeted part" of a component is a category error worth watching for when changing either file in isolation. Layout bugs recur from standard flexbox behavior colliding with real, variable-length content: flex items shrink below their own content width by default, so label text and grouped count spans wrap word-by-word (sometimes into a vertical stack) unless given `white-space:nowrap` explicitly — this hit both the board's zone-header labels/counts and, separately, the shared `.atom` class used for card chips like "6.4M tok", which lacked `nowrap` even though the sibling `.chip` class already had it. Similarly, a flex-column ancestor missing `min-width:0` lets an unbreakable-text descendant grow the whole chain — the stylesheet had already fixed this once, at `#room-term-pane`, with a comment explaining why, but left the identical pattern unfixed on its sibling `#room-chat-pane` and on ancestors `.view`/`.liverail`/`.liverow`, meaning a documented fix in one place did not get generalized to structurally identical siblings. A second, orthogonal hazard is that some CSS selectors are pinned byte-for-byte by literal-regex tests (`.bh`'s base rule is asserted verbatim by a test in `visual-foundation-pass-on.test.ts`, the same pattern already known for `.turn.you .bubble2`), so a visual fix touching such a selector should add sibling/child rules rather than editing the pinned declaration block, unless the pinning test is deliberately updated too. The stylesheet is intentionally minimal by design — no build step, no framework — but that minimalism had, until a dedicated pass, also meant almost no responsive design existed (three `@media` queries total, one of them `prefers-reduced-motion`), so narrow/phone-width support had to be built largely from scratch rather than patched incrementally. Two more constraints sit above the CSS layer: the renderer must never use `window.prompt`/`confirm`/`alert`, since these throw "not supported" in Electron and Chrome-embedded panes and silently kill whatever control calls them (every confirmation or reason-collection must instead be an in-DOM affordance — inline row, confirm/cancel buttons, Escape to cancel); and a feature that looks missing from the outside sometimes already exists deeper in — a full three-state (system/light/dark) theme cycle with localStorage persistence was already built, and a "close the gap" brief's real gap was just one missing `@media (prefers-color-scheme: light)` block, a reminder to read the current app-styles.ts/app-client.ts closely before assuming a redesign is needed.

## Contradictions / open questions

None of the cited packets conflict with each other. One open note rather than a contradiction: the phone-width sweep (referenced by the `#work-split`/`.runs` and min-width:0 packets) found the stylesheet had essentially no narrow-width design at the time (three `@media` queries, one being `prefers-reduced-motion`) — later packets in this same cluster (the light-theme gap, the zone-header regression) describe a design system that has since grown considerably more deliberate (tokenized colors, a "visual foundation" pass with its own pinned tests, documented flex/min-width fix precedents). Whether the responsive/narrow-layout gap has been fully closed since that sweep is not confirmed by any packet in this set.
