Kage: the control plane for agent-delivered software

The customer contract is simple: connect GitHub, assign work, and receive a reviewable pull request with verified context and evidence.

Task → trusted delivery
01
Connect GitHub

Select repositories and set policies.

02
Give Kage a task

From an issue, prompt, Slack, or API.

03
Build trusted context

Verified memory, code graph, risks, and decisions.

04
Run isolated

Connected agent in a controlled sandbox.

05
Verify

Tests, security, quality, and policy gates.

06
Deliver a draft PR

Evidence, risks, unresolved questions, and human approval.

Kage owns

The task-to-PR outcome

Task state, verified context, routing, policies, evidence, approval, PR delivery, and learning from the result.

Kage connects first

Models and execution

Codex, Claude, GitHub/customer runners, and customer credentials. A managed Kage sandbox becomes an optional paid tier later.

Is this the right product boundary?

A

Approve this direction

Kage owns reliable agent delivery, while models and compute remain pluggable initially.

B

Revise the boundary

Kage should own more or less of execution, delivery, or governance.
